Redis 가 무엇이고 자료구조를 어떻게 쓰는지는 [개념 글](/blog/redis-basics/)에 적었습니다. 이 글은 컨테이너로 실행 중인 Redis 에 접속해 상태를 확인하는 방법입니다.

## redis-cli 접속

도커로 띄웠다면 컨테이너 안에 `redis-cli` 가 이미 들어 있습니다. 따로 설치할 것이 없습니다.

```sh
docker ps                          # 컨테이너 이름이나 ID 확인
docker exec -it myapp-redis bash        # 컨테이너 안으로
redis-cli                          # 여기서 Redis 에 접속
```

이름을 정확히 적어야 합니다. 이름에 버전을 붙여 띄우는 방식이면 `myapp-redis` 가 아니라 `myapp-redis_1.0.0` 이고, 짐작해서 치면 `No such container` 가 납니다. `docker ps` 의 맨 오른쪽 칸이 실제 이름입니다.

셸을 거치지 않고 한 번에 붙을 수도 있습니다.

```sh
docker exec -it myapp-redis redis-cli
```

두 방식의 차이는 이렇습니다. 앞쪽은 컨테이너 안에서 설정 파일을 보거나 다른 명령을 같이 쓸 수 있고, 뒤쪽은 Redis 에만 볼일이 있을 때 한 줄로 끝납니다.

이미지가 가벼운 판이면 `bash` 가 없을 수 있습니다. 그때는 `sh` 로 들어갑니다.

```sh
docker exec -it myapp-redis sh
```

접속하면 프롬프트가 이렇게 바뀝니다.

```
127.0.0.1:6379>
```

앞이 접속한 주소와 포트, 뒤의 `>` 부터가 명령을 치는 자리입니다. `exit` 로 나옵니다.

비밀번호가 걸려 있으면 접속한 뒤 먼저 `AUTH 비밀번호` 를 칩니다. 안 치면 명령마다 `NOAUTH Authentication required.` 가 돌아옵니다.

포트를 밖으로 열어 두었고 호스트에도 `redis-cli` 가 있으면 컨테이너에 들어가지 않고 `redis-cli -h 192.168.0.10 -p 6379` 로 바로 붙습니다.

## 메모리 상태 확인

지금 메모리를 얼마나 쓰고 있는지, 한도에 닿아 키가 버려지고 있는지 봅니다.

```sh
docker exec myapp-redis redis-cli INFO memory | grep -E "used_memory_human|maxmemory_human|maxmemory_policy"
docker exec myapp-redis redis-cli INFO stats | grep evicted_keys
```

| 항목 | 뜻 |
| --- | --- |
| `used_memory_human` | 지금 쓰는 양 |
| `maxmemory_human` | 한도. `0B` 면 한도가 없습니다 |
| `maxmemory_policy` | 한도에 닿았을 때 무엇을 하나 |
| `evicted_keys` | 한도 때문에 버린 키 수 |

`evicted_keys` 가 0 이 아니면 **이미 키가 버려지고 있다는 뜻**입니다. 세션을 담고 있다면 그만큼 로그아웃이 일어났다는 것입니다.

## 키 조회와 모니터링

접속하지 않고 한 줄로 물어볼 수도 있습니다. 컨테이너 안에 있는 Redis 라면 앞에 `docker exec myapp-redis` 를 붙입니다.

```sh
redis-cli DBSIZE                            # 키 개수
redis-cli TYPE session:a1b2c3               # 이 키가 어느 자료구조인가
redis-cli TTL  session:a1b2c3
```

키를 찾을 때는 `KEYS` 대신 `--scan` 을 씁니다. 나눠 가져오기 때문에 전체를 막지 않습니다.

```sh
redis-cli --scan --pattern "session:*" | head -20
redis-cli --scan --pattern "session:*" | wc -l
```

메모리를 많이 쓰는 키는 이것으로 찾습니다.

```sh
redis-cli --bigkeys
```

지금 오가는 명령을 그대로 보려면 `MONITOR` 입니다. 모든 명령을 출력하므로 운영에서는 잠깐만 켭니다.

```sh
redis-cli MONITOR
```

## GUI 도구

`redis-cli` 로 충분한 일이 많지만, 키가 많아지면 목록을 눈으로 훑는 편이 빠릅니다.

저는 [Another Redis Desktop Manager](https://github.com/qishibo/AnotherRedisDesktopManager) 를 씁니다. 오픈소스이고 무료이며 Windows·mac·Linux 판이 있습니다.

고르게 된 이유는 세 가지입니다. **키를 클릭해서 복사하는 게 편하고, JSON 을 넣어 둔 값이 들여쓰기된 형태로 보이고, 값을 그 자리에서 고치거나 지울 수 있습니다.**

두 번째가 특히 차이가 납니다. 객체를 JSON 문자열로 저장해 두면 `redis-cli` 로 꺼낼 때 한 줄로 이어진 채 나옵니다.

```
"{\"callId\":\"a1b2c3\",\"agent\":\"1000\",\"startedAt\":\"2026-09-22T10:00:00\",\"state\":\"TALKING\"}"
```

필드가 열 개를 넘어가면 눈으로 읽기 어렵습니다. 터미널에서 보려면 `jq` 로 넘겨야 합니다.

```sh
docker exec myapp-redis redis-cli GET session:a1b2c3 | jq
```

GUI 는 이걸 알아서 펼쳐서 보여줍니다. 값을 자주 들여다봐야 하면 이 차이가 쌓입니다.

값을 고치는 것은 `redis-cli` 로도 되지만, 긴 JSON 의 한 필드만 바꾸려면 전체를 다시 쳐야 합니다. GUI 는 그 자리에서 고쳐 저장합니다. 테스트 데이터를 손으로 만들거나 잘못 들어간 값을 바로잡을 때 쓰입니다.

대신 운영 Redis 에 붙였을 때 위험한 기능이기도 합니다. [개념 글](/blog/redis-basics/#원본이-어디-있느냐로-갈립니다)에서 본 것처럼 **진행 중인 콜 상태나 세션은 그 순간 Redis 가 원본**입니다. 실수로 지우면 되살릴 곳이 없습니다. 삭제 버튼에 확인 절차가 없는 도구도 있어서, 운영 접속과 개발 접속을 목록에서 눈에 띄게 구분해 두는 편이 안전합니다. 접속 이름에 `[운영]` 을 붙이는 정도로도 됩니다.

또 키를 콜론 기준으로 접어서 보여줍니다. `call:20260922:1000` 같은 키가 수천 개면 `call` → `20260922` 로 묶여서, 어느 종류가 얼마나 있는지 펼쳐 보며 찾게 됩니다.

### 다른 도구

| 도구 | 성격 |
| --- | --- |
| **RedisInsight** | Redis 를 만드는 쪽의 공식 도구. 무료입니다. 어떤 키가 메모리를 많이 쓰는지 분석하고 느린 명령 기록을 함께 봅니다 |
| **DataGrip**, IntelliJ Ultimate | JetBrains 도구를 이미 쓰고 있으면 같은 창에서 봅니다 |
| **VS Code 확장** | 편집기 안에서 키를 훑고 값을 고칩니다 |
| **TablePlus** | 유료. 관계형 DB와 Redis 를 한 도구로 |
| **Medis** | mac |

운영 상태를 파고들 일이 많으면 **RedisInsight** 를 같이 깔아 두는 편이 낫습니다. 메모리를 먹는 키를 찾는 화면이 `--bigkeys` 보다 보기 편하고, 메모리 정책을 정할 때 근거가 됩니다.

> 검색하면 **Redis Desktop Manager** 라는 이름이 많이 나옵니다. 지금은 `RESP.app` 으로 이름이 바뀌고 유료가 됐습니다. 이 글에서 말하는 Another Redis Desktop Manager 와는 다른 도구입니다. 가격 정책은 바뀌니 받기 전에 확인하는 편이 좋습니다.

### 포트와 SSH 터널

GUI 는 컨테이너 밖에서 접속하므로 **포트가 호스트로 열려 있어야** 합니다.

```sh
docker port myapp-redis
# 6379/tcp -> 0.0.0.0:6379   이렇게 나오면 붙을 수 있습니다
```

아무것도 안 나오면 컨테이너 안에서만 쓰도록 띄운 것입니다. 이때는 두 가지 방법이 있습니다. 도구의 **SSH 터널** 기능으로 서버를 거쳐 붙거나, `docker exec` 로 들어가 `redis-cli` 를 쓰는 것입니다.

`0.0.0.0` 은 호스트의 모든 네트워크 인터페이스에 열렸다는 뜻입니다. 그 호스트에 닿을 수 있으면 누구든 접속을 시도할 수 있다는 것이라, 비밀번호가 걸려 있는지 같이 확인합니다.

```sh
docker exec myapp-redis redis-cli CONFIG GET requirepass
```

값이 비어 있으면 비밀번호가 없는 상태입니다. 특정 인터페이스로만 열려면 `-p 6379:6379` 대신 `-p 127.0.0.1:6379:6379` 처럼 앞에 주소를 붙입니다.

SSH 터널을 쓰면 채우는 칸이 두 벌입니다.

| | 넣는 것 |
| --- | --- |
| Host, Port | `127.0.0.1`, `6379` — 서버 입장에서 본 Redis 주소 |
| SSH Host, Port | 서버 IP, `22` |
| SSH Username | 서버 로그인 계정 |
| SSH Key, Password | 서버 접속 인증 |

Redis 주소를 `127.0.0.1` 로 적는 것이 헷갈리는 지점입니다. 내 PC 가 아니라 **SSH 로 들어간 서버에서 본 주소**입니다.

붙고 나서 키 목록을 불러오는 버튼을 누를 때는 한 번 생각합니다. 그 버튼이 `KEYS` 를 쓰면 키가 많을 때 [Redis 전체가 그동안 멈춥니다](/blog/redis-basics/#명령을-한-줄로-세워-하나씩-처리합니다). 운영에 붙이기 전에 개발 Redis 에서 먼저 눌러 보고, 앞에서 본 `MONITOR` 로 어떤 명령이 나가는지 확인해 두면 됩니다.

## 명령어 한눈에

| 하려는 것 | 명령 |
| --- | --- |
| 컨테이너 안에서 접속 | `docker exec -it myapp-redis redis-cli` |
| 열린 포트 확인 | `docker port myapp-redis` |
| 메모리 상태 | `redis-cli INFO memory` |
| 버려진 키 수 | `redis-cli INFO stats` 의 `evicted_keys` |
| 키 개수 | `redis-cli DBSIZE` |
| 키 찾기 | `redis-cli --scan --pattern "session:*"` |
| 큰 키 찾기 | `redis-cli --bigkeys` |
| 오가는 명령 보기 | `redis-cli MONITOR` |
