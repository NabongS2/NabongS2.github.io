HTTP 상태 코드와 에러 위치 확인

2026년 10월 12일 · 읽는 데 8분
nabong

브라우저가 요청을 보내면 서버는 응답 맨 앞에 세 자리 숫자를 붙여 돌려줍니다. 이 숫자가 상태 코드입니다. 이 글은 주요 상태 코드의 뜻과, 화면에 에러가 떴을 때 그 에러가 어디서 났는지 확인하는 방법입니다.

상태 코드

섹션 제목: “상태 코드”

응답의 첫 줄은 이렇게 생겼습니다.

부분 값 뜻
프로토콜 HTTP/1.1 주고받는 규약의 버전
상태 코드 404 요청이 어떻게 처리됐는지
이름 Not Found 상태 코드를 사람이 읽을 수 있게 붙인 이름

숫자와 이름은 HTTP 규약(지금은 RFC 9110)에 정해져 있습니다. 그래서 어느 서버든 404 는 “요청한 것을 찾지 못했다” 는 같은 뜻으로 씁니다. 프로그램은 숫자만 보고, 이름은 사람을 위해 붙어 있습니다.

1xx~5xx 분류

섹션 제목: “1xx~5xx 분류”

상태 코드는 첫 자리로 다섯 가지로 나뉩니다. 처음 보는 코드라도 첫 자리만 보면 성공인지, 어디 문제인지 알 수 있습니다.

분류 뜻 원인을 찾을 곳
1xx 처리 중이라는 알림 거의 볼 일이 없습니다. WebSocket 연결 전환의 101 정도입니다
2xx 성공 문제없음
3xx 리다이렉션. 다른 주소로 다시 요청하라는 응답입니다. 304 는 저장해 둔 파일을 그대로 쓰라는 뜻이라 조금 다릅니다 리다이렉트 설정, 캐시
4xx 요청이 잘못됐거나 허용되지 않음 요청. 주소, 값, 로그인 상태, 권한
5xx 요청은 맞는데 서버가 처리하지 못함 서버. 백엔드 로그, Nginx 로그

주요 상태 코드

섹션 제목: “주요 상태 코드”

2xx

섹션 제목: “2xx”
코드 이름 언제
200 OK 조회, 수정 같은 요청이 성공하고 응답 본문이 있을 때
201 Created 새로 만드는 요청(POST)이 성공했을 때
204 No Content 성공했지만 돌려줄 본문이 없을 때. 삭제 요청에 자주 씁니다

3xx

섹션 제목: “3xx”
코드 이름 언제
301 Moved Permanently 주소가 영영 바뀌었으니 새 주소로 가라. Nginx 2편의 http → https 이동
302 Found 이번만 다른 주소로 가라. 로그인 안 된 사용자를 로그인 화면으로 보낼 때
304 Not Modified 바뀐 게 없으니 저장해 둔 것을 써라. 에러가 아닙니다

3xx 응답에는 Location 헤더로 갈 주소가 함께 옵니다. 브라우저는 이 주소로 다시 요청하기 때문에, 개발자 도구에는 요청이 두 줄로 보입니다.

4xx

섹션 제목: “4xx”
코드 이름 언제
400 Bad Request 요청 값이 잘못됐을 때. JSON 형식 오류, 필수 값 누락, 타입이 다른 값
401 Unauthorized 누구인지 확인되지 않았을 때. 로그인 안 함, 토큰 없음·만료
403 Forbidden 누구인지는 알지만 이 요청을 할 권한이 없을 때
404 Not Found 그 주소에 해당하는 것이 없을 때
405 Method Not Allowed 주소는 있는데 방식이 다를 때. POST 만 받는 주소에 GET 을 보냄
413 Content Too Large 요청 본문이 너무 클 때. 큰 파일 업로드

5xx

섹션 제목: “5xx”
코드 이름 언제
500 Internal Server Error 백엔드가 처리하다 예외가 났을 때
502 Bad Gateway 중간의 프록시(Nginx)가 백엔드에서 제대로 된 응답을 받지 못했을 때
503 Service Unavailable 서버가 잠시 요청을 받을 수 없을 때. 점검 중, 과부하
504 Gateway Timeout 중간의 프록시가 백엔드 응답을 기다리다 시간이 다 됐을 때

비슷한 코드 비교

섹션 제목: “비슷한 코드 비교”

401 과 403

섹션 제목: “401 과 403”

둘 다 “안 된다” 는 응답이지만 이유가 다릅니다.

401 403
뜻 누구인지 확인되지 않음 누구인지는 알지만 허용되지 않음
흔한 원인 로그인 안 함, 토큰 만료 일반 사용자가 관리자 API 호출
해결 다시 로그인 권한을 받거나, 권한이 있는 계정으로

401 의 이름이 Unauthorized(권한 없음)라서 헷갈리는데, 실제 뜻은 “인증되지 않음” 입니다. 권한이 없을 때는 403 입니다. 그래서 프론트엔드는 보통 401 을 받으면 로그인 화면으로 보내고, 403 을 받으면 권한이 없다는 안내를 띄웁니다.

404 와 405

섹션 제목: “404 와 405”

404 는 주소 자체가 없는 것이고, 405 는 주소는 있는데 GET·POST 같은 방식이 맞지 않는 것입니다. 405 가 나오면 주소는 맞게 쓴 것이니, 프론트의 요청 방식과 백엔드의 @GetMapping·@PostMapping 을 맞춰 봅니다.

301 과 302

섹션 제목: “301 과 302”

301 은 브라우저가 기억합니다. 한 번 301 을 받으면 다음부터는 서버에 묻지 않고 바로 새 주소로 갑니다. 그래서 잘못 걸어 둔 301 은 설정을 고쳐도 사용자 브라우저에 한동안 남습니다. 바뀔 수 있는 이동이면 302 를 씁니다.

POST 요청을 다른 주소로 보낼 때는 307(잠시), 308(영영)도 있습니다. 301·302 는 브라우저가 요청을 GET 으로 바꿔 보낼 수 있지만, 307·308 은 방식과 본문을 그대로 유지합니다.

502 와 504

섹션 제목: “502 와 504”

둘 다 Nginx 같은 프록시가 돌려주는 코드입니다.

502 504
뜻 백엔드에서 제대로 된 응답을 받지 못함 백엔드 응답을 기다리다 시간이 다 됨
흔한 원인 백엔드가 꺼짐, 주소·포트가 틀림 백엔드 처리가 오래 걸림, 백엔드가 멈춤
걸리는 시간 대개 바로 proxy_read_timeout(기본 60초) 뒤

에러가 뜨기까지 걸린 시간도 단서입니다. 바로 뜨면 502, 1분쯤 기다린 뒤 뜨면 504 일 가능성이 큽니다. 자세한 원인은 Nginx error 로그에 남습니다.

500 과 502

섹션 제목: “500 과 502”

500 은 백엔드가 요청을 받아서 처리하다 실패한 것이고, 502 는 요청이 백엔드까지 가지 못했거나 백엔드가 응답을 끝내지 못한 것입니다. 500 이면 백엔드 로그에 예외가 남아 있고, 502 면 백엔드 로그에는 그 요청이 아예 없는 경우가 많습니다.

에러 위치 확인

섹션 제목: “에러 위치 확인”

브라우저 → Nginx → 백엔드 구조에서는 에러가 이 세 곳 중 한 곳에서 발생합니다. 같은 404 라도 발생 위치에 따라 고칠 곳이 다릅니다.

개발자 도구 Network 탭

섹션 제목: “개발자 도구 Network 탭”

브라우저 개발자 도구(F12)의 Network 탭에서 실패한 요청을 누르면 세 곳을 봅니다.

탭 볼 것
Headers Status Code 줄의 상태 코드와 이름, Content-Type
Response 응답 본문. HTML 인지 JSON 인지
Timing 응답까지 걸린 시간. 504 인지 가늠할 때

응답 본문 비교

섹션 제목: “응답 본문 비교”

같은 404 라도 응답 본문의 모양이 다릅니다.

Nginx 의 에러 응답은 짧은 HTML 화면입니다. 맨 아래에 nginx 가 표시됩니다.

Spring Boot 의 에러 응답은 JSON 입니다. 따로 바꾸지 않았다면 이런 모양입니다.

응답 본문 발생 위치 확인할 곳
nginx 가 표시된 HTML Nginx Nginx 설정, Nginx error 로그
status, error, path 가 있는 JSON 백엔드 백엔드 로그, 컨트롤러 경로
프로젝트에서 정한 JSON (code, message 등) 백엔드의 예외 처리 백엔드 로그

응답 헤더의 Server: nginx 는 구분에 쓸 수 없습니다. Nginx 는 백엔드 응답을 넘길 때 백엔드의 Server 헤더를 빼고 자기 것을 붙여서, 백엔드가 만든 응답에도 Server: nginx 가 보입니다.

404 에서 자주 있는 경우는 둘입니다. 화면 파일(/assets/index-3f9a1c2e.js)이 404 면 배포한 dist 와 브라우저의 index.html 이 맞지 않는 것이고, API(/api/...)가 JSON 404 면 프론트가 호출한 주소와 백엔드의 경로가 다른 것입니다.

브라우저 오류

섹션 제목: “브라우저 오류”

브라우저에서 멈춘 에러는 상태 코드가 없거나, 있어도 화면 코드가 응답을 읽지 못합니다. Network 탭의 Status 칸에 숫자 대신 다른 글자가 보입니다.

Network 탭 표시 뜻 확인할 곳
(failed) net::ERR_CONNECTION_REFUSED 그 주소와 포트에 실행 중인 서버가 없습니다 서버·컨테이너가 떠 있는지, 포트가 맞는지
(failed) net::ERR_CERT_AUTHORITY_INVALID 믿을 수 없는 인증서입니다 자체 서명 인증서인지, 인증서 설정
CORS error 화면과 다른 곳에서 온 응답을 브라우저가 막았습니다. 아래 설명 참고 화면과 API 주소가 같은지

CORS 오류

섹션 제목: “CORS 오류”

콘솔 메시지

섹션 제목: “콘솔 메시지”

로컬에서 화면(localhost:5173)이 백엔드(localhost:8100)를 직접 호출하면, 브라우저 콘솔에 이런 메시지가 뜹니다.

5173 에서 열린 화면이 8100 의 응답을 읽으려 했는데, 허용 표시가 없어서 브라우저가 막았다는 뜻입니다. 백엔드는 정상으로 응답했는데 화면에서는 실패로 처리됩니다.

동일 출처 정책

섹션 제목: “동일 출처 정책”

브라우저가 응답을 막는 이유는 보안입니다.

은행 사이트 bank.com 에 로그인해 둔 채로, 다른 탭에서 evil.com 을 열었다고 해 봅니다. evil.com 의 JS 가 fetch('https://bank.com/api/account') 를 실행하면, 브라우저는 bank.com 으로 가는 요청에 로그인 쿠키를 자동으로 붙여 보냅니다. 이 응답을 evil.com 의 JS 가 읽을 수 있다면 계좌 정보가 그대로 넘어갑니다.

그래서 브라우저에는 화면의 JS 는 화면과 같은 출처에서 온 응답만 읽을 수 있다는 기본 규칙이 있습니다. 이 규칙을 동일 출처 정책(Same-Origin Policy)이라고 합니다.

CORS

섹션 제목: “CORS”

다른 출처의 응답을 읽어야 하는 정상적인 경우도 있습니다. 그때 서버가 직접 허용해 주는 방법이 CORS(Cross-Origin Resource Sharing)입니다.

서버가 응답에 Access-Control-Allow-Origin: http://localhost:5173 헤더를 붙이면, 브라우저는 이 화면이 응답을 읽어도 된다고 보고 넘겨줍니다. 이 헤더가 없으면 막습니다. 이것이 CORS 오류입니다.

그래서 CORS 오류는 서버 에러가 아니라, 브라우저가 보안 규칙에 따라 응답을 화면 코드에 넘기지 않은 것입니다. 백엔드는 이미 응답을 보냈기 때문에, 백엔드 로그에는 그 요청이 정상(200)으로 남아 있을 수 있습니다.

출처

섹션 제목: “출처”

브라우저가 “같은 곳인가” 를 판단하는 기준이 출처(origin)입니다. 출처는 URL 에서 프로토콜, 호스트, 포트 세 가지만 떼어 낸 것이고, 경로와 쿼리는 들어가지 않습니다.

구분 범위 예
URL 주소 전체. 프로토콜, 호스트, 포트, 경로, 쿼리 http://localhost:5173/history/12?tab=info
출처 (origin) 프로토콜, 호스트, 포트 http://localhost:5173

세 가지가 모두 같으면 같은 출처, 하나라도 다르면 다른 출처입니다. 화면이 http://localhost:5173 에서 열려 있을 때 API 주소별로 비교하면 이렇습니다.

API 주소 출처 다른 부분
http://localhost:5173/api/users 같음 경로만 다름
http://localhost:8100/api/users 다름 포트 (5173, 8100)
https://localhost:5173/api/users 다름 프로토콜 (http, https)
http://192.168.0.20:5173/api/users 다름 호스트

localhost:5173 과 localhost:8100 은 같은 컴퓨터이지만 포트가 달라 다른 출처입니다. 위의 콘솔 메시지가 이 경우입니다.

해결 방법

섹션 제목: “해결 방법”
방법 내용 예
같은 출처로 맞추기 화면과 API 를 한 주소로 받고, 서버 안에서 백엔드로 넘깁니다 Vite 프록시, Nginx 프록시
서버에서 허용하기 백엔드가 응답에 Access-Control-Allow-Origin 헤더를 붙입니다 Spring 의 @CrossOrigin, CORS 설정

첫 번째 방법은 Nginx 1편의 구조입니다. 화면 코드는 fetch('/api/users') 처럼 경로만 적고, 브라우저는 이 요청을 화면과 같은 주소로 보냅니다. 백엔드로 넘기는 일은 Nginx 가 서버 안에서 하기 때문에 브라우저는 알지 못합니다.

브라우저 입장에서는 처음부터 끝까지 app.example.com 하고만 주고받았으니 CORS 를 따지지 않습니다. 로컬 개발의 Vite 프록시도 같습니다. 화면(localhost:5173)에서 /api 로 요청하면 Vite 개발 서버가 받아서 8100 으로 넘깁니다.
