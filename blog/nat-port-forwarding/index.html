NAT 와 포트포워딩

2026년 10월 22일 · 읽는 데 5분
nabong

시리즈네트워크 기초

  1. 네트워크 계층

  3. NAT 와 포트포워딩
  4. VPN
  5. DNS 와 도메인
  6. HTTPS 와 인증서

앞 글에서 사설 IP 는 내부 네트워크마다 따로 쓰기 때문에 인터넷에서 찾아올 수 없다고 했습니다. 그런데 사설 IP 를 쓰는 회사 PC 도 인터넷 사이트에는 접속합니다. 이 글에서는 사설 IP 를 쓰는 컴퓨터가 인터넷에 접속하는 방법(NAT)과, 외부에서 내부 서버에 접속하게 하는 방법(포트포워딩)을 알아봅니다.

이 글의 예시에서 쓰는 주소는 다음과 같습니다.

이름 주소
공유기(또는 회사 방화벽)의 공인 IP 203.0.113.10
내부 PC 192.168.0.31
내부 서버 192.168.0.20
인터넷의 외부 서버 198.51.100.10

NAT

섹션 제목: “NAT”

NAT(Network Address Translation)는 요청이 내부 네트워크를 나갈 때 출발지 주소를 공인 IP 로 바꾸고, 응답이 돌아오면 다시 원래 내부 주소로 돌려주는 기능입니다. 집에서는 공유기가, 회사에서는 방화벽이나 라우터가 이 일을 합니다.

내부 PC 가 외부 서버에 요청을 보내면 다음 순서로 진행됩니다.

단계 출발지 목적지 하는 일
1 192.168.0.31:51000 198.51.100.10:443 내부 PC 가 요청을 보냅니다
2 203.0.113.10:40001 198.51.100.10:443 공유기가 출발지를 자기 공인 IP 와 새 포트로 바꿔 보내고, 40001 ↔ 192.168.0.31:51000 을 기록해 둡니다
3 198.51.100.10:443 203.0.113.10:40001 외부 서버가 공유기의 공인 IP 로 응답합니다
4 198.51.100.10:443 192.168.0.31:51000 공유기가 기록을 보고 응답을 내부 PC 에 전달합니다

외부 서버는 공유기의 공인 IP 만 보고, 내부 PC 의 사설 IP 는 알지 못합니다. 내부의 여러 PC 가 공인 IP 하나를 함께 쓰는 것도 이 기록 덕분입니다. 공유기가 PC 마다 다른 포트를 배정해 기록하므로, 응답이 섞이지 않고 각 PC 로 전달됩니다.

밖에서 들어오는 요청

섹션 제목: “밖에서 들어오는 요청”

NAT 는 내부에서 먼저 보낸 요청의 응답만 돌려보낼 수 있습니다. 밖에서 203.0.113.10:8080 으로 새 요청이 오면 공유기에는 그 포트에 대한 기록이 없습니다. 내부의 어느 컴퓨터로 보내야 할지 알 수 없으므로 요청은 버려집니다.

그래서 내부 서버를 밖에서 접속할 수 있게 하려면, 어느 포트로 온 요청을 어느 내부 주소로 보낼지 공유기에 미리 등록해 두어야 합니다. 이것이 포트포워딩입니다.

포트포워딩

섹션 제목: “포트포워딩”

포트포워딩은 공유기나 방화벽에 “이 포트로 들어온 요청은 내부의 이 주소로 보낸다”는 규칙을 등록하는 설정입니다.

외부 포트 보낼 내부 주소 용도
8080 192.168.0.20:8080 내부 서버의 웹 서비스
2222 192.168.0.20:22 내부 서버의 SSH

이 규칙이 있으면 밖에서 http://203.0.113.10:8080 으로 접속했을 때 공유기가 요청을 192.168.0.20:8080 으로 전달합니다. 두 번째 줄처럼 외부 포트와 내부 포트를 다르게 정할 수도 있습니다. 밖에서는 ssh -p 2222 dev@203.0.113.10 으로 접속하고, 요청은 내부 서버의 22 번 포트로 전달됩니다.

규칙은 집에서는 공유기 관리 화면에서, 회사에서는 방화벽 설정에서 정합니다.

서버가 보는 접속자 IP

섹션 제목: “서버가 보는 접속자 IP”

포트포워딩은 목적지 주소만 바꾸고 출발지 주소는 바꾸지 않습니다. 그래서 내부 서버는 접속한 사람의 공인 IP 를 그대로 봅니다.

Nginx 같은 리버스 프록시는 다릅니다. 리버스 프록시는 요청을 받아 자기가 새 요청을 보내기 때문에, 뒤의 백엔드는 접속자 대신 프록시의 IP 를 봅니다. 백엔드가 원래 접속자 IP 를 알려면 X-Forwarded-For 같은 헤더가 필요한 이유가 이것입니다.

포트포워딩 리버스 프록시
하는 일 목적지 주소를 바꿔 전달 요청을 받아 새 요청으로 다시 보냄
보는 정보 (계층) IP 주소, 포트 (3·4계층) HTTP 경로, 헤더 (7계층)
서버가 보는 접속자 IP 원래 접속자의 IP 프록시의 IP
경로·헤더 처리 하지 않음 경로별로 나누고 헤더를 더할 수 있음

내부에서 공인 주소로 접속

섹션 제목: “내부에서 공인 주소로 접속”

포트포워딩을 설정한 뒤 같은 내부 네트워크의 PC 에서 203.0.113.10:8080 으로 접속하면 접속되지 않는 경우가 있습니다. 내부에서 나간 요청이 공유기를 거쳐 다시 내부로 돌아와야 하는데, 이 기능(NAT 루프백, 헤어핀 NAT)을 지원하지 않거나 꺼 둔 장비가 있기 때문입니다.

내부에서는 192.168.0.20:8080 처럼 사설 IP 로 접속합니다. 포트포워딩이 제대로 설정되었는지는 휴대폰 데이터 통신처럼 내부 네트워크 밖에서 확인합니다.

Docker -p 와 포트포워딩

섹션 제목: “Docker -p 와 포트포워딩”

docker run -p 8080:80 도 같은 원리입니다. 컨테이너는 호스트 안의 별도 네트워크에서 172.17.0.2 같은 사설 IP 를 받습니다. -p 는 호스트의 8080 포트로 들어온 요청을 그 컨테이너의 80 포트로 보내는 규칙을 Docker 가 호스트에 만들어 두는 옵션입니다.

공유기 포트포워딩 Docker -p 8080:80
밖에서 접속하는 주소 공인 IP 203.0.113.10:8080 호스트 IP 192.168.0.20:8080
실제로 받는 곳 내부 서버 192.168.0.20:8080 컨테이너 172.17.0.2:80
규칙을 두는 곳 공유기·방화벽 설정 Docker 가 호스트의 방화벽 규칙(iptables)에 추가

Linux 에서 Docker 가 추가하는 규칙은 ufw 같은 방화벽 설정보다 먼저 적용됩니다. ufw 에서 8080 을 막아 두어도 -p 8080:80 으로 연 포트는 밖에서 접속될 수 있습니다. 같은 서버 안에서만 쓸 포트라면 앞 글처럼 -p 127.0.0.1:8080:80 으로 바인딩 주소를 지정합니다.

포트포워딩의 접속 범위

섹션 제목: “포트포워딩의 접속 범위”

포트포워딩으로 연 포트는 그 공인 IP 와 포트를 아는 사람이면 누구나 접속을 시도할 수 있습니다. 공인 IP 주소 범위는 공개되어 있어서, 열린 포트를 자동으로 찾는 프로그램이 인터넷 전체를 계속 확인하고 있습니다. 주소를 알리지 않았더라도 연 지 얼마 지나지 않아 접속 시도가 들어옵니다.

확인할 것 이유
꼭 필요한 포트만 엽니다 열린 포트마다 공격받을 수 있는 프로그램이 하나씩 늘어납니다
로그인이나 비밀번호가 있는 서비스인지 확인합니다 인증 없는 관리 화면이나 API 는 접속한 누구나 쓸 수 있습니다
방화벽에서 접속을 허용할 IP 를 정할 수 있는지 확인합니다 회사 사무실 IP 처럼 정해진 곳에서만 접속하게 할 수 있습니다
HTTPS 로 여는지 확인합니다 HTTP 는 주고받는 내용이 암호화되지 않습니다

DB, Redis 처럼 앱 서버만 접속하면 되는 포트는 포트포워딩으로 열지 않습니다. 비밀번호를 설정해 두어도 비밀번호를 계속 대입해 보는 공격의 대상이 됩니다.

밖에서 내부 서버를 써야 하는 사람이 정해져 있다면, 포트를 인터넷에 여는 대신 그 사람들만 내부 네트워크에 접속하게 하는 방법도 있습니다. 다음 글에서 다루는 VPN 입니다.

정리

섹션 제목: “정리”
작업 방법
내부 PC 에서 인터넷 사이트에 접속 NAT. 공유기가 자동으로 처리
밖에서 내부 서버에 접속 공유기·방화벽에 포트포워딩 규칙 추가
호스트의 포트로 컨테이너에 접속 docker run -p 호스트포트:컨테이너포트
컨테이너 포트를 같은 서버에서만 쓰기 -p 127.0.0.1:호스트포트:컨테이너포트
포트포워딩 설정 확인 내부 네트워크 밖(휴대폰 데이터 등)에서 공인IP:포트 로 접속
