CSR 과 SSR 의 차이

2026년 10월 12일 · 읽는 데 6분
nabong

화면에 보이는 것은 결국 HTML 입니다. 그 HTML 을 브라우저가 만드느냐, 서버가 만들어서 보내느냐에 따라 CSR 과 SSR 로 나뉩니다. 이 글에서는 CSR 과 SSR 의 요청 흐름이 어떻게 다르고, 지금 쓰는 프레임워크가 어느 쪽에 속하는지 알아보려 합니다.

렌더링

섹션 제목: “렌더링”

렌더링은 데이터를 화면에 보일 HTML 로 만드는 일입니다. 같은 /history/12 화면이라도, 기록 데이터를 받아서 제목과 표가 들어간 HTML 로 만드는 과정이 필요합니다.

이름 HTML 을 만드는 곳
CSR Client-Side Rendering 브라우저. JS 가 실행되면서 만듭니다
SSR Server-Side Rendering 서버. 요청이 올 때마다 만들어서 보냅니다

요청 흐름

섹션 제목: “요청 흐름”

CSR

섹션 제목: “CSR”

Vite 로 빌드한 React 앱이 이 방식입니다. Nginx 1편에서 본 dist 가 그 결과물입니다.

  1. 브라우저가 /history/12 를 요청하면 Nginx 가 index.html 을 보냅니다.
  2. index.html 에는 내용이 없고, JS 파일을 불러오는 줄만 있습니다.
  3. 브라우저가 JS 를 내려받아 실행하고, JS 가 /api/history/12 를 호출해 데이터를 받습니다.
  4. JS 가 받은 데이터로 <div id="root"> 안에 화면을 만듭니다.

화면은 4번이 끝나야 보입니다. 1~3 동안은 빈 화면이나 로딩 표시가 보입니다.

서버가 하는 일은 파일을 보내는 것뿐입니다. 어느 주소로 요청하든 같은 index.html 을 보내면 되고, 주소에 맞는 화면은 JS 가 알아서 만듭니다. Nginx 1편의 try_files $uri $uri/ /index.html 이 이 일을 합니다.

SSR

섹션 제목: “SSR”

Next.js, Nuxt 같은 프레임워크가 이 방식입니다. 요청을 받는 서버가 Node 로 실행됩니다.

  1. 브라우저가 /history/12 를 요청하면 Node 서버가 받습니다.
  2. Node 서버가 API 를 직접 호출해 데이터를 받습니다.
  3. Node 서버가 데이터를 채운 HTML 을 만들어 보냅니다.
  4. 브라우저는 받은 HTML 을 바로 보여 줍니다.
  5. 이어서 JS 가 내려받아져 실행되고, 이미 보이는 화면에 클릭 같은 동작을 연결합니다.

화면은 4번에서 보입니다. 서버가 API 호출과 HTML 만들기를 먼저 끝내고 보내기 때문입니다.

hydration

섹션 제목: “hydration”

SSR 의 5번을 hydration 이라고 합니다. 서버가 보낸 HTML 은 보이기만 하는 상태라, 버튼을 눌러도 아무 일이 일어나지 않습니다. JS 가 실행되면서 이미 있는 HTML 에 이벤트를 연결하고 나서야 CSR 앱처럼 동작합니다.

그래서 SSR 에서도 JS 는 받습니다. 차이는 화면이 JS 를 기다리지 않고 먼저 보인다는 점입니다. hydration 이 끝난 뒤의 화면 이동은 CSR 처럼 브라우저 안에서 처리합니다.

페이지 소스로 확인

섹션 제목: “페이지 소스로 확인”

지금 보는 화면을 CSR 과 SSR 중 어느 방식으로 만들었는지는 브라우저에서 페이지 소스 보기(Ctrl + U) 로 확인합니다. 페이지 소스는 서버가 보낸 HTML 그대로라, JS 가 실행되기 전의 모습입니다.

페이지 소스 방식
<div id="root"></div> 처럼 비어 있고 화면의 글자가 없음 CSR
화면에 보이는 글자가 HTML 에 들어 있음 SSR, 또는 SSG(빌드할 때 미리 만들어 둔 HTML, 아래에서 설명)

개발자 도구의 Elements 탭은 JS 가 만든 결과까지 보여 주기 때문에, CSR 이어도 내용이 다 보입니다. 구분할 때는 Elements 가 아니라 페이지 소스를 봅니다.

차이

섹션 제목: “차이”
CSR SSR
HTML 을 만드는 곳 브라우저 서버 (Node)
처음 받는 HTML 내용 없음 내용이 들어 있음
첫 화면이 보이는 시점 JS 실행과 API 호출이 끝난 뒤 HTML 을 받은 직후
화면 이동 브라우저 안에서 바로 바뀜 hydration 뒤에는 CSR 과 같음
검색 엔진, 링크 미리보기 내용을 읽지 못할 수 있음 HTML 에 있는 내용을 읽음
서버 파일만 보내면 됨 (Nginx) 요청마다 HTML 을 만드는 Node 서버
서버 부담 적음 요청마다 렌더링 비용

첫 화면

섹션 제목: “첫 화면”

CSR 은 JS 파일이 클수록, API 가 느릴수록 첫 화면이 늦게 뜹니다. 그 사이 사용자는 빈 화면을 봅니다. SSR 은 서버에서 API 를 호출하는 시간만큼 HTML 응답이 늦어지지만, 받자마자 내용이 보입니다.

화면 이동

섹션 제목: “화면 이동”

CSR 은 한 번 JS 를 받고 나면 메뉴를 옮길 때 HTML 을 새로 받지 않습니다. JS 가 화면만 바꾸고 필요한 데이터만 API 로 받아서, 이동이 빠릅니다. 이렇게 HTML 한 장으로 여러 화면을 바꿔 가며 보여 주는 앱을 SPA(Single Page Application)라고 합니다.

검색 엔진과 링크 미리보기

섹션 제목: “검색 엔진과 링크 미리보기”

검색 엔진과, 메신저로 링크를 보냈을 때 뜨는 미리보기는 서버가 보낸 HTML 을 읽습니다. CSR 은 HTML 이 비어 있어서 내용이나 제목·이미지를 못 읽는 경우가 있습니다. Google 은 JS 를 실행해서 읽기도 하지만, 메신저 미리보기는 HTML 만 읽는 경우가 많습니다.

서버와 배포

섹션 제목: “서버와 배포”
CSR SSR
빌드 결과 HTML, JS, CSS 파일 (dist) Node 로 실행하는 서버 앱
배포 파일을 Nginx 에 올림 Node 서버를 컨테이너로 띄움
Nginx 의 역할 파일을 내보내고 /api 를 백엔드로 넘김 요청을 Node 서버로 넘김

CSR 은 백엔드가 하나 늘지 않습니다. SSR 은 프론트엔드도 서버가 되어서, 띄우고 지켜봐야 할 프로세스가 하나 더 생깁니다.

SSG

섹션 제목: “SSG”

SSG(Static Site Generation)는 HTML 을 빌드할 때 미리 만들어 두는 방식입니다. 요청이 오면 만들어 둔 파일을 보내기만 합니다.

HTML 을 만드는 때 서버
CSR 요청 뒤, 브라우저에서 파일만 보냄
SSR 요청마다, 서버에서 Node 서버
SSG 빌드할 때 한 번 파일만 보냄

이 블로그가 SSG 입니다. 글을 올릴 때 빌드하면서 글마다 HTML 을 만들어 두고, GitHub Pages 는 그 파일을 보내기만 합니다. 그래서 페이지 소스에 글 내용이 다 들어 있고, 서버는 CSR 처럼 파일만 있으면 됩니다.

대신 빌드한 뒤에 바뀐 내용은 다시 빌드해야 반영됩니다. 글처럼 자주 바뀌지 않는 내용에 맞고, 사용자마다 다른 데이터를 보여 주는 화면에는 맞지 않습니다.

프레임워크별 방식

섹션 제목: “프레임워크별 방식”

지금 쓰는 프레임워크가 어느 쪽에 속하는지는 이렇게 나뉩니다.

프레임워크 방식
React, Vue 를 Vite 로 빌드 CSR. 빌드 결과가 dist 정적 파일입니다
Next.js (React), Nuxt (Vue) SSR 이 기본이고, 페이지마다 SSG·CSR 로 바꿀 수 있습니다
Astro SSG 가 기본이고, 필요한 페이지만 SSR 로 바꿀 수 있습니다. 이 블로그가 Astro 입니다
Spring + Thymeleaf, JSP SSR. Java 서버가 HTML 을 만들어 보냅니다

같은 React 라도 Vite 로 만들면 CSR, Next.js 위에서 쓰면 SSR 입니다. 방식을 정하는 것은 UI 라이브러리가 아니라 그 위의 프레임워크입니다.

Nginx 1편에서 본, 자바 앱 하나가 화면과 API 를 함께 내보내던 구조가 Thymeleaf·JSP 같은 SSR 입니다. 그 화면을 React 로 떼어 내면서 CSR 로 바뀌었고, 그래서 화면 파일을 내보내는 Nginx 가 따로 필요해졌습니다.

선택 기준

섹션 제목: “선택 기준”
화면 맞는 방식 이유
로그인 뒤에 쓰는 관리자 화면 CSR 검색 엔진에 나올 일이 없고, 서버는 Nginx 하나로 충분합니다
블로그, 문서 사이트 SSG 내용이 자주 바뀌지 않고, 검색 엔진에 나와야 합니다
쇼핑몰 상품 페이지, 뉴스 SSR 내용이 자주 바뀌면서도 검색 엔진과 링크 미리보기에 나와야 합니다

회사 관리자 화면이 CSR 인 것도 이 기준에 맞습니다. 로그인해야 쓰는 화면이라 검색 엔진에 노출될 필요가 없고, 첫 화면이 조금 늦어도 한 번 들어온 뒤로는 화면 이동이 빠릅니다.

Next.js 같은 프레임워크는 한 앱 안에서 화면마다 SSR, SSG, CSR 을 섞어 쓸 수 있습니다. 어느 하나만 고르는 문제가 아니라, 화면마다 어디서 HTML 을 만들지 정하는 문제입니다.

함께 읽을 글

액세스 토큰과 리프레시 토큰토큰을 둘로 나누는 이유, 액세스 토큰과 리프레시 토큰의 유효 기간, 토큰을 보내는 방법과 저장 위치를 XSS·CSRF 기준으로 비교, 401 을 받았을 때 토큰을 갱신하는 흐름, 리프레시 토큰 회전, 로그아웃을 Spring 과 axios 예시로 정리했습니다.
세션과 토큰인증과 인가의 차이, HTTP 가 상태를 저장하지 않는다는 뜻, 세션 방식과 토큰 방식의 로그인 흐름, JWT 의 헤더·페이로드·서명 구조, Spring 으로 세션과 JWT 를 다루는 코드, 두 방식의 비교를 정리했습니다.
쿠키, localStorage, sessionStorage브라우저에 값을 저장하는 쿠키, localStorage, sessionStorage 의 사용법, 남아 있는 기간과 공유 범위, 쿠키가 요청마다 서버로 보내지는 과정, HttpOnly·Secure·SameSite 속성, 다른 주소의 API 로 쿠키를 보내는 설정을 정리했습니다.
