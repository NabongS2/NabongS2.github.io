쿠키, localStorage, sessionStorage

2026년 10월 14일 · 읽는 데 7분
nabong

시리즈로그인과 인증

  1. 쿠키, localStorage, sessionStorage
  2. 세션과 토큰
  3. 액세스 토큰과 리프레시 토큰

페이지를 새로고침하면 자바스크립트 변수에 넣어 둔 값은 모두 사라집니다. 다크 모드 설정, 작성 중인 글, 로그인 상태처럼 새로고침한 뒤에도 남아 있어야 하는 값은 브라우저 저장소에 둡니다.

이 글은 브라우저 저장소 중 쿠키, localStorage, sessionStorage 가 어떻게 다르고, 각각 어떻게 사용하는지 보고자 합니다. 로그인 정보를 이 중 어디에 두는지는 다음 글에서 다룹니다.

브라우저 저장소

섹션 제목: “브라우저 저장소”

브라우저 저장소는 브라우저가 사이트별로 값을 저장해 두는 공간입니다. 새로고침하거나 페이지를 옮겨도 값이 남습니다.

설명
쿠키 서버가 저장하게 하고, 브라우저가 요청마다 서버로 보내는 작은 값
localStorage 자바스크립트로 읽고 쓰는 저장소. 지우기 전까지 남음
sessionStorage localStorage 와 쓰는 법이 같고, 탭을 닫으면 지워짐
IndexedDB 파일이나 많은 양의 데이터를 저장하는 데이터베이스

이 글은 그중 쿠키, localStorage, sessionStorage 를 다룹니다. localStorage 와 sessionStorage 는 함께 웹 스토리지(Web Storage)라고 부릅니다.

웹 스토리지

섹션 제목: “웹 스토리지”

사용법

섹션 제목: “사용법”

localStorage 와 sessionStorage 는 쓰는 함수가 같습니다. 키와 값을 짝으로 저장합니다.

값은 문자열로만 저장됩니다. 객체는 JSON.stringify 로 문자열로 바꿔 저장하고, 읽을 때 JSON.parse 로 되돌립니다.

저장할 수 있는 크기는 약 5MB 이고, 브라우저마다 조금씩 다릅니다.

남아 있는 기간과 공유 범위

섹션 제목: “남아 있는 기간과 공유 범위”

웹 스토리지는 origin(출처) 별로 나뉩니다. origin 은 프로토콜, 도메인, 포트를 합친 것입니다. https://app.example.com 과 http://app.example.com 은 프로토콜이 달라서 다른 origin 이고, 저장소도 따로입니다.

같은 origin 안에서 두 저장소가 다른 점은 값이 남아 있는 기간과, 탭끼리 값을 나눠 쓰는지입니다.

localStorage sessionStorage
새로고침 남음 남음
탭을 닫을 때 남음 지워짐
브라우저를 닫을 때 남음 지워짐
같은 origin 의 다른 탭 같은 값을 읽고 씀 탭마다 따로 있음

다크 모드처럼 모든 탭에 같게 적용되고 다음에 방문했을 때도 남아야 하는 값은 localStorage 에 둡니다. 여러 단계로 나뉜 입력 화면의 현재 단계처럼 탭마다 달라야 하고 탭을 닫으면 필요 없는 값은 sessionStorage 에 둡니다.

쿠키

섹션 제목: “쿠키”

쿠키(cookie)는 서버가 브라우저에 저장해 두게 하는 작은 값입니다. 브라우저는 저장한 쿠키를 그 서버로 보내는 요청마다 함께 보냅니다. 웹 스토리지는 자바스크립트가 직접 읽고 쓰는 저장소이고, 쿠키는 서버와 주고받기 위한 저장소라는 점이 다릅니다.

쿠키가 오가는 과정

섹션 제목: “쿠키가 오가는 과정”

서버는 응답의 Set-Cookie 헤더로 쿠키를 저장하게 합니다.

브라우저는 이 쿠키를 저장해 두고, 이후 같은 서버로 보내는 요청에 Cookie 헤더로 넣습니다.

Cookie 헤더는 브라우저가 자동으로 넣습니다. fetch 나 axios 코드에 따로 쓰지 않아도 됩니다. 페이지 이동, 이미지, fetch 요청 모두 같습니다.

쿠키 하나의 크기는 약 4KB 까지입니다. 요청마다 함께 보내지므로 쿠키가 크고 많을수록 모든 요청이 커집니다.

쿠키 속성

섹션 제목: “쿠키 속성”

Set-Cookie 의 이름=값 뒤에 ; 로 속성을 이어 씁니다.

속성 하는 일 예
Max-Age 몇 초 뒤에 지울지 Max-Age=2592000 (30일)
Expires 언제 지울지 날짜로 지정 Expires=Fri, 13 Nov 2026 09:00:00 GMT
Path 어떤 경로의 요청에 보낼지 Path=/ (모든 경로)
Domain 어떤 도메인의 요청에 보낼지 Domain=example.com (하위 도메인 포함)
  • Max-Age 와 Expires 를 모두 빼면 브라우저를 닫을 때 지워집니다. 이런 쿠키를 세션 쿠키라고 합니다. 여기서 세션은 “브라우저를 연 동안”이라는 뜻이고, 다음 글에서 다룰 로그인 세션과는 다른 말입니다.
  • Domain 을 빼면 쿠키를 만든 도메인으로만 보냅니다. Domain=example.com 으로 지정하면 app.example.com, api.example.com 같은 하위 도메인의 요청에도 보냅니다.

자바스크립트에서 쿠키 다루기

섹션 제목: “자바스크립트에서 쿠키 다루기”

쿠키는 자바스크립트의 document.cookie 로도 읽고 쓸 수 있습니다.

읽으면 이 페이지에서 쓸 수 있는 쿠키가 이름=값; 이름=값 형태의 문자열 하나로 나옵니다. 값 하나를 꺼내려면 이 문자열을 직접 나눠야 해서, 화면에서만 쓰는 값은 웹 스토리지가 다루기 쉽습니다.

쿠키 보안 속성

섹션 제목: “쿠키 보안 속성”

쿠키는 로그인 정보를 담는 데 자주 쓰입니다. 그래서 쿠키를 훔치거나 남이 쓰지 못하게 하는 속성이 따로 있습니다.

HttpOnly

섹션 제목: “HttpOnly”

XSS(Cross-Site Scripting)는 공격자가 게시글 내용 같은 곳에 스크립트를 넣어, 그 페이지를 연 다른 사용자의 브라우저에서 실행되게 하는 공격입니다. 이 스크립트는 그 사이트의 코드와 같은 권한으로 실행되어서, localStorage 와 document.cookie 를 읽어 공격자의 서버로 보낼 수 있습니다.

HttpOnly 를 붙인 쿠키는 자바스크립트로 읽을 수 없습니다. document.cookie 에 나오지 않고, 요청에 함께 보내지는 것만 됩니다.

XSS 스크립트가 실행되어도 이 쿠키의 값은 읽어 갈 수 없습니다. 반대로 사이트의 코드도 이 값을 읽을 수 없으므로, 자바스크립트가 읽어야 하는 값에는 붙이지 않습니다.

Secure

섹션 제목: “Secure”

Secure 를 붙인 쿠키는 HTTPS 요청에만 보냅니다. HTTP 요청은 내용이 암호화되지 않아서, 중간에서 요청을 볼 수 있는 사람에게 쿠키 값이 그대로 보이기 때문입니다.

개발 중의 http://localhost 는 브라우저가 안전한 주소로 보기 때문에 Secure 쿠키도 저장하고 보냅니다.

SameSite

섹션 제목: “SameSite”

CSRF(Cross-Site Request Forgery)는 사용자가 로그인한 상태에서 다른 사이트를 열었을 때, 그 사이트가 사용자 모르게 원래 사이트로 요청을 보내게 하는 공격입니다. 브라우저는 요청에 쿠키를 자동으로 넣기 때문에, 서버는 이 요청을 로그인한 사용자가 보낸 것으로 처리합니다.

SameSite 는 다른 사이트에서 시작된 요청에 쿠키를 보낼지 정합니다. 여기서 사이트는 origin 보다 넓은 단위입니다. 프로토콜과 등록 도메인(example.com 처럼 도메인 등록 기관에 등록한 이름)이 같으면 같은 사이트입니다.

두 주소 origin 사이트
https://app.example.com, https://api.example.com 다름 같음
https://example.com, https://example.com:8080 다름 같음
https://app.example.com, https://app.other.com 다름 다름
값 다른 사이트에서 시작된 요청에
Strict 보내지 않음
Lax 링크를 눌러 페이지로 이동하는 GET 요청에만 보냄
None 모두 보냄. Secure 를 함께 붙여야 함

Lax 이면 다른 사이트의 링크로 들어왔을 때는 로그인 상태가 유지되고, 다른 사이트의 코드가 보낸 fetch 나 폼 전송(POST)에는 쿠키가 붙지 않습니다. Strict 는 다른 사이트의 링크로 들어온 첫 페이지에도 쿠키를 보내지 않아서, 로그인한 상태인데도 로그인 화면이 보일 수 있습니다.

Chrome 등 크로미움 기반 브라우저는 SameSite 를 적지 않은 쿠키를 Lax 로 처리합니다. 이 기본값은 브라우저마다 달라서, 쿠키를 만들 때 직접 적어 두면 브라우저와 관계없이 같게 동작합니다.

다른 주소의 API 로 쿠키 보내기

섹션 제목: “다른 주소의 API 로 쿠키 보내기”

화면은 https://app.example.com 에서, API 는 https://api.example.com 에서 제공하면 둘은 다른 origin 입니다. 이때 fetch 와 axios 는 기본으로 요청에 쿠키를 넣지 않고, 응답의 Set-Cookie 도 저장하지 않습니다.

다른 origin 으로 보내는 요청에 쿠키를 함께 보내려면 옵션을 지정합니다.

credentials 는 쿠키 같은 인증 정보를 함께 보낼지 정하는 옵션입니다. fetch 의 기본값은 'same-origin' 으로 같은 origin 에만 보내고, 'include' 로 바꾸면 다른 origin 에도 보냅니다. axios 의 withCredentials: true 가 같은 일을 합니다.

서버도 응답 헤더로 허락해야 합니다. 허락하지 않으면 브라우저가 응답을 막고 CORS 오류를 냅니다.

  • Access-Control-Allow-Origin 에는 * 대신 화면의 origin 을 정확히 적습니다. 쿠키를 함께 보내는 요청에는 * 를 쓸 수 없습니다.
  • Access-Control-Allow-Credentials: true 는 쿠키를 함께 보낸 요청의 응답을 화면 코드가 읽어도 된다는 뜻입니다.

위 예의 두 주소는 origin 은 다르지만 같은 사이트라서, SameSite=Lax 쿠키도 보내집니다. 화면과 API 가 다른 사이트(app.example.com 과 api.other.com)이면 쿠키에 SameSite=None; Secure 를 붙여야 하고, Safari 와 Firefox 처럼 다른 사이트의 쿠키를 기본으로 막는 브라우저에서는 그래도 보내지지 않을 수 있습니다.

개발 중에는 Vite 같은 개발 서버의 프록시로 /api 요청을 API 서버에 넘겨, 화면과 API 를 같은 origin 처럼 쓰기도 합니다. 이때는 위 설정 없이도 쿠키가 오갑니다.
