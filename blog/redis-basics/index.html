Redis 가 뭔가

섹션 제목: “Redis 가 뭔가”

키에 값을 넣고, 키로 꺼내는 저장소입니다. 그 데이터를 디스크가 아니라 메모리에 둡니다.

이름은 REmote DIctionary Server 입니다. 프로그램 안에서 쓰는 Map 을 프로세스 밖으로 꺼내 여러 서버가 같이 쓰게 만든 것으로 보면 됩니다. 서버 세 대가 같은 Redis 를 바라보면 세 대가 같은 세션을 공유합니다.

성질은 “메모리에 있다” 하나에서 거의 다 따라옵니다.

메모리에 있으니 따라오는 것
디스크를 왕복하지 않는다 응답이 1밀리초 아래로 떨어집니다
메모리 크기가 한계다 담을 수 있는 양이 장비 메모리에 묶입니다
프로세스가 죽으면 사라진다 남겨야 하면 디스크에 따로 써 두는 설정이 필요합니다

관계형 DB와 다른 점

섹션 제목: “관계형 DB와 다른 점”

쓰던 감각이 그대로 오지 않는 지점만 추립니다.

관계형 DB Redis
저장 방식 디스크 기반. 메모리는 버퍼 풀로 씀 인메모리. 디스크는 영속화용
데이터 모델 테이블, 열, 타입, 제약 키-값. 스키마 없음
조회 방식 SQL 로 조건을 걸어 탐색 키로 직접 접근
조인 지원 없음
트랜잭션 커밋·롤백, 격리 수준 원자적 실행은 되지만 롤백 없음
용량 상한 디스크 크기 메모리 크기

버퍼 풀은 관계형 DB가 디스크에서 읽어 온 페이지를 메모리에 올려 두는 영역입니다. 원본은 디스크에 있고, 메모리는 자주 쓰는 것을 임시로 두는 자리입니다.

영속화는 메모리에 있는 것을 디스크에 써 두는 일입니다. 메모리는 프로세스가 죽으면 사라지니, 다시 켰을 때 되살릴 수 있게 파일로 복사해 둡니다. 이 기능을 영속성이라고도 합니다.

Redis 는 관계형 DB와 정반대입니다. 원본이 메모리에 있고 디스크에 있는 것이 사본입니다.

키를 모르면 못 찾습니다

섹션 제목: “키를 모르면 못 찾습니다”

가장 큰 차이입니다. 관계형 DB에서는 넣어 두고 나중에 질문을 만들 수 있습니다.

Redis 에는 이런 것이 없습니다. 나이로 찾고 싶으면 그 조건에 해당하는 키 목록을 미리 만들어 두어야 합니다.

그래서 Redis 는 무엇을 어떻게 꺼낼지 먼저 정하고 그 모양대로 넣는 저장소입니다. 관계형 DB는 순서가 반대라서, 넣어 둔 데이터에 나중에 새 조건을 걸 수 있습니다.

전체를 훑는 KEYS * 가 있긴 합니다. 운영에서는 쓰지 않습니다. 이유는 바로 아래에 있습니다.

명령을 한 줄로 세워 하나씩 처리합니다

섹션 제목: “명령을 한 줄로 세워 하나씩 처리합니다”

Redis 는 명령 실행을 한 스레드에서 합니다. 들어온 순서대로 하나를 끝내고 다음을 시작합니다. (네트워크 입출력은 여러 스레드로 나눠 처리하지만, 명령 자체는 한 번에 하나입니다.)

그래서 이렇게 갈립니다.

  • 좋은 쪽 — 락 경쟁이나 컨텍스트 스위치가 없어서 명령 하나하나가 매우 빠릅니다. 동시에 두 명령이 같은 키를 고치는 일이 없으니 카운터 증가나 락 구현이 단순합니다
  • 주의할 쪽 — 오래 걸리는 명령 하나가 그동안 전체를 막습니다. 키가 수백만 개인데 KEYS * 를 실행하면 그 시간 내내 다른 요청이 모두 대기합니다

훑어야 할 때는 SCAN 을 씁니다. 조금씩 나눠 가져오기 때문에 전체를 막지 않습니다.

관계형 DB는 커넥션마다 병렬로 처리하므로 무거운 쿼리 하나가 전체를 세우지는 않습니다. 대신 락과 격리 수준을 신경 써야 합니다.

사용 예시

섹션 제목: “사용 예시”
쓰임 무엇을 넣나 자료구조
세션 로그인 상태 String, Hash
진행 중인 상태 통화 중인 콜, 처리 중인 주문 Hash
캐시 관계형 DB 조회 결과 String
카운터 조회수, 호출 건수 String + INCR
순위표 점수 상위 N명 Sorted Set
분산 락 한 번만 실행되게 String + SET NX

같은 Redis 인데 고른 이유는 쓰임마다 다릅니다. 아래 여섯 가지 중 하나만 해당해도 쓸 이유가 되고, 대개는 여러 개가 겹칩니다.

이런 게 필요하면 예를 들어
디스크를 왕복하면 느리다 캐시, 진행 중인 상태
서버 여러 대가 같은 것을 봐야 한다 세션, 분산 락
재배포하거나 재시작해도 남아야 한다 세션, 진행 중인 상태
시간이 지나면 알아서 사라져야 한다 세션, 캐시
여러 곳에서 동시에 고쳐도 어긋나면 안 된다 카운터, 분산 락
정렬된 순서를 계속 유지해야 한다 순위표

마지막 줄이 무슨 뜻이냐면, 관계형 DB로 순위를 뽑으면 조회할 때마다 정렬해야 합니다. Sorted Set 은 넣을 때 자리를 잡아 둬서 상위 10명이나 특정 사용자의 등수가 바로 나옵니다.

가운데 셋은 속도와 무관합니다. 앱 프로세스 안에 Map 을 두면 첫 줄은 만족하지만 나머지는 안 됩니다. 관계형 DB에 두면 반대로 첫 줄만 안 됩니다.

반대로 이런 것은 Redis 로 가져올 이유가 없습니다.

  • 조건을 걸어 찾아야 하는 것 — 키를 모르면 못 찾습니다
  • 오래 보관해야 하는 것 — 메모리가 디스크보다 비쌉니다
  • 트랜잭션이 필요한 것 — 롤백이 없습니다

원본이 어디 있느냐로 갈립니다

섹션 제목: “원본이 어디 있느냐로 갈립니다”
예 Redis 가 죽으면
원본이 관계형 DB에 있다 캐시, 순위표 다시 읽어 채웁니다
Redis 가 원본이다 세션, 진행 중인 상태 그때 진행 중이던 것을 잃습니다

통화 중인 콜을 예로 들면, 통화가 이어지는 동안 그 상태는 Redis 에만 있습니다. 관계형 DB에는 통화가 끝난 뒤에 이력으로 들어갑니다.

Redis 가 원본인 것을 담는다면 영속성과 메모리 정책을 같이 정해야 합니다. 캐시로만 쓸 때는 안 해도 되는 일입니다.

JSON 문자열로 넣을까, 자료구조를 쓸까

섹션 제목: “JSON 문자열로 넣을까, 자료구조를 쓸까”

객체를 Redis 에 넣는 방법은 두 가지입니다.

JSON 문자열 하나로 넣거나

Hash 로 넣습니다.

전체를 읽을 때는 차이가 거의 없습니다. 갈리는 것은 일부만 바꿀 때입니다.

콜 상태를 TALKING 에서 ENDED 로 바꾼다고 하겠습니다. JSON 쪽은 세 단계입니다.

Hash 쪽은 한 단계입니다.

여기서 두 가지가 달라집니다.

주고받는 양. JSON 쪽은 필드 하나를 바꾸려고 객체 전체를 두 번 옮깁니다. 필드가 서른 개면 서른 개를 받아서 서른 개를 보냅니다.

동시 변경. 이쪽이 더 중요합니다.

JSON 쪽에서 서버B 는 자기가 읽은 옛 값을 기준으로 전체를 덮어썼습니다. state 를 건드리지도 않았는데 A 가 바꾼 ENDED 가 날아갑니다.

HSET 은 지정한 필드만 바꿉니다. 읽어 오는 단계가 없으니 덮어쓸 옛 값도 없습니다.

그래서 이렇게 고릅니다.

넣는 방법
항상 전체를 읽고 전체를 쓴다 JSON 문자열이 단순합니다
필드를 따로 고친다 Hash
여러 서버가 같은 객체를 고친다 Hash

목록도 같습니다. JSON 배열을 String 에 넣으면 하나를 더할 때마다 전체를 왕복해야 하고, List 를 쓰면 RPUSH 한 번입니다.

redis-cli 접속

섹션 제목: “redis-cli 접속”

아래 명령은 redis-cli 프롬프트에서 입력합니다. 컨테이너로 띄웠다면 이렇게 접속합니다.

접속하면 프롬프트가 127.0.0.1:6379> 로 바뀝니다. exit 로 나옵니다. 지금 상태를 확인하는 명령과 GUI 로 연결하는 방법은 Redis 컨테이너 접속과 상태 확인에 있습니다.

다섯 가지

섹션 제목: “다섯 가지”
자료구조 무엇인가 쓰는 자리
String 키 하나에 값 하나 세션, 캐시, 카운터
Hash 필드와 값의 묶음. 객체 하나 객체를 필드별로 읽고 고칠 때
List 순서가 있는 목록. 양쪽 끝에서 넣고 뺀다 최근 목록, 간단한 큐
Set 중복 없는 모음. 순서 없음 중복 제거, 교집합
Sorted Set 점수로 정렬된 모음 순위표, 시간순 목록

String

섹션 제목: “String”

INCR 은 값을 읽어 더해서 다시 쓰는 것이 아니라 Redis 안에서 한 번에 처리됩니다. 그래서 여러 서버가 같은 카운터를 올려도 값이 어긋나지 않습니다.

Hash

섹션 제목: “Hash”

HashOperations 처럼 Java 쪽 대응은 3편에 있습니다.

List

섹션 제목: “List”

LPUSH 로 넣고 LTRIM 0 9 로 자르면 최근 10개만 유지되는 목록이 됩니다. 넣을 때마다 자르는 것이 관례입니다.

한쪽에서 RPUSH, 다른 쪽에서 LPOP 하면 큐가 됩니다. 다만 재시도나 실패 처리가 필요하면 RabbitMQ 같은 전용 도구를 씁니다. List 로 만든 큐는 꺼낸 메시지를 처리하다 죽으면 그 메시지가 사라집니다.

Set

섹션 제목: “Set”

SISMEMBER 는 원소가 10개든 100만 개든 걸리는 시간이 거의 같습니다. Set 은 안에서 값으로 바로 찾아가는 구조라 처음부터 하나씩 훑지 않습니다. SMEMBERS 로 전부 받아와 앱에서 찾으면, 원소가 많을수록 받아오는 데만 오래 걸립니다.

Sorted Set

섹션 제목: “Sorted Set”

값마다 점수를 같이 넣고, 점수 순으로 정렬해 둡니다.

점수 자리에 시각을 숫자로 넣으면 시간순 목록이 됩니다. ZRANGEBYSCORE 로 기간을 잘라 가져올 수 있습니다.

만료 걸기

섹션 제목: “만료 걸기”

키에 수명을 걸어두면 시간이 지났을 때 Redis 가 알아서 지웁니다. 이 수명을 TTL, Time To Live 라고 합니다.

TTL 의 답은 셋 중 하나입니다.
양수 남은 초
-1 만료가 없음. 영원히 남습니다
-2 키가 없음. 이미 사라졌거나 처음부터 없었습니다

관계형 DB에는 이런 기능이 없습니다. 만료 시각 컬럼을 두고 배치로 지우거나, 조회할 때마다 시각을 비교해야 합니다. 앞의 「사용 예시」에서 “시간이 지나면 알아서 사라져야 한다” 가 Redis 를 고르는 이유가 되는 것이 이 때문입니다.

값을 넣을 때 같이 거는 편이 안전합니다. SET 하고 EXPIRE 를 따로 실행하면 그 사이에 프로세스가 죽었을 때 만료 없는 키가 남습니다.

TTL 이 -1 로 나오는 키가 쌓이는 것이 메모리가 계속 차는 흔한 원인입니다.

Spring 연동

섹션 제목: “Spring 연동”

Spring 에서 연결하는 방법은 따로 정리했습니다. 여기 나온 명령이 StringRedisTemplate 에서 각각 무엇에 대응하는지도 거기 있습니다.

명령어 한눈에

섹션 제목: “명령어 한눈에”
하려는 것 명령
값 넣기 SET k v
만료까지 같이 SET k v EX 1800
값 꺼내기 GET k
숫자 올리기 INCR k
객체 필드 넣기 HSET k f v
객체 전체 꺼내기 HGETALL k
목록에 넣기 RPUSH k v
목록 잘라 보기 LRANGE k 0 9
목록 길이 제한 LTRIM k 0 9
모음에 넣기 SADD k v
들어 있나 SISMEMBER k v
점수와 함께 넣기 ZADD k 120 v
상위 10개 ZREVRANGE k 0 9
만료 걸기 EXPIRE k 1800
남은 시간 TTL k
