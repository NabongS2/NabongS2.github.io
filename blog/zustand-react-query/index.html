Zustand 와 React Query

2026년 10월 13일 · 읽는 데 10분
nabong

시리즈API 데이터 다루기

  1. 동기와 비동기
  2. fetch 와 axios
  3. Zustand 와 React Query

React 기본 훅 글에서는 컴포넌트끼리 값을 주고받을 때 props 와 useContext 를 썼습니다. 여러 컴포넌트가 같은 값을 함께 써야 할 때는 React 가 기본으로 주는 기능 대신 상태 관리 라이브러리를 사용하여 관리할 수 있습니다. 서버에서 받아 온 데이터도 이를 관리하는 라이브러리를 사용할 수 있습니다.

이 글은 그중 Zustand 와 React Query 를 다룹니다. 두 라이브러리가 어떻게 다르고, 각각 어떻게 사용하는지 보고자 합니다.

클라이언트 상태와 서버 상태

섹션 제목: “클라이언트 상태와 서버 상태”

화면이 기억하는 값은 그 데이터가 어디에 저장되는지에 따라 두 가지로 나뉩니다.

  • 클라이언트 상태: 브라우저에만 저장되는 데이터입니다. 사이드바가 열렸는지, 어느 탭을 골랐는지, 검색창에 무엇을 입력했는지가 여기에 속합니다. 새로고침하면 사라져도 되고, 서버는 이 값을 모릅니다.
  • 서버 상태: 서버의 데이터베이스에 저장된 데이터입니다. 화면은 이 데이터를 받아 와서 보여 줍니다. 글 목록, 사용자 정보, 주문 통계가 여기에 속합니다.

서버 상태가 다른 점

섹션 제목: “서버 상태가 다른 점”

클라이언트 상태는 내가 바꾸지 않으면 바뀌지 않습니다. 서버 상태는 그렇지 않습니다. 화면이 받아 온 데이터를 보여 주는 동안 다른 사용자가 글을 쓰면 서버의 데이터가 바뀌고, 화면이 가진 데이터는 오래된 값이 됩니다.

그래서 서버 상태에는 클라이언트 상태에 없는 일이 따라옵니다.

  • 받아 오는 중인지, 실패했는지 표시하기
  • 같은 데이터를 여러 화면이 쓸 때 한 번만 요청하기
  • 받아 온 데이터가 오래됐다고 보고 다시 요청하기
  • 데이터를 바꾼 뒤 관련 목록을 새로 받기

두 종류의 상태는 다루는 라이브러리도 나뉩니다.

라이브러리 이 글에서 다루는 것
클라이언트 상태 Redux, Zustand, Jotai 등 Zustand
서버 상태 React Query, SWR, RTK Query 등 React Query

Zustand

섹션 제목: “Zustand”

Zustand 는 클라이언트 상태를 다루는 상태 관리 라이브러리입니다. 값을 컴포넌트 밖의 스토어에 두고, 여러 컴포넌트가 그 스토어에서 값을 꺼내 함께 씁니다.

같은 일을 하는 라이브러리는 값을 모아 두는 방식에 따라 나뉩니다.

  • 스토어 방식: 앱의 상태를 스토어라는 객체에 모아 둡니다. Redux 와 Zustand 가 이 방식입니다. Redux 는 값을 바꿀 때 액션(무엇을 할지 적은 객체)과 리듀서(액션을 받아 새 상태를 만드는 함수)를 거치도록 규칙을 정해 두었고, Zustand 는 스토어 안의 함수로 바로 바꿉니다.
  • 아톰 방식: 아톰(atom)은 “원자”, 즉 더 나눌 수 없는 가장 작은 단위라는 뜻입니다. 여러 컴포넌트가 함께 쓰는 값을 하나씩 따로 아톰으로 만들고, 컴포넌트는 필요한 아톰만 골라 씁니다. Jotai 가 이 방식입니다.

두 방식은 함께 쓰는 값들이 서로 어떤 관계인지에 따라 편한 쪽이 다릅니다.

아톰 방식 스토어 방식
값의 관계 서로 따로 바뀜 하나를 바꾸면 다른 값도 같이 바뀜
예 테마, 글자 크기, 사이드바 열림 장바구니의 상품 목록·개수·합계

테마를 바꿔도 글자 크기는 그대로이니, 값마다 따로 아톰으로 두면 됩니다. 장바구니는 상품을 하나 담으면 목록, 개수, 합계가 함께 바뀌어야 합니다. 스토어에 세 값과 addItem 같은 함수를 함께 두면, 상품을 담을 때 세 값을 같이 바꾸는 일을 그 함수 한곳에서 처리할 수 있습니다.

스토어 만들기

섹션 제목: “스토어 만들기”

스토어는 값과 그 값을 바꾸는 함수를 한곳에 모은 객체입니다. create 로 만듭니다.

  • set 은 스토어의 값을 바꾸는 함수입니다. 넘긴 객체가 기존 상태에 합쳐집니다. useState 의 setState 와 달리 나머지 값을 직접 펼쳐 넣지 않아도 됩니다.
  • 이전 값이 필요하면 set((state) => ...) 처럼 함수를 넘깁니다.

컴포넌트에서 쓰기

섹션 제목: “컴포넌트에서 쓰기”

create 가 돌려주는 useSidebarStore 는 useState 처럼 use 로 시작하는 훅입니다. 컴포넌트 안에서 이 함수를 호출하면서 필요한 값을 고르는 함수를 넘기면, 그 값을 돌려받습니다.

두 컴포넌트는 부모와 자식 관계가 아니어도 됩니다. props 로 넘기지 않고 각자 스토어에서 꺼내 쓰기 때문에, React 기본 훅 글에서 본 props drilling 이 생기지 않습니다.

선택자

섹션 제목: “선택자”

(state) => state.isOpen 처럼 스토어에서 필요한 값을 골라내는 함수를 선택자(selector)라고 합니다. 컴포넌트는 선택자가 돌려준 값이 바뀔 때만 다시 렌더링됩니다.

위 예시에서 toggle 을 눌러 isOpen 이 바뀌면 Sidebar 만 다시 렌더링됩니다. SidebarButton 이 고른 toggle 함수는 그대로라서 다시 렌더링되지 않습니다.

선택자 없이 스토어 전체를 꺼내면 이 장점이 사라집니다.

값을 하나씩 고르면 여기까지로 충분합니다. 여러 값을 객체나 배열 하나로 묶어 고를 때만 주의할 점이 있습니다.

이 선택자는 호출될 때마다 { ... } 로 새 객체를 만듭니다. Zustand 는 선택자가 돌려준 값을 이전 값과 === 로 비교하는데, 새 객체는 안의 값이 같아도 매번 다른 객체라서 값이 바뀌었다고 판단합니다. Zustand v5 에서는 이 판단이 반복되어 Maximum update depth exceeded 에러가 날 수 있습니다.

이때 선택자를 useShallow 로 감쌉니다. useShallow 는 객체를 통째로 비교하지 않고 안의 값을 하나씩 비교해서, 값이 모두 같으면 이전 객체를 그대로 돌려줍니다.

컴포넌트 밖에서 쓰기

섹션 제목: “컴포넌트 밖에서 쓰기”

스토어의 값을 컴포넌트가 아닌 곳에서 바꿔야 할 때가 있습니다. 예를 들어 API 요청 함수에서 에러가 나면 에러 내용을 스토어에 기록하고, 화면 한 곳에서 그 값을 보고 에러 창을 띄우는 경우입니다.

에러 스토어는 아래처럼 만들었다고 하겠습니다.

이때 컴포넌트에서 하던 것처럼 useErrorStore((state) => state.setError) 를 호출해서 setError 를 받을 수는 없습니다. useErrorStore 는 훅이고, React 의 훅은 컴포넌트 함수 안에서만 호출할 수 있는데 API 요청 함수는 컴포넌트가 아니기 때문입니다.

그래서 Zustand 는 create 로 만든 훅에 getState 라는 함수를 함께 달아 둡니다. getState() 는 스토어의 현재 상태 객체를 돌려주는 함수이고, 훅이 아니라서 어디서든 호출할 수 있습니다. 돌려받은 객체에는 값과 함수가 모두 들어 있습니다.

아래 fetchPosts 는 서버의 /api/posts 주소에서 글(post) 목록을 받아 오는 함수입니다. 이 글의 다른 예시도 같은 주소를 씁니다.

useContext 와 비교

섹션 제목: “useContext 와 비교”

여러 컴포넌트가 값을 나눠 쓴다는 점은 useContext 와 같습니다. 차이는 두 가지입니다.

useContext Zustand
준비 Provider 로 감싸야 함 create 만 하면 됨
다시 렌더링되는 범위 value 가 바뀌면 그 Context 를 쓰는 컴포넌트 전부 선택자로 고른 값이 바뀐 컴포넌트만

두 번째 차이를 예로 보겠습니다. 로그인 사용자(user)와 장바구니에 담은 개수(cartCount)를 함께 나눠 쓰는 앱입니다. 화면 위쪽의 UserName 은 user 만 쓰고, CartBadge 는 cartCount 만 씁니다.

장바구니에 상품을 하나 담아 cartCount 가 바뀌면 이렇게 됩니다.

useContext Zustand
CartBadge 다시 렌더링 다시 렌더링
UserName 다시 렌더링 (user 는 그대로인데도) 다시 렌더링하지 않음

useContext 는 value 객체가 바뀌었는지만 보기 때문에, 그 Context 를 쓰는 컴포넌트는 자기가 쓰는 값이 그대로여도 모두 다시 렌더링됩니다. Zustand 는 선택자가 돌려준 값을 비교해서, 그 값이 바뀐 컴포넌트만 다시 렌더링합니다.

그래서 로그인 사용자나 화면 테마처럼 거의 바뀌지 않는 값은 useContext 로 충분합니다. 장바구니 개수처럼 자주 바뀌는 값을 여러 컴포넌트가 함께 쓰면, useContext 에서는 그 값을 쓰지 않는 컴포넌트까지 매번 다시 렌더링되고, Zustand 에서는 그 값을 쓰는 컴포넌트만 다시 렌더링됩니다.

React Query

섹션 제목: “React Query”

React Query 는 서버 상태를 받아 오고, 캐시에 보관하고, 언제 다시 받을지 관리하는 라이브러리입니다. 지금 이름은 TanStack Query 이고, 이 글은 v5 기준입니다.

axios 와의 차이

섹션 제목: “axios 와의 차이”

axios 와 브라우저의 fetch 는 HTTP 클라이언트입니다. 서버에 요청을 보내고 응답을 받는 일만 합니다(fetch 와 axios 글). React Query 는 요청을 직접 보내지 않습니다. 요청은 넘겨받은 함수가 보내고, React Query 는 그 결과를 언제 요청하고 어디에 보관할지를 관리합니다.

axios, fetch React Query
하는 일 요청을 보내고 응답을 받음 응답을 캐시에 보관하고, 다시 요청할 때를 정함
아는 것 주소, 헤더, 요청 본문 쿼리 키, 캐시, 화면에서 쓰는 곳

그래서 둘은 같이 씁니다. 아래 코드에서 요청을 보내는 부분이 axios 입니다.

useQuery

섹션 제목: “useQuery”
  • queryKey: 이 데이터의 이름입니다. 아래에서 다룹니다.
  • queryFn: 데이터를 받아 오는 함수입니다. Promise 를 돌려주면 됩니다.
  • isPending: 아직 받은 데이터가 없는 상태입니다.
  • isError: 요청이 실패한 상태입니다. 실패하면 기본으로 세 번 더 시도한 뒤 이 상태가 됩니다.

받아 오는 중과 실패 상태를 useState 로 따로 만들지 않아도 됩니다.

React Query 를 쓰려면 앱을 한 번 QueryClientProvider 로 감싸야 합니다. 캐시는 여기서 만든 QueryClient 안에 있습니다.

쿼리 키와 캐시

섹션 제목: “쿼리 키와 캐시”

캐시는 받아 온 데이터를 다음에 다시 쓰려고 보관해 두는 저장소입니다. React Query 는 캐시를 쿼리 키로 구분합니다.

  • 같은 쿼리 키를 쓰는 컴포넌트가 여러 개면 요청은 한 번만 갑니다. 받은 데이터는 모두가 나눠 씁니다.
  • 쿼리 키는 배열이고, 요청 조건도 넣습니다. 조건이 다르면 다른 데이터이기 때문입니다.

queryFn 이 쓰는 값을 쿼리 키에 빠뜨리면, 조건이 바뀌어도 쿼리 키가 같아서 이전 조건의 데이터가 그대로 보입니다. queryFn 안에서 쓰는 값은 모두 쿼리 키에 넣습니다.

staleTime 과 gcTime

섹션 제목: “staleTime 과 gcTime”

캐시의 데이터에는 두 가지 시간이 있습니다.

  • staleTime: 받아 온 데이터를 언제까지 최신으로 볼지 정합니다. 이 시간이 지나면 데이터는 오래된(stale) 상태가 됩니다.
  • gcTime: 데이터를 쓰는 컴포넌트가 하나도 없게 된 뒤, 캐시에서 지우기까지 기다리는 시간입니다.
기본값 늘리면 줄이면
staleTime 0 요청이 줄어듦. 대신 서버가 바뀌어도 그 시간 동안 이전 데이터를 보여 줌 늘 최신에 가까움. 대신 요청이 많아짐
gcTime 5분 화면을 다시 열 때 캐시의 데이터를 바로 보여 줄 수 있음. 대신 메모리를 더 씀 메모리를 덜 씀. 대신 다시 열 때 처음부터 불러옴

기본 staleTime 이 0 이라서 데이터는 받자마자 오래된 상태입니다. 오래된 데이터는 아래 때에 다시 요청합니다.

  • 그 쿼리를 쓰는 컴포넌트가 새로 화면에 나타날 때
  • 브라우저 창에 다시 포커스가 갈 때
  • 네트워크가 다시 연결될 때

다시 요청하는 동안에는 캐시에 있던 데이터를 먼저 보여 줍니다. 그래서 isPending 은 false 이고, 요청이 진행 중인지는 isFetching 으로 확인합니다.

자주 바뀌지 않는 데이터(코드 목록, 설정)라면 staleTime 을 늘려 요청을 줄일 수 있습니다. 얼마로 둘지는 데이터가 얼마나 자주 바뀌는지, 오래된 값을 잠깐 보여 줘도 되는지에 따라 정합니다.

useMutation 과 무효화

섹션 제목: “useMutation 과 무효화”

데이터를 만들거나 바꾸거나 지우는 요청에는 useMutation 을 씁니다. useQuery 와 달리 컴포넌트가 나타날 때 실행되지 않고, mutate 를 호출할 때 실행됩니다.

글을 새로 쓰면 글 목록 캐시는 오래된 데이터가 됩니다. 이때 invalidateQueries 로 그 쿼리를 무효화합니다. invalidate 는 “무효로 하다”라는 뜻입니다. 무효화는 캐시의 데이터를 오래된 상태로 표시하고, 지금 화면에서 쓰고 있으면 바로 다시 요청하게 하는 일입니다.

queryKey: ['posts'] 로 무효화하면 ['posts'] 로 시작하는 쿼리가 모두 대상입니다. ['posts', { page: 1 }] 과 ['posts', { page: 2 }] 가 함께 무효화됩니다.

useEffect 로 직접 불러올 때와 비교

섹션 제목: “useEffect 로 직접 불러올 때와 비교”

React Query 없이 같은 일을 하면 아래처럼 됩니다.

이 코드는 한 컴포넌트의 요청 한 번만 처리합니다. 다른 화면이 같은 목록을 쓰면 요청이 또 가고, 창에 다시 포커스가 가도 새로 받지 않으며, 글을 쓴 뒤 목록을 새로 받으려면 상태를 직접 연결해야 합니다. React Query 는 이 일들을 쿼리 키 하나로 처리합니다.

v3 와 v5 의 이름 차이

섹션 제목: “v3 와 v5 의 이름 차이”

v3 까지는 패키지 이름이 react-query 였고, v4 부터 @tanstack/react-query 입니다. 오래된 프로젝트의 코드를 읽을 때 아래 이름이 다릅니다.

v3 (react-query) v5 (@tanstack/react-query)
useQuery('posts', fetchPosts, options) useQuery({ queryKey: ['posts'], queryFn: fetchPosts })
isLoading (데이터가 아직 없음) isPending
cacheTime gcTime
invalidateQueries('posts') invalidateQueries({ queryKey: ['posts'] })
useQuery 의 onSuccess, onError 없어짐. useMutation 에는 남아 있음

함께 쓰기

섹션 제목: “함께 쓰기”

두 라이브러리를 함께 쓸 때 판단 기준은 하나입니다. 데이터가 브라우저에만 저장되면 Zustand, 서버에 저장되면 React Query 에 둡니다.

필터 값과 요청 조건

섹션 제목: “필터 값과 요청 조건”

기간을 골라 주문 통계를 보는 화면을 예로 들겠습니다. 사용자가 고른 기간은 브라우저에만 있는 값이고, 그 기간의 통계는 서버에 있는 값입니다.

기간 선택 컴포넌트와 통계 컴포넌트는 서로 props 를 주고받지 않습니다. 기간 선택 컴포넌트가 setRange 를 호출하면 흐름이 이렇게 이어집니다.

enabled 는 쿼리를 실행할지 정하는 옵션입니다. false 면 요청하지 않습니다. 기간을 지워서 빈 값이 되면 잘못된 요청이 가지 않게 막습니다.

서버 데이터를 스토어에 복사하지 않기

섹션 제목: “서버 데이터를 스토어에 복사하지 않기”

useQuery 로 받은 데이터를 onSuccess 나 useEffect 에서 Zustand 스토어에 다시 넣는 코드가 있습니다. 여러 컴포넌트에서 쓰려는 의도이지만, 이렇게 하면 같은 데이터가 캐시와 스토어 두 곳에 생깁니다.

  • 무효화로 캐시가 새 데이터를 받아도 스토어에 복사해 둔 데이터는 그대로입니다.
  • 어느 쪽이 최신인지 코드를 따라가야 알 수 있습니다.

여러 컴포넌트에서 쓰려면 같은 쿼리 키로 useQuery 를 호출하면 됩니다. 요청은 한 번만 가고 캐시를 나눠 씁니다. 위의 useOrderStats 처럼 훅으로 묶어 두면 쿼리 키를 여러 곳에 따로 적지 않아도 됩니다.

실시간 데이터

섹션 제목: “실시간 데이터”

서버 상태라고 모두 React Query 에 맞지는 않습니다. React Query 는 내가 요청해서 받는 데이터를 기준으로 만들어졌습니다. 채팅 메시지나 실시간 시세처럼 서버가 WebSocket 으로 계속 보내 주는 데이터는 요청하는 시점이 없습니다.

이런 데이터는 받은 메시지를 Zustand 스토어에 넣어 화면이 구독하게 하거나, queryClient.setQueryData 로 React Query 캐시를 직접 바꾸는 방법을 씁니다. 처음 목록은 요청으로 받고 이후 변경만 WebSocket 으로 받는 화면이면 캐시를 바꾸는 쪽이 한곳에서 관리하기 쉽고, 요청 없이 메시지로만 채워지는 화면이면 스토어에 두는 쪽이 단순합니다.

정리

섹션 제목: “정리”
Zustand React Query
다루는 상태 클라이언트 상태 서버 상태
데이터 저장 위치 브라우저 서버
값을 바꾸는 방법 set 서버에 요청한 뒤 무효화
다시 렌더링 범위 선택자로 고른 값이 바뀐 컴포넌트 그 쿼리 키를 쓰는 컴포넌트
예시 사이드바 열림, 선택한 탭, 고른 기간 글 목록, 사용자 정보, 기간별 통계

요청을 보내는 일은 axios 나 fetch 가 하고, 그 결과를 캐시하고 다시 받을 때를 정하는 일은 React Query 가 합니다. 브라우저에만 있는 값은 Zustand 에 두고, 그 값을 요청 조건으로 쓸 때는 쿼리 키에 넣습니다.
