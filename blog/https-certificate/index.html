HTTPS 와 인증서

nabong

  1. 네트워크 계층
  2. IP 주소와 포트
  3. NAT 와 포트포워딩
  4. VPN
  5. DNS 와 도메인
  6. HTTPS 와 인증서

앞 글에서는 도메인이 DNS 를 거쳐 IP 로 바뀌는 과정을 살펴봤습니다. 그런데 DNS 가 알려 준 IP 로 접속했다고 해서, 그 서버가 정말 그 도메인의 서버인지, 주고받는 내용을 중간에서 누군가 보고 있지 않은지는 알 수 없습니다. 이 글에서는 HTTPS 가 이 문제를 어떻게 해결하는지, 그 중심에 있는 인증서가 무엇이고 어떻게 검증되는지 알아봅니다.

HTTP 와 HTTPS

섹션 제목: “HTTP 와 HTTPS”

HTTP 는 요청과 응답을 암호화하지 않은 글자 그대로 보냅니다. 브라우저에서 서버까지 요청이 전송되는 경로에는 공유기, 통신사 장비 같은 여러 장비가 있고, 같은 Wi-Fi 에 연결된 기기도 있습니다. 이 경로에 있는 누구든 HTTP 요청을 볼 수 있습니다.

위험 내용
도청 로그인 비밀번호, 쿠키, 요청 내용을 중간에서 읽습니다
변조 응답에 다른 스크립트를 삽입하거나 내용을 바꿉니다
사칭 가짜 서버가 진짜 서버인 것처럼 응답합니다

HTTPS 는 HTTP 를 TLS 로 감싸 보내는 방식입니다. 네트워크 계층에서 본 것처럼 TLS(Transport Layer Security)는 데이터를 암호화하고, 접속한 서버가 진짜인지 인증서로 확인하는 규칙입니다. 위 세 가지 위험에 각각 대응합니다.

TLS 가 하는 일 막는 위험
암호화 도청. 중간 장비는 IP 와 포트만 보고, 요청 경로와 내용은 읽지 못합니다
무결성 확인 변조. 중간에 바뀐 데이터는 받는 쪽에서 오류로 처리합니다
서버 인증 사칭. 인증서로 접속한 서버가 그 도메인의 주인인지 확인합니다

HTTPS 의 기본 포트는 443 이고, 주소는 https:// 로 시작합니다. TLS 의 이전 이름이 SSL 이어서, 설정 항목과 도구 이름에는 지금도 ssl 이 많이 남아 있습니다.

공개키와 비밀키

섹션 제목: “공개키와 비밀키”

인증서를 이해하려면 먼저 TLS 가 쓰는 두 종류의 키를 알아야 합니다. 두 키는 한 쌍으로 만들어지고, 한쪽 키로 서명한 결과를 다른 쪽 키로 확인합니다.

키 가진 곳 하는 일
비밀키(private key) 서버만 가집니다 데이터에 서명합니다. 서명은 “이 데이터를 이 비밀키의 주인이 만들었다”는 표시입니다
공개키(public key) 누구에게나 공개합니다 비밀키로 만든 서명이 맞는지 확인합니다

서명은 짝이 되는 공개키로만 확인되고, 공개키로는 비밀키를 알아낼 수 없습니다. 그래서 서버가 비밀키로 서명한 데이터를 보내면, 받는 쪽은 공개키로 확인해 그 데이터가 비밀키를 가진 서버에서 왔다는 것을 알 수 있습니다.

비밀키가 유출되면 다른 사람이 그 서버인 것처럼 행세할 수 있습니다. 서버의 비밀키 파일은 권한을 제한하고, 저장소나 이미지에 넣지 않습니다.

인증서

섹션 제목: “인증서”

공개키만으로는 그 공개키가 누구의 것인지 알 수 없습니다. 가짜 서버도 자기 공개키를 보내면서 app.example.com 의 공개키라고 주장할 수 있기 때문입니다. 그래서 믿을 수 있는 기관이 “이 공개키는 이 도메인의 것이다”라고 확인하고 서명한 파일을 함께 보냅니다. 이 파일이 인증서(certificate)이고, 서명하는 기관을 인증 기관(CA, Certificate Authority)이라고 합니다.

항목 내용 예
주체(Subject) 인증서의 주인 CN=app.example.com
주체 대체 이름(SAN) 이 인증서로 접속할 수 있는 이름 목록 app.example.com, www.example.com
발급자(Issuer) 서명한 인증 기관 CN=R11, O=Let's Encrypt
유효 기간 시작일과 만료일 2026-10-01 ~ 2026-12-30
공개키 서버 비밀키의 짝
서명 발급자가 위 내용 전체에 한 서명

브라우저는 접속한 도메인이 SAN(Subject Alternative Name)에 있는지 확인합니다. 주체의 CN 은 예전에 이름 확인에 쓰였지만, 지금 브라우저는 SAN 만 확인합니다. SAN 에는 *.example.com 같은 와일드카드도 넣을 수 있고, 이 이름은 api.example.com 처럼 한 단계 아래 서브도메인과 일치합니다. example.com 자체나 a.b.example.com 과는 일치하지 않습니다.

인증 기관과 인증서 체인

섹션 제목: “인증 기관과 인증서 체인”

인증 기관은 보통 두 단계로 나뉩니다.

구분 하는 일 보관 위치
루트 인증 기관(Root CA) 중간 인증 기관의 인증서에 서명합니다 루트 인증서가 OS 와 브라우저의 신뢰 저장소에 처음부터 들어 있습니다
중간 인증 기관(Intermediate CA) 서버 인증서에 서명합니다 서버가 자기 인증서와 함께 보냅니다

신뢰 저장소(trust store)는 “이 루트 인증서로 이어지는 인증서는 믿는다”고 정해 둔 목록입니다. Windows, macOS, Linux, Firefox, Java 가 각자 목록을 가집니다.

서버 인증서에서 중간 인증서를 거쳐 루트 인증서까지 서명으로 이어진 줄을 인증서 체인이라고 합니다. 서버는 자기 인증서와 중간 인증서를 함께 보내야 체인이 완성됩니다. Nginx 에서 두 인증서를 이어 붙인 파일(fullchain)을 쓰는 이유가 이것이고, 설정은 Nginx 글에 정리했습니다.

인증서 검증

섹션 제목: “인증서 검증”

브라우저는 서버 인증서를 받으면 다음 항목을 확인합니다. 하나라도 맞지 않으면 접속을 멈추고 경고를 보여 줍니다.

확인 항목 내용
체인 서명을 따라가면 신뢰 저장소의 루트 인증서에 도달하는지
이름 주소창의 도메인이나 IP 가 SAN 에 있는지
유효 기간 지금 시각이 시작일과 만료일 사이인지
비밀키 서버가 인증서의 공개키와 짝인 비밀키를 가졌는지. 아래 핸드셰이크에서 확인합니다

TLS 핸드셰이크

섹션 제목: “TLS 핸드셰이크”

브라우저와 서버는 HTTP 요청을 보내기 전에, 인증서를 확인하고 암호화에 쓸 키를 정하는 과정을 먼저 거칩니다. 이 과정을 TLS 핸드셰이크라고 합니다. TLS 1.3 기준으로 줄이면 다음 순서입니다.

  1. 브라우저가 지원하는 TLS 버전과 암호 방식, 키 교환에 쓸 값, 접속하려는 도메인 이름을 보냅니다. 이 도메인 이름을 SNI(Server Name Indication)라고 합니다.
  2. 서버가 SNI 의 도메인에 맞는 인증서와 체인, 키 교환에 쓸 값을 보냅니다. 그리고 지금까지 주고받은 핸드셰이크 내용에 비밀키로 서명해 보냅니다.
  3. 브라우저가 위 “인증서 검증” 의 항목을 확인하고, 인증서의 공개키로 서명을 확인합니다. 서명이 맞으면 상대가 그 인증서의 비밀키를 가진 서버라는 뜻입니다.
  4. 브라우저와 서버가 1, 2단계에서 주고받은 키 교환 값으로 같은 세션 키를 각자 계산합니다. 세션 키 자체는 네트워크로 보내지 않습니다.
  5. 이후 HTTP 요청과 응답을 세션 키로 암호화해 주고받습니다.

세션 키는 같은 키 하나로 암호화와 복호화를 모두 하는 대칭 암호에 씁니다. 공개키 방식은 계산량이 많아서 서버 확인과 키 교환에만 쓰고, 실제 데이터는 대칭 암호로 처리합니다.

SNI 가 있어서 IP 하나에 여러 도메인을 두어도 서버가 도메인마다 다른 인증서를 고를 수 있습니다. Nginx 는 SNI 의 도메인을 server_name 과 비교해 그 server 의 인증서를 보냅니다.

인증서 종류

섹션 제목: “인증서 종류”

인증서는 누가 서명했는지에 따라 세 가지로 나뉩니다. 차이는 그 서명을 확인할 루트 인증서가 어느 신뢰 저장소에 있는지입니다.

종류 서명한 곳 신뢰하는 곳 쓰는 곳
공인 인증서 공인 인증 기관 (Let’s Encrypt, DigiCert, Sectigo 등) 모든 OS 와 브라우저. 루트 인증서가 처음부터 들어 있습니다 인터넷에 공개하는 서비스
사설 CA 인증서 회사나 팀이 직접 만든 인증 기관 그 사설 CA 의 루트 인증서를 설치한 PC 와 서버만 내부망 서버, 개발 서버
자체 서명 인증서 인증서 자신 그 인증서를 직접 설치한 PC 만. 설치하지 않으면 접속할 때마다 경고를 넘겨야 합니다 서버가 적은 개발 환경, 테스트

세 종류 모두 암호화 방식은 같습니다. 다른 것은 브라우저가 서버를 확인할 수 있는지이고, 확인할 수 없으면 경고가 표시됩니다.

공인 인증서 발급

섹션 제목: “공인 인증서 발급”

공인 인증 기관은 인증서를 발급하기 전에 신청한 사람이 그 도메인을 관리하는지 확인합니다. 무료 인증 기관인 Let’s Encrypt 는 ACME 라는 자동 발급 규칙으로 이 확인과 발급을 처리합니다.

확인 방식 하는 일 조건
HTTP-01 인증 기관이 준 값을 http://도메인/.well-known/acme-challenge/ 경로에 올리면, 인증 기관이 그 주소로 접속해 확인합니다 인터넷에서 그 도메인의 80 번 포트로 접속할 수 있어야 합니다
DNS-01 인증 기관이 준 값을 도메인의 TXT 레코드로 등록하면, 인증 기관이 DNS 로 확인합니다 DNS 레코드를 수정할 수 있어야 합니다. 서버가 인터넷에 열려 있지 않아도 됩니다. 와일드카드 인증서는 이 방식으로만 받습니다

Let’s Encrypt 인증서의 유효 기간은 90일이라 자동 갱신을 함께 설정합니다. ACME 를 쓰는 도구로 Certbot, acme.sh 가 있고, Caddy 같은 웹 서버는 발급과 갱신을 직접 처리합니다. 유효 기간이 더 긴 유료 인증서도 있지만, 공인 인증서의 최대 유효 기간은 점점 짧아지는 추세라 어느 쪽이든 갱신 절차를 정해 두어야 합니다.

사설 CA 인증서 발급

섹션 제목: “사설 CA 인증서 발급”

내부망 서버는 인터넷에서 접속할 수 없거나 공인 도메인이 없어서, 공인 인증서를 받기 어려운 경우가 많습니다. 이때 사설 CA 를 만들어 인증서를 발급하고, 그 루트 인증서를 사용할 PC 에 설치합니다. 다음은 openssl 로 인증서를 만드는 순서입니다.

파일 내용 두는 곳
ca.key 사설 CA 의 비밀키 안전한 곳에 따로 보관합니다
ca.crt 사설 CA 의 루트 인증서 접속할 PC 와 서버의 신뢰 저장소
server.key, server.crt 서버의 비밀키와 인증서 웹 서버 설정 (Nginx 의 ssl_certificate_key, ssl_certificate)
server.csr 인증서 서명 요청. 서명이 끝나면 쓰지 않습니다

CSR(Certificate Signing Request)은 서버의 공개키와 이름을 담아 인증 기관에 서명을 요청하는 파일입니다. 공인 인증서를 받을 때도 같은 형식을 씁니다.

ca.crt 를 신뢰 저장소에 설치하는 방법은 OS 마다 다릅니다.

환경 설치 방법
Windows 관리자 권한으로 certutil -addstore -f Root ca.crt, 또는 인증서 파일을 열어 “신뢰할 수 있는 루트 인증 기관” 에 설치
macOS sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain ca.crt
Ubuntu, Debian ca.crt 를 /usr/local/share/ca-certificates/ 에 복사한 뒤 sudo update-ca-certificates
Firefox 자체 신뢰 저장소를 써서, 설정의 인증서 관리자에서 따로 가져오기
Java 애플리케이션 JDK 의 신뢰 저장소에 keytool -importcert 로 추가

ca.key 를 가진 사람은 어떤 도메인의 인증서든 만들 수 있고, ca.crt 를 설치한 PC 는 그 인증서를 모두 믿습니다. 그래서 ca.key 는 서버 인증서의 비밀키보다 더 엄격하게 관리합니다. 자세한 내용은 루트 인증서를 설치한 PC 의 위험에 있습니다.

자체 서명 인증서 생성

섹션 제목: “자체 서명 인증서 생성”

자체 서명 인증서는 CA 없이 명령 한 번으로 비밀키와 인증서를 함께 만듭니다. 인증서가 자기 자신의 비밀키로 서명하므로 받는 쪽에는 확인할 루트 인증서가 없습니다. 그래서 그 인증서를 직접 설치하지 않은 PC 에서는 경고가 표시됩니다.

마지막 줄의 basicConstraints 는 이 인증서가 다른 인증서에 서명할 수 있는 CA 인지 정하는 항목입니다. openssl req -x509 는 기본 설정에서 CA 용 확장을 붙이므로, 이 항목을 지정하지 않으면 CA:TRUE 인 인증서가 만들어집니다. 사설 CA 의 루트 인증서를 만든 1단계 명령도 같은 이유로 CA:TRUE 가 됩니다. CA:FALSE 로 지정하는 이유는 루트 인증서를 설치한 PC 의 위험에 있습니다.

자체 서명과 사설 CA 의 차이

섹션 제목: “자체 서명과 사설 CA 의 차이”

두 방식 모두 서버에 두는 파일은 비밀키와 인증서 두 개로 같습니다. 사설 CA 는 여기에 CA 의 비밀키와 루트 인증서가 더해집니다. 루트 인증서는 접속하는 쪽에 설치하고, CA 의 비밀키는 서버에 두지 않습니다.

파일 자체 서명 사설 CA
server.key (서버의 비밀키) 서버 서버
server.crt (서버의 인증서, 공개키 포함) 서버 서버
ca.crt (루트 인증서) 없음 접속하는 PC 와 서버의 신뢰 저장소
ca.key (CA 의 비밀키) 없음 서버와 PC 가 아닌 곳에 따로 보관하고, 인증서를 발급할 때만 사용

경고 없이 접속하려면 접속하는 PC 마다 신뢰 저장소에 인증서를 넣어야 합니다. 이때 넣는 인증서와, 다시 넣어야 하는 때가 두 방식에서 다릅니다.

작업 자체 서명 사설 CA
경고 없이 접속 서버 인증서를 PC 마다 신뢰하는 인증서로 설치 루트 인증서를 PC 마다 한 번 설치
서버 추가 새 서버의 인증서를 PC 마다 다시 설치 같은 CA 로 서명만 하고, PC 에는 다시 설치하지 않음
인증서 갱신 바뀐 인증서를 PC 마다 다시 설치. 경고를 넘겨 쓰던 브라우저는 경고를 다시 넘김 PC 에는 다시 설치하지 않음
인증서 만들기 명령 한 번 CA 만들기, CSR 만들기, 서명의 세 단계

예를 들어 서버 3대에 PC 10대가 접속한다면, 자체 서명은 서버 인증서 3개를 PC 마다 넣어 모두 30번 설치합니다. 사설 CA 는 루트 인증서 1개를 PC 마다 넣어 10번 설치하고, 이후 서버가 늘거나 인증서를 갱신해도 PC 에는 다시 설치하지 않습니다.

PC 에 아무것도 설치하지 않고 경고를 넘겨 쓰는 경우에는 두 방식 모두 ERR_CERT_AUTHORITY_INVALID 경고가 표시되어, 사용자가 보는 차이가 없습니다. 차이는 서버와 사용자가 늘어나고 경고 없이 접속해야 할 때 커집니다.

개발 PC 한 대에서만 쓸 인증서는 mkcert 도구로도 만듭니다. mkcert -install 은 그 PC 에 사설 CA 를 만들어 신뢰 저장소에 넣고, mkcert localhost 192.168.0.20 은 그 CA 로 서명한 인증서를 만듭니다. 사설 CA 방식이므로 그 PC 에서는 경고가 표시되지 않고, 루트 인증서를 설치하지 않은 다른 PC 에서는 경고가 표시됩니다.

루트 인증서를 설치한 PC 의 위험

섹션 제목: “루트 인증서를 설치한 PC 의 위험”

신뢰 저장소에 넣은 루트 인증서에는 기본으로 서명할 수 있는 도메인의 제한이 없습니다. 그래서 CA 의 비밀키가 유출되면 다음 순서로 문제가 이어집니다.

  1. 비밀키를 가진 사람은 bank.example.com 처럼 아무 도메인의 인증서나 만들 수 있습니다.
  2. 루트 인증서를 설치한 PC 는 그 인증서를 정상 인증서로 믿습니다.
  3. 공격자가 같은 네트워크에 있거나 DNS 응답을 바꿀 수 있으면, 그 PC 와 실제 서버 사이에서 HTTPS 내용을 경고 없이 보고 바꿀 수 있습니다. 이를 중간자 공격(man-in-the-middle)이라고 합니다.

서버가 침입당하면 유출되는 것은 서버의 비밀키와 인증서입니다. 서버 인증서는 CA 가 아니어서 다른 인증서에 서명할 수 없으므로, 공격자가 사칭할 수 있는 것은 그 인증서의 SAN 에 있는 이름뿐입니다. 이 범위는 ca.key 를 서버에 함께 두지 않았을 때 유지됩니다.

자체 서명 인증서에서도 같은 문제가 생길 수 있습니다. CA:TRUE 인 자체 서명 인증서를 신뢰 저장소에 설치하면, 그 인증서는 루트 인증서와 같은 자리에 놓입니다. 이 인증서의 비밀키는 서버에 있으므로, 서버가 침입당하면 위 1~3번이 그대로 일어날 수 있습니다. 앞의 명령에서 CA:FALSE 를 지정한 것이 이 때문이고, CA:FALSE 인 인증서는 설치하더라도 그 SAN 에 있는 이름만 믿게 됩니다.

작업 방법
ca.key 보관 서버에 올리지 않고, 인증서를 발급할 때만 쓰는 곳에 따로 둡니다
서명 범위 제한 루트 인증서에 Name Constraints 확장을 넣어 .test 같은 내부 도메인에만 서명하도록 제한합니다. 이 확장을 지원하는 정도는 OS 와 브라우저마다 다릅니다
설치 범위 루트 인증서는 필요한 PC 에만 설치하고, 쓰지 않게 되면 신뢰 저장소에서 지웁니다
자체 서명 인증서 basicConstraints=critical,CA:FALSE 로 만듭니다

IP 주소 인증서

섹션 제목: “IP 주소 인증서”

https://192.168.0.20 처럼 IP 로 접속하면, 브라우저는 그 IP 가 SAN 에 IP:192.168.0.20 으로 들어 있는지 확인합니다. 도메인만 넣은 인증서로 IP 접속을 하면 이름이 맞지 않아 경고가 표시됩니다.

사설 IP 는 여러 내부망에서 같은 주소를 쓰기 때문에, 공인 인증 기관은 사설 IP 로 인증서를 발급하지 않습니다. 내부망 서버를 IP 로 접속해야 한다면 사설 CA 인증서 발급의 3단계처럼 IP 를 SAN 에 넣어 발급합니다. 내부 DNS 나 hosts 파일로 이름을 붙일 수 있다면 도메인으로 발급할 수도 있습니다.

인증서 경고

섹션 제목: “인증서 경고”

인증서 검증이 실패하면 브라우저는 페이지 대신 경고 화면을 보여 줍니다. 경고 화면의 오류 코드로 어느 항목이 실패했는지 알 수 있습니다. 다음은 Chrome 의 오류 코드입니다.

오류 코드 실패한 항목 흔한 원인
NET::ERR_CERT_AUTHORITY_INVALID 체인 자체 서명 인증서나 사설 CA 의 루트 인증서를 설치하지 않은 PC, 서버가 중간 인증서를 보내지 않음
NET::ERR_CERT_COMMON_NAME_INVALID 이름 접속한 도메인이나 IP 가 SAN 에 없음
NET::ERR_CERT_DATE_INVALID 유효 기간 인증서 만료, PC 의 시계가 틀림

주소창의 사이트 정보 아이콘을 누르면 인증서의 발급자, SAN, 유효 기간을 볼 수 있습니다.

경고를 넘긴 접속

섹션 제목: “경고를 넘긴 접속”

경고 화면의 “고급” 에서 계속 진행하면 그 페이지는 열립니다. 이 선택은 그 브라우저에 일정 시간 예외로 남지만, 인증서를 믿게 된 것은 아닙니다. 그래서 다음 경우에는 문제가 남습니다.

경우 결과
다른 사람이나 다른 브라우저로 접속 사람마다 경고를 다시 넘겨야 합니다
페이지가 다른 주소(API 서버 등)로 보내는 fetch 요청, WebSocket(wss://) 연결 경고 화면은 주소창으로 연 페이지에만 나오므로, 예외를 등록하지 않은 그 주소로는 경고 없이 연결이 실패합니다
다른 서버나 앱이 호출 서버의 HTTP 클라이언트는 예외를 두지 않으므로 인증서 오류로 실패합니다

여러 사람이 쓰는 서버라면 경고를 넘기는 대신, 공인 인증서를 쓰거나 사설 CA 의 루트 인증서를 사용하는 PC 에 설치해 경고 자체가 표시되지 않게 합니다.

HSTS

섹션 제목: “HSTS”

HSTS(HTTP Strict Transport Security)는 서버가 “이 도메인은 앞으로 HTTPS 로만 접속하라”고 브라우저에 알려 두는 응답 헤더입니다.

부분 뜻
max-age 브라우저가 이 지시를 기억하는 시간(초). 31536000 은 1년
includeSubDomains 서브도메인에도 똑같이 적용

이 헤더를 받은 브라우저는 max-age 동안 두 가지를 다르게 처리합니다.

  • 주소창에 http:// 로 입력해도 요청을 보내기 전에 https:// 로 바꿉니다. 중간에서 HTTP 요청을 가로채는 공격을 막습니다.
  • 그 도메인의 인증서 경고 화면에서 계속 진행하는 버튼을 없앱니다.

두 번째 동작 때문에, 접속하는 PC 에 설치하지 않은 자체 서명 인증서나 사설 CA 인증서를 쓰는 서버에서는 HSTS 를 켜지 않습니다. 켜면 그 도메인에 접속할 수 없게 됩니다. 브라우저가 기억한 HSTS 는 헤더를 지워도 max-age 가 지날 때까지 남습니다. Nginx 의 HTTPS 설정과 HTTP→HTTPS 리다이렉션은 Nginx 글에 있습니다.

인증서 확인 명령

섹션 제목: “인증서 확인 명령”

브라우저 밖에서는 openssl 과 curl 로 서버가 보내는 인증서를 확인합니다.

-servername 은 SNI 로 보낼 도메인입니다. 한 IP 에 여러 도메인이 있는 서버는 이 값에 따라 다른 인증서를 보냅니다.

curl -k 는 인증서 검증을 건너뜁니다. 서버가 응답하는지만 확인할 때 쓰고, 인증서 문제를 해결하는 방법으로 쓰지 않습니다.

명령어 요약

섹션 제목: “명령어 요약”
작업 명령
서버 인증서 확인 openssl s_client -connect 도메인:443 -servername 도메인
인증서 파일 내용 보기 openssl x509 -in 파일 -noout -text
사설 CA 만들기 openssl req -x509 -new -nodes -newkey rsa:2048 -keyout ca.key -out ca.crt -days 3650
자체 서명 인증서 만들기 openssl req -x509 -nodes -newkey rsa:2048 -keyout server.key -out server.crt -addext "basicConstraints=critical,CA:FALSE"
서버 비밀키와 CSR 만들기 openssl req -new -nodes -newkey rsa:2048 -keyout server.key -out server.csr
사설 CA 로 서명 openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out server.crt -extfile san.ext
루트 인증서 설치 (Ubuntu) /usr/local/share/ca-certificates/ 에 복사 후 sudo update-ca-certificates
사설 CA 로 검증해 요청 curl --cacert ca.crt https://도메인
