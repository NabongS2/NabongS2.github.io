Nginx, 정적 파일부터 API 프록시까지

2026년 9월 28일 · 읽는 데 8분
nabong

자바 앱 하나가 화면과 API 를 함께 내보내다가 프론트엔드와 백엔드로 나누면, 전에는 없던 일이 둘 생깁니다. 빌드된 화면 파일을 누가 내보낼지, 브라우저가 보내는 API 요청을 누가 백엔드로 넘길지입니다. 이 글은 그 두 일이 환경마다 어떻게 동작하는지와, 서버에서 그 일을 Nginx 로 하는 방법입니다.

단일 애플리케이션과 분리 구조

섹션 제목: “단일 애플리케이션과 분리 구조”

스프링 부트 앱 하나로 만든 서비스는 앱 하나가 모든 요청을 받습니다. / 로 오면 HTML 을 만들어 돌려주고, /api 로 오면 JSON 을 돌려줍니다. 컨테이너도 하나, 주소도 하나입니다.

프론트엔드를 React 나 Vue 로 따로 만들면 사정이 달라집니다. 프론트엔드는 npm run build 를 하면 dist/ 폴더에 index.html 과 JS, CSS 파일이 나옵니다. 이건 파일일 뿐이라 스스로 요청을 받지 못합니다. 누군가 이 파일을 브라우저에 내보내 줘야 합니다. 백엔드는 이제 API 만 처리합니다.

단일 애플리케이션 분리 구조
화면 자바 앱이 HTML 을 만들어 돌려줌 빌드된 파일. 내보낼 프로그램이 따로 필요
API 자바 앱 백엔드
실행 단위 하나 둘

그래서 질문이 둘 생깁니다. 화면 파일은 누가 내보내나. 그리고 화면에서 보낸 /api 요청은 어떻게 백엔드까지 가나.

한 주소와 경로 분리

섹션 제목: “한 주소와 경로 분리”

화면과 API 를 서로 다른 주소에 두면 브라우저가 막습니다. 브라우저는 주소의 프로토콜·호스트·포트가 모두 같아야 같은 출처로 봅니다. 화면이 :8080 에 있고 API 가 :8100 에 있으면 출처가 다르고, 그러면 백엔드가 CORS 헤더를 따로 돌려주지 않는 한 브라우저가 응답을 읽지 못하게 합니다. 로그인 쿠키를 주고받는 것도 복잡해집니다.

그래서 보통은 앞에 프로그램 하나를 두고, 주소는 하나로 모은 뒤 경로로 나눕니다.

브라우저 입장에서는 주소가 하나라 출처 문제가 없습니다. 앞에 둔 프로그램이 경로를 보고 /api 는 백엔드로 넘기고, 나머지는 화면 파일로 답합니다. 이런 프로그램을 리버스 프록시라고 합니다.

프록시와 리버스 프록시

섹션 제목: “프록시와 리버스 프록시”

프록시는 요청을 대신 받아서 다른 곳에 전달하고, 받은 응답을 다시 돌려주는 중간 프로그램입니다. 영어 proxy 가 “대리” 라는 뜻입니다.

프록시는 누구 쪽에 있느냐로 둘로 나뉩니다.

프록시 (포워드 프록시) 리버스 프록시
어느 쪽에 있나 요청하는 쪽. 브라우저 앞 요청받는 쪽. 서버 앞
누가 존재를 아나 브라우저가 설정해서 씁니다 브라우저는 모릅니다. 그 주소가 곧 서버인 줄 압니다
가려 주는 것 요청한 사람. 서버는 프록시가 요청한 것으로 봅니다 뒤의 서버. 브라우저는 백엔드 주소를 모릅니다
예 회사 네트워크에서 외부 사이트로 나갈 때 거치는 프록시 Nginx 가 /api 를 백엔드로 넘기는 것

그냥 “프록시” 라고 하면 보통 앞쪽, 포워드 프록시를 가리킵니다. 이 글에서 Nginx 가 하는 일은 리버스 프록시입니다. 브라우저는 app.example.com 하나만 알고, 그 뒤에 화면 파일과 백엔드가 따로 있다는 것은 모릅니다.

설정 이름에 붙은 proxy 도 이 뜻입니다. Nginx 의 proxy_pass 와 Vite 설정의 proxy 둘 다, 받은 요청을 뒤의 백엔드로 넘기는 리버스 프록시 설정입니다.

환경별 역할

섹션 제목: “환경별 역할”

그 리버스 프록시가 환경마다 다릅니다.

화면 파일 내보내기 /api 넘기기
로컬 개발 Vite 개발 서버 (npm run dev) vite.config.ts 의 server.proxy
개발 서버·운영 Nginx Nginx 의 proxy_pass

로컬에서 Nginx 없이 개발할 수 있는 건 Vite 개발 서버가 같은 일을 하기 때문입니다. npm run dev 로 띄운 개발 서버가 화면을 내보내고, 설정 파일의 proxy 에 적힌 경로는 백엔드로 넘깁니다.

백엔드는 IDE 나 Gradle 로 따로 띄워 둡니다. 브라우저는 localhost:5173 하나만 보고, /api 로 시작하는 요청은 개발 서버가 localhost:8100 으로 넘깁니다.

개발 서버는 개발할 때만 씁니다. 코드를 고치면 바로 화면에 반영하는 기능이 들어 있어서, 서버에 올리는 용도가 아닙니다. 서버에서는 npm run build 로 만든 dist/ 를 Nginx 가 내보냅니다.

두 환경이 같은 일을 서로 다른 설정 파일로 하기 때문에, 경로 규칙은 두 곳에 같이 적혀 있어야 합니다. vite.config.ts 에 /auth 를 넘기도록 추가하고 Nginx 설정에는 빠뜨리면, 로컬에서는 되는데 서버에서는 404 가 납니다.

dist 빌드

섹션 제목: “dist 빌드”

Nginx 가 내보낼 화면 파일은 프론트엔드 프로젝트에서 빌드해서 만듭니다. Vite 기준입니다.

npm install 대신 npm ci 를 쓰면 매번 같은 버전으로 설치됩니다. 서버나 CI 에서 빌드할 때 씁니다.

빌드가 끝나면 이런 폴더가 생깁니다.

index.html 하나와, JS·CSS 를 묶은 파일 몇 개입니다. 파일 이름 뒤의 문자열은 내용으로 만든 값이라, 코드를 고쳐 다시 빌드하면 이름이 바뀝니다.

빌드 모드와 환경 변수

섹션 제목: “빌드 모드와 환경 변수”

개발 서버용과 운영용 설정이 다르면 모드를 지정해 빌드합니다. --mode dev 로 빌드하면 .env.dev 파일을 읽습니다.

VITE_ 로 시작하는 값은 빌드할 때 JS 파일 안에 들어갑니다. 서버에서 실행 중에 읽는 값이 아니라서, 값을 바꾸려면 다시 빌드해야 합니다.

그래서 API 주소는 https://api.example.com 처럼 환경 변수에 적기보다 /api 같은 경로로만 쓰는 편이 다루기 쉽습니다. 화면과 API 가 같은 주소에 있으니 경로만으로 요청이 가고, 개발 서버든 운영이든 같은 빌드 결과를 쓸 수 있습니다.

서버에 두는 방법

섹션 제목: “서버에 두는 방법”

dist/ 를 Nginx 의 root 가 가리키는 폴더에 두면 됩니다. 방법은 셋입니다.

볼륨으로 연결 이미지에 복사 이미지 안에서 빌드
빌드 컨테이너 밖에서 npm run build 컨테이너 밖에서 npm run build Dockerfile 안에서
이미지 nginx 공식 이미지 그대로 nginx + dist/ nginx + dist/
새 버전 배포 호스트의 dist/ 폴더만 바꿔 넣음 밖에서 빌드하고 이미지를 다시 만듦 이미지를 다시 만듦
빌드 환경 빌드하는 PC·CI 마다 다를 수 있음 빌드하는 PC·CI 마다 다를 수 있음 Dockerfile 에 고정

볼륨으로 연결하면 docker run 에 -v /opt/web/dist:/usr/share/nginx/html 을 붙입니다. 아래 「컨테이너 간 연결」의 예시가 이 방식입니다.

이미지에 복사는 밖에서 만든 dist/ 를 이미지에 넣기만 합니다.

Dockerfile 이 짧고 이미지도 작습니다. 대신 빌드하는 곳에 Node 가 있어야 하고, 사람마다 Node 버전이 다르면 결과가 달라질 수 있습니다.

이미지 안에서 빌드할 때는 빌드와 실행을 나눠 적습니다.

앞 단계에서 Node 로 빌드하고, 뒤 단계에는 dist/ 와 설정 파일만 옮깁니다. 최종 이미지에는 Node 와 소스 코드가 남지 않습니다. 이렇게 Dockerfile 하나 안에서 단계를 나누는 것을 멀티 스테이지 빌드라고 합니다.

단계를 나누지 않고 node 이미지 하나에서 빌드와 실행을 다 하면 Node, node_modules, 소스 코드가 모두 최종 이미지에 남아 수백 MB 가 됩니다. 서버에서는 쓰지 않는 것들입니다.

Nginx 설정

섹션 제목: “Nginx 설정”

화면 파일을 내보내고 /api 를 넘기는 최소 설정입니다. 공식 이미지 기준으로 /etc/nginx/conf.d/default.conf 에 둡니다.

server 와 location

섹션 제목: “server 와 location”

server 는 포트 하나에 대한 설정 묶음입니다. 그 안의 location 이 경로별로 무엇을 할지 정합니다.

요청 경로가 여러 location 에 맞으면 가장 길게 맞는 쪽을 씁니다. /api/users 는 / 에도 /api/ 에도 맞지만, 더 긴 /api/ 가 처리합니다. 그래서 / 를 “나머지 전부” 로 두고 필요한 경로만 따로 적으면 됩니다.

정적 파일 — root 와 try_files

섹션 제목: “정적 파일 — root 와 try_files”

root 는 파일을 찾을 폴더입니다. /logo.png 로 요청이 오면 /usr/share/nginx/html/logo.png 를 찾아 돌려줍니다.

try_files 가 없으면 새로고침할 때 404 가 납니다. React·Vue 앱의 화면 주소는 파일이 아니기 때문입니다. /history/12 같은 주소는 브라우저 안의 JS 가 화면을 바꾸면서 만든 것이라, dist/ 에 그런 파일이 없습니다. 앱 안에서 이동할 때는 문제가 없다가, 그 주소에서 새로고침하면 브라우저가 서버에 /history/12 파일을 달라고 하고 Nginx 는 없다고 답합니다.

try_files $uri $uri/ /index.html 은 앞에서부터 차례로 찾습니다.

순서 찾는 것 예: /logo.png 예: /history/12
1 $uri — 그 이름의 파일 있음 → 돌려줌 없음
2 $uri/ — 그 이름의 폴더 없음
3 /index.html 돌려줌 → JS 가 /history/12 화면을 그림

API 프록시 — proxy_pass

섹션 제목: “API 프록시 — proxy_pass”

proxy_pass 가 요청을 백엔드로 넘깁니다. upstream 은 백엔드 주소에 이름을 붙여 두는 것입니다. 주소를 proxy_pass http://192.168.0.20:8100; 처럼 바로 적어도 됩니다.

Nginx 를 거치면 백엔드가 보는 접속자는 브라우저가 아니라 Nginx 가 됩니다. 아래 헤더 넷이 원래 요청의 정보를 백엔드에 전합니다.

헤더 담는 것
Host 브라우저가 요청한 도메인
X-Real-IP 브라우저의 IP
X-Forwarded-For 거쳐 온 IP 목록. 맨 앞이 브라우저
X-Forwarded-Proto 브라우저가 http 로 왔는지 https 로 왔는지

백엔드가 접속자 IP 를 로그에 남기거나 리다이렉트 주소를 만들 때 이 헤더를 읽습니다. 빠뜨리면 모든 요청이 Nginx 의 IP 에서 온 것으로 보입니다.

proxy_pass 끝에 / 를 붙이느냐에 따라 백엔드가 받는 경로가 달라집니다. 브라우저가 /api/users 를 요청했을 때를 따라가 보겠습니다.

  • / 가 없으면 요청 경로를 손대지 않고 그대로 넘깁니다. /api/users 가 그대로 갑니다
  • / 가 있으면 location 에 걸린 /api/ 를 떼고, 그 자리에 proxy_pass 에 적은 / 를 넣습니다. /api/users 에서 /api/ 가 / 로 바뀌어 /users 가 됩니다

어느 쪽을 쓸지는 백엔드 컨트롤러의 주소를 보고 정합니다.

백엔드에서 404 가 나는데 Nginx 로그에는 요청이 찍혀 있다면 이 부분부터 봅니다.

컨테이너 간 연결

섹션 제목: “컨테이너 간 연결”

Nginx 와 백엔드를 각각 컨테이너로 띄우면, Nginx 설정의 백엔드 주소를 무엇으로 적을지가 문제입니다.

localhost 는 쓸 수 없습니다. 컨테이너 안에서 localhost 는 그 컨테이너 자신입니다. Nginx 컨테이너 안에는 백엔드가 없으니 연결이 거부됩니다.

방법은 둘입니다.

호스트 IP 로 적기

섹션 제목: “호스트 IP 로 적기”

도커 네트워크를 따로 만들지 않아도 됩니다. 백엔드 포트를 -p 로 호스트에 열고, Nginx 설정에는 서버의 IP 와 그 포트를 적습니다.

Nginx 는 컨테이너 밖으로 나가 서버의 8100 포트로 연결하고, 그 포트가 백엔드 컨테이너로 이어집니다. 백엔드가 다른 서버에 있어도 IP 만 바꾸면 같은 방식으로 됩니다.

적는 IP 는 서버의 IP 입니다. docker inspect 로 보이는 172.17.0.x 같은 컨테이너 IP 는 컨테이너를 다시 띄우면 바뀔 수 있어서 설정에 적지 않습니다.

도커 네트워크로 연결하기

섹션 제목: “도커 네트워크로 연결하기”

같은 도커 네트워크에 두면 도커가 컨테이너 이름을 주소로 풀어 줍니다. 네트워크를 만들고 두 컨테이너를 그 네트워크로 띄웁니다.

이 경우 백엔드는 -p 로 포트를 밖에 열지 않아도 됩니다. 브라우저는 Nginx 만 거치고, Nginx 는 네트워크 안에서 백엔드에 연결하기 때문입니다.

둘의 차이

섹션 제목: “둘의 차이”
호스트 IP 도커 네트워크
준비 없음 docker network create
설정에 적는 주소 192.168.0.20:8100 backend-app:8100
백엔드 포트를 밖에 열기 열어야 합니다 열지 않아도 됩니다
백엔드가 다른 서버에 있을 때 됩니다 안 됩니다. 같은 서버, 같은 네트워크만
서버 IP 가 바뀌면 설정을 고쳐야 합니다 영향이 없습니다

컨테이너를 띄우는 방법 자체는 도커 글에 있습니다.

설정 검사와 반영

섹션 제목: “설정 검사와 반영”

설정을 고친 뒤에는 먼저 문법을 검사하고, 통과하면 다시 읽게 합니다.

nginx -t 가 실패한 상태로 reload 하면 Nginx 는 옛 설정으로 계속 동작합니다. 바꾼 게 반영이 안 되는 것처럼 보일 때는 nginx -t 결과부터 봅니다.

공식 이미지는 접근 로그와 에러 로그를 컨테이너 출력으로 내보내서 docker logs 로 바로 보입니다.

자주 보는 응답 코드는 이 정도입니다.

코드 뜻 먼저 볼 곳
404 (새로고침할 때만) 화면 주소에 해당하는 파일이 없음 try_files
404 (백엔드가 돌려줌) 백엔드가 받은 경로가 다름 proxy_pass 끝의 /
502 Bad Gateway Nginx 가 백엔드에 연결하지 못함 백엔드 주소·포트, 백엔드 컨테이너가 떠 있는지
504 Gateway Timeout 백엔드가 제시간에 답하지 않음 백엔드 처리 시간. 기본 대기 시간은 60초
