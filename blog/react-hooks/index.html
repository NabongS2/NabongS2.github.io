React 기본 훅

2026년 10월 12일 · 읽는 데 8분
nabong

CSR 글에서 CSR 은 브라우저의 JS 가 화면을 만든다고 했습니다. React 앱에서 그 일을 하는 것이 컴포넌트이고, 컴포넌트가 값을 기억하거나 화면을 그린 뒤 작업을 하게 해 주는 함수가 훅(hook)입니다. 이 글은 자주 쓰는 기본 훅 여섯 가지와, 컴포넌트끼리 값을 주고받는 props 입니다.

컴포넌트와 렌더링

섹션 제목: “컴포넌트와 렌더링”

컴포넌트는 화면에 보일 JSX 를 return 하는 함수입니다.

이 버튼은 눌러도 숫자가 바뀌지 않습니다. 두 가지 이유가 있습니다.

  • count 를 바꿔도 React 는 화면을 다시 그려야 한다는 걸 모릅니다.
  • 다시 그리더라도 Counter() 가 처음부터 실행되면서 let count = 0 으로 돌아갑니다.

React 에서 화면을 바꾸려면 React 가 보관하는 값, 즉 상태를 바꿔야 합니다. 상태가 바뀌면 React 는 컴포넌트 함수를 다시 실행합니다. 이것을 렌더링이라고 합니다.

이 글의 훅들은 모두 이 순서를 바탕으로 합니다. 특히 렌더링마다 함수가 처음부터 다시 실행되고, 함수 안의 변수·객체·함수가 매번 새로 만들어진다는 점이 useRef, useMemo, useCallback 이 필요한 이유입니다.

useState

섹션 제목: “useState”

렌더링이 끝나도 남아 있고, 바꾸면 화면을 다시 그리는 값입니다.

부분 뜻
useState(0) 처음 값. 첫 렌더링에만 쓰입니다
count 이번 렌더링의 값
setCount 값을 바꾸고 다시 렌더링하게 하는 함수

바로 바뀌지 않는 값

섹션 제목: “바로 바뀌지 않는 값”

setCount 를 호출해도 지금 실행 중인 함수의 count 는 그대로입니다. 새 값은 다음 렌더링에서 보입니다.

이전 값으로 바꾸기

섹션 제목: “이전 값으로 바꾸기”

같은 이유로, 한 번에 두 번 더하려고 이렇게 쓰면 1 만 늘어납니다.

이전 값을 기준으로 바꿀 때는 함수를 넘깁니다. React 가 바로 앞의 값을 넣어 줍니다.

객체와 배열

섹션 제목: “객체와 배열”

React 는 새 값이 이전 값과 같은 객체인지를 보고 다시 그릴지 정합니다. 내용을 바꿔도 같은 배열이면 바뀌지 않은 것으로 봅니다.

... 은 전개 구문(spread syntax)입니다. 배열이나 객체의 내용을 그 자리에 하나씩 꺼내 놓습니다. 그래서 [...items] 는 내용이 같은 새 배열이고, { ...user } 는 필드가 같은 새 객체입니다.

하려는 것 원본을 바꾸는 방법 (쓰지 않음) 새로 만드는 방법
추가 push [...items, item]
삭제 splice items.filter((x) => x.id !== id)
수정 items[i] = … items.map((x) => x.id === id ? { ...x, name } : x)
정렬 sort [...items].sort(…), items.toSorted(…)
객체 필드 수정 user.name = … { ...user, name }

sort 는 원본 배열의 순서를 바꾼다는 점을 놓치기 쉽습니다. 서버에서 받아 온 데이터 배열에 바로 sort 를 쓰면, 그 데이터를 함께 쓰는 다른 화면의 순서까지 바뀝니다.

props

섹션 제목: “props”

props 는 부모 컴포넌트가 자식 컴포넌트에 넘기는 값입니다. 컴포넌트가 함수이니, props 는 그 함수의 인자입니다.

성질 뜻
읽기 전용 자식은 받은 props 를 바꾸지 않습니다. 바꿔야 하면 값을 가진 부모가 바꿉니다
부모를 따라 다시 렌더링 부모가 다시 렌더링되면 자식도 다시 렌더링됩니다. props 가 같아도 그렇습니다

함수 props

섹션 제목: “함수 props”

자식이 부모의 값을 바꿔야 할 때는 부모가 함수를 props 로 넘기고, 자식은 그 함수를 호출합니다.

PlusButton 은 count 를 모르고, 눌렸다는 것만 onPlus() 로 알립니다. 상태를 바꾸는 것은 Parent 이고, 바뀐 count 는 Parent 가 다시 렌더링되면서 화면에 반영됩니다.

React 의 데이터는 이렇게 한 방향으로 흐릅니다. 값은 props 로 위에서 아래로 내려가고, 이벤트는 함수 호출로 아래에서 위로 올라갑니다. 값이 어디서 바뀌는지 찾을 때는 그 값을 상태로 가진 컴포넌트 하나만 보면 됩니다.

상태 끌어올리기

섹션 제목: “상태 끌어올리기”

형제 컴포넌트 둘이 같은 값을 써야 하면, 그 상태를 둘의 공통 부모로 옮기고 props 로 나눠 줍니다. 이것을 상태 끌어올리기(lifting state up)라고 합니다.

SearchInput 이 keyword 를 자기 상태로 가지고 있으면 ResultList 는 그 값을 알 수 없습니다. 둘의 부모인 SearchPage 가 상태를 가지면 둘 다 props 로 받습니다.

props drilling

섹션 제목: “props drilling”

상태를 위로 올리다 보면, 맨 아래 컴포넌트 하나에 값을 넘기려고 중간 컴포넌트들이 쓰지도 않는 props 를 받아서 그대로 넘기게 됩니다. 이것을 props drilling 이라고 합니다.

몇 단계 정도는 문제가 없습니다. 단계가 깊어지면 중간 컴포넌트가 상관없는 props 를 알아야 하고, props 이름이나 타입을 바꿀 때 거쳐 가는 파일을 모두 고쳐야 합니다. 이때 아래의 useContext 를 쓰거나, 상태 관리 라이브러리를 사용하여 관리할 수 있습니다.

useEffect

섹션 제목: “useEffect”

화면이 그려진 뒤에 실행할 작업을 등록합니다. 렌더링 결과를 만드는 일과 상관없는 작업, 즉 API 호출, 타이머, 이벤트 구독, DOM 직접 조작 같은 것을 여기에 둡니다.

의존성 배열

섹션 제목: “의존성 배열”

두 번째 인자인 배열이 언제 다시 실행할지 정합니다.

의존성 배열 실행 시점
없음 렌더링할 때마다
[] 처음 화면에 나왔을 때 한 번
[id] 처음 한 번, 그리고 id 가 바뀔 때마다

effect 안에서 쓰는 props, 상태, 변수는 모두 배열에 넣습니다. 빠뜨리면 effect 가 옛 값을 계속 쓰게 됩니다. ESLint 의 react-hooks/exhaustive-deps 규칙이 빠진 것을 알려 줍니다.

정리 함수

섹션 제목: “정리 함수”

effect 가 함수를 return 하면, React 는 다음 effect 를 실행하기 전과 컴포넌트가 화면에서 사라질 때 그 함수를 호출합니다. 타이머나 구독을 해제하는 데 씁니다.

개발 모드의 StrictMode 에서는 effect 가 실행 → 정리 → 다시 실행 순서로 두 번 돕니다. 정리 함수를 빠뜨렸을 때 바로 드러나게 하려는 것이고, 운영 빌드에서는 한 번만 실행됩니다. 개발 중에 API 가 두 번 호출되는 것이 이 때문입니다.

effect 가 필요 없는 경우

섹션 제목: “effect 가 필요 없는 경우”

props 나 상태로 계산할 수 있는 값은 effect 와 상태를 쓰지 않고 렌더링 중에 바로 계산합니다.

실무에서 API 호출은 직접 useEffect 로 쓰기보다 React Query 같은 라이브러리에 맡기는 경우가 많습니다. 불러오는 중·실패 상태, 캐시, 다시 불러오기를 대신 처리해 주기 때문입니다.

useRef

섹션 제목: “useRef”

렌더링이 끝나도 남아 있지만, 바꿔도 다시 렌더링하지 않는 값입니다. ref.current 로 읽고 씁니다.

쓰임 예
DOM 요소 잡기 입력창에 포커스, 스크롤 위치 이동
화면과 상관없는 값 보관 타이머 id, 이전 값, 요청 중인지 여부
일반 변수 useState useRef
다음 렌더링까지 남는가 아니요. 매번 새로 만들어짐 예 예
바꾸면 다시 렌더링하는가 아니요 예 아니요
바꾼 값이 보이는 때 바로 다음 렌더링 바로

화면에 보여야 하는 값은 useState, 화면과 상관없이 기억만 하면 되는 값은 useRef 입니다.

useMemo 와 useCallback

섹션 제목: “useMemo 와 useCallback”

렌더링마다 함수 안의 객체와 함수는 새로 만들어집니다. 내용이 같아도 새로 만든 객체는 이전 것과 다른 객체로 봅니다.

useMemo 는 계산 결과를, useCallback 은 함수를 기억해 둡니다. 의존성 배열의 값이 바뀌지 않으면 이전에 만든 것을 그대로 돌려줍니다.

useCallback(fn, deps) 는 useMemo(() => fn, deps) 와 같습니다. 기억하는 대상이 함수일 뿐입니다.

필요한 경우

섹션 제목: “필요한 경우”
경우 예
계산이 무거울 때 수천 건의 목록을 정렬하거나 필터링
결과를 다른 곳의 비교 기준으로 넘길 때 useEffect 의 의존성 배열, React.memo 로 감싼 자식의 props

두 번째 경우가 위의 options 예입니다. 기억해 두지 않으면 effect 가 렌더링마다 실행되거나, React.memo 로 감싼 자식이 props 가 바뀐 것으로 보고 매번 다시 렌더링됩니다.

필요 없는 경우

섹션 제목: “필요 없는 경우”
  • 짧은 배열의 filter, 문자열 합치기처럼 가벼운 계산
  • 결과를 화면에 바로 쓰고, 다른 곳의 비교 기준으로 넘기지 않을 때

이럴 때는 기억해 두는 비용(의존성 비교, 이전 값 보관)과 코드가 길어지는 비용이 얻는 것보다 큽니다. 붙여도 동작은 같지만, 모든 값에 붙이면 정말 필요한 곳이 어디인지 알아보기 어려워집니다. React Compiler 를 쓰면 빌드할 때 이런 기억을 자동으로 넣어 줘서 직접 붙일 일이 줄어듭니다.

안에서 원본을 바꾸지 않기

섹션 제목: “안에서 원본을 바꾸지 않기”

useMemo 안에서 정렬할 때도 원본 배열을 바꾸지 않습니다.

JS 에서 배열을 변수에 담거나 넘기면 배열이 복사되지 않습니다. 같은 배열 하나를 여러 이름이 함께 가리킬 뿐입니다.

sort 는 새 배열을 만들지 않고 그 배열 자체의 순서를 바꿉니다. 그래서 위의 첫 번째 코드에서 data.sort(…) 는 useMemo 안에서만 쓰는 값이 아니라, data 가 가리키는 원래 배열을 바꿉니다.

data 가 React Query 같은 라이브러리에서 받은 서버 데이터라면, 그 배열은 라이브러리가 캐시로 보관하는 바로 그 배열입니다. 같은 데이터를 쓰는 다른 화면이 있으면 그쪽에서도 순서가 바뀐 배열을 받게 됩니다. 정렬 기준이 다른 화면이 두 개면 서로의 순서를 덮어쓰고, 어느 화면이 먼저 렌더링되느냐에 따라 결과가 달라집니다.

[...data] 로 복사본을 만든 뒤 정렬하면 원래 배열은 그대로 남습니다. data.toSorted(…) 도 같은 일을 합니다. 정렬된 새 배열을 돌려주고 원본은 바꾸지 않습니다.

메서드 원본을 바꾸나 대신 쓰는 것
sort 바꿈 [...arr].sort(), arr.toSorted()
reverse 바꿈 [...arr].reverse(), arr.toReversed()
splice 바꿈 filter, arr.toSpliced()
push, pop, shift, unshift 바꿈 [...arr, item], arr.slice(…)
map, filter, slice, concat 안 바꿈 그대로 써도 됨

useContext

섹션 제목: “useContext”

앞의 props drilling 을 해결합니다. 위에서 값을 한 번 넣어 두면, 아래 컴포넌트는 중간을 거치지 않고 바로 꺼내 씁니다.

Provider 의 value 가 바뀌면 그 값을 쓰는 컴포넌트가 모두 다시 렌더링됩니다. 그래서 로그인 사용자, 화면 테마, 언어처럼 자주 바뀌지 않고 여러 곳에서 쓰는 값에 맞습니다. 여러 컴포넌트가 함께 쓰는 값이 자주 바뀌면, 그 값을 쓰지 않는 컴포넌트까지 다시 렌더링되지 않도록 Zustand 같은 상태 관리 라이브러리를 사용하여 관리할 수 있습니다.

훅의 규칙

섹션 제목: “훅의 규칙”

훅은 아무 곳에서나 호출할 수 있는 함수가 아닙니다. React 가 정해 둔 규칙이 두 가지 있습니다. 이 글의 훅뿐 아니라 라이브러리가 주는 훅과 직접 만든 훅도 같은 규칙을 따릅니다.

컴포넌트 안에서만 호출

섹션 제목: “컴포넌트 안에서만 호출”

훅은 컴포넌트 함수나 다른 훅 안에서만 호출합니다. 일반 함수에서는 호출할 수 없습니다.

훅이 기억하는 값은 지금 렌더링 중인 컴포넌트에 저장됩니다. 일반 함수는 렌더링 중인 컴포넌트가 없어서 값을 저장할 곳이 없습니다.

컴포넌트 맨 위에서 호출

섹션 제목: “컴포넌트 맨 위에서 호출”

훅은 컴포넌트 함수의 맨 위에서 호출합니다. 조건이 필요하면 훅을 호출한 다음에 씁니다.

useEffect 를 조건에 따라 실행하고 싶으면, 조건을 useEffect 안에 씁니다.

ESLint 의 react-hooks/rules-of-hooks 규칙이 두 규칙을 어긴 곳을 알려 줍니다.

직접 만든 훅

섹션 제목: “직접 만든 훅”

use 로 시작하고 안에서 다른 훅을 호출하는 함수도 훅입니다. 이 글의 useLoginUser 처럼 여러 컴포넌트에서 쓰는 훅 조합을 함수 하나로 묶을 때 만듭니다. 이름이 use 로 시작해야 ESLint 가 훅으로 알아보고 위 규칙을 검사합니다.

정리

섹션 제목: “정리”
