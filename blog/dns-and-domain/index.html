DNS 와 도메인

2026년 10월 28일 · 읽는 데 13분
nabong

시리즈네트워크 기초

  1. 네트워크 계층
  2. IP 주소와 포트
  3. NAT 와 포트포워딩
  4. VPN
  5. DNS 와 도메인
  6. HTTPS 와 인증서

앞 글들에서는 192.168.0.20 처럼 IP 로 접속했습니다. 실제로는 example.com 같은 도메인으로 접속하는 경우가 많고, 브라우저는 접속하기 전에 도메인을 IP 로 바꿉니다. 이 글에서는 그 과정인 DNS 와 레코드, hosts 파일, 내부 DNS, 조회 결과를 확인하는 방법을 알아봅니다. 네트워크 계층으로 보면 DNS 는 응용 계층의 프로토콜이고, UDP 53 번 포트를 씁니다(응답이 크면 TCP 53 번).

도메인과 DNS

섹션 제목: “도메인과 DNS”

도메인은 사람이 기억하기 쉽게 IP 주소에 붙인 이름입니다. DNS(Domain Name System)는 도메인을 IP 주소로 바꿔 주는 시스템입니다.

브라우저에 https://api.example.com 을 입력하면, 브라우저는 먼저 DNS 에 api.example.com 의 IP 를 묻고, 받은 IP(203.0.113.20)로 접속합니다. 서버를 다른 IP 로 옮겨도 DNS 의 값만 바꾸면 사용자는 같은 도메인으로 접속할 수 있습니다.

도메인의 구조

섹션 제목: “도메인의 구조”

도메인은 점으로 나뉘고, 오른쪽으로 갈수록 넓은 범위입니다.

부분 이름 정하는 곳
.com 최상위 도메인(TLD) 국제 기관이 정합니다. .com, .org, .kr 등
example 등록한 도메인 도메인 등록 업체에서 구매해 등록합니다
api 서브도메인 도메인 주인이 DNS 에 레코드를 추가해 만듭니다

example.com 을 등록하면 api.example.com, www.example.com, dev.example.com 처럼 그 아래 이름은 따로 등록하지 않고 만들 수 있습니다.

서브도메인과 경로

섹션 제목: “서브도메인과 경로”

서브도메인은 도메인 앞에 붙는 이름이고, 도메인 뒤의 /users/12 같은 부분은 경로입니다. 둘은 처리하는 곳이 다릅니다.

부분 https://api.example.com/users/12 에서 처리하는 곳
서브도메인과 도메인 api.example.com DNS 가 IP 로 바꿉니다. 서브도메인마다 다른 IP 로 보낼 수 있습니다
경로 /users/12 DNS 는 경로를 보지 않습니다. 그 IP 의 서버(Nginx, 백엔드)가 받아서 나눕니다

그래서 프론트엔드와 백엔드를 나누는 주소도 두 가지로 만들 수 있습니다.

방식 주소 특징
경로로 나누기 example.com, example.com/api Nginx 글의 방식입니다. 주소가 하나라 CORS 설정이 필요 없습니다
서브도메인으로 나누기 example.com, api.example.com DNS 에서 서로 다른 서버로 보낼 수 있습니다. 호스트가 달라 origin 이 다르므로 백엔드에 CORS 설정이 필요합니다

레코드

섹션 제목: “레코드”

DNS 에 도메인마다 적어 두는 한 줄 한 줄을 레코드라고 합니다. 레코드는 아래에서 볼 네임서버에 저장됩니다.

왼쪽부터 이름, TTL(이 결과를 캐시에 둘 수 있는 시간, 초), 레코드 종류, 값입니다. TTL 은 아래 “캐시와 TTL” 에서 다룹니다.

종류 값 쓰는 곳
A IPv4 주소 도메인을 IP 로 연결
AAAA IPv6 주소 도메인을 IPv6 주소로 연결
CNAME 다른 도메인 별칭. 위 예에서 www.example.com 은 example.com 의 IP 를 따릅니다
MX 메일 서버 도메인 이 도메인으로 오는 메일을 받을 서버
TXT 텍스트 도메인 소유 확인, 메일 발신 인증
NS 네임서버 도메인 이 도메인을 맡은 권한 있는 네임서버

CNAME

섹션 제목: “CNAME”

A 레코드는 IP 를 바로 돌려주고, CNAME 레코드는 다른 도메인 이름을 돌려줍니다.

레코드 조회한 이름 돌아오는 값
A example.com 203.0.113.10 (IP)
CNAME www.example.com example.com (다른 도메인)

그래서 www.example.com 의 IP 를 알아내려면 조회가 두 번 일어납니다.

  1. www.example.com 을 조회하면 IP 대신 CNAME 으로 example.com 이 돌아옵니다. www.example.com 은 example.com 의 다른 이름이라는 뜻입니다.
  2. 이어서 example.com 을 조회해 A 레코드의 203.0.113.10 을 받습니다.
  3. 브라우저는 마지막에 받은 203.0.113.10 으로 접속합니다.

두 번째 조회는 DNS 가 이어서 처리하므로 브라우저는 IP 하나만 받습니다.

CNAME 을 쓰는 이유는 IP 를 한 곳에서만 관리하기 위해서입니다. 서버 IP 가 203.0.113.10 에서 203.0.113.50 으로 바뀐 경우를 예로 들면 다음과 같습니다.

www 레코드 설정 IP 가 바뀔 때 고칠 레코드
A 레코드로 IP 를 직접 적은 경우 example.com, www.example.com 두 개
CNAME 으로 example.com 에 연결한 경우 example.com 하나. www.example.com 은 따라서 바뀝니다

클라우드 배포 서비스가 “blog.example.com 을 CNAME 으로 myapp.host.example 에 연결하라”고 안내하는 것도 같은 원리입니다. myapp.host.example 의 A 레코드는 서비스 회사가 관리하므로, 서비스 쪽 IP 가 바뀌어도 내 DNS 의 레코드는 그대로 둡니다.

네임서버

섹션 제목: “네임서버”

네임서버(name server)는 도메인의 레코드를 저장해 두고, “이 도메인의 IP 는 무엇인가” 라는 질문에 답하는 DNS 서버입니다.

인터넷의 모든 도메인 정보를 서버 한 대가 가지고 있지는 않습니다. 도메인 구조처럼 계층으로 나뉘어, 각 네임서버는 자기가 맡은 범위만 알고 그 아래는 다음 네임서버에 맡깁니다. 이것을 위임(delegation)이라고 합니다.

네임서버 알고 있는 것
루트 네임서버 각 최상위 도메인(.com, .kr 등)을 맡은 네임서버의 주소
TLD 네임서버 (.com) .com 아래 각 도메인(example.com 등)을 맡은 네임서버의 주소
권한 있는 네임서버 (example.com) example.com 과 그 서브도메인의 실제 레코드

“권한 있는(authoritative)” 은 그 도메인의 레코드를 직접 가지고 있어서, 다른 곳에 묻지 않고 답할 수 있다는 뜻입니다.

도메인 등록과 네임서버

섹션 제목: “도메인 등록과 네임서버”

도메인을 등록하면 그 도메인의 권한 있는 네임서버를 지정합니다. 등록 업체가 기본으로 주는 네임서버를 쓰거나, Cloudflare, AWS Route 53 같은 DNS 서비스의 네임서버로 바꿀 수 있습니다. 지정한 네임서버는 TLD 네임서버에 NS 레코드로 등록됩니다.

이후 A, CNAME 같은 레코드는 지정한 네임서버의 관리 화면에서 추가하고 고칩니다. 네임서버를 두 대 이상 지정하는 것은, 한 대가 멈춰도 다른 한 대가 조회에 답할 수 있게 하기 위해서입니다.

리졸버와 네임서버

섹션 제목: “리졸버와 네임서버”

DNS 서버에는 답하는 쪽인 네임서버 말고, 대신 조회해 주는 쪽인 리졸버(resolver)도 있습니다.

리졸버 권한 있는 네임서버
하는 일 내 PC 대신 여러 네임서버에 차례로 물어 최종 IP 를 찾고, 결과를 캐시에 둡니다 자기가 맡은 도메인의 레코드로 답합니다
예 인터넷 업체의 DNS, 8.8.8.8(Google), 1.1.1.1(Cloudflare), 회사 내부 DNS 도메인에 지정한 DNS 서비스의 네임서버
PC 네트워크 설정의 “DNS 서버” 칸 여기에 적는 것이 리졸버입니다 적지 않습니다

조회 과정

섹션 제목: “조회 과정”

api.example.com 을 처음 조회할 때는 다음 순서로 진행됩니다.

  1. 내 PC 가 hosts 파일과 자기 캐시를 확인합니다. 결과가 있으면 조회를 마칩니다.
  2. 없으면 네트워크 설정에 적힌 리졸버에 묻습니다.
  3. 리졸버가 루트 네임서버에 묻고, .com 을 맡은 TLD 네임서버 주소를 받습니다.
  4. 리졸버가 TLD 네임서버에 묻고, example.com 의 권한 있는 네임서버 주소를 받습니다.
  5. 리졸버가 권한 있는 네임서버에 묻고, api.example.com 의 IP 203.0.113.20 을 받습니다.
  6. 리졸버가 결과를 캐시에 저장하고 내 PC 에 알려 줍니다.

캐시와 TTL

섹션 제목: “캐시와 TTL”

DNS 응답에는 TTL(Time To Live, 유효 시간)이 포함되어 있습니다. 리졸버와 PC 는 TTL 동안 결과를 캐시에 두고, 같은 도메인을 다시 물으면 3~5단계 없이 바로 답합니다.

그래서 레코드의 IP 를 바꿔도 바로 모든 사용자에게 반영되지 않습니다. 이전 값을 캐시에 둔 리졸버와 PC 는 TTL 이 지날 때까지 옛 IP 로 접속합니다. 서버를 옮기기 전에 TTL 을 짧게 줄여 두면, 바꾼 값이 더 빨리 반영됩니다.

hosts 파일

섹션 제목: “hosts 파일”

개발과 확인 작업을 하다 보면 도메인 이름으로 접속해야 하는데, DNS 에 레코드를 만들 수 없거나 아직 만들면 안 되는 경우가 있습니다. 이때 쓰는 것이 hosts 파일입니다.

hosts 파일은 PC 안에 도메인과 IP 의 짝을 직접 적어 두는 파일입니다. 위 조회 과정의 1단계처럼, PC 는 리졸버에 묻기 전에 이 파일을 먼저 확인합니다. 여기에 적힌 이름은 DNS 조회 없이 적어 둔 IP 로 바로 연결됩니다.

OS 위치
Windows C:\Windows\System32\drivers\etc\hosts (관리자 권한으로 편집)
Linux, mac /etc/hosts

한 줄에 IP 와 도메인을 하나씩 적습니다.

hosts 파일을 쓰는 상황

섹션 제목: “hosts 파일을 쓰는 상황”
상황 IP 로 접속할 수 없는 이유 적는 내용
한 서버의 여러 서비스를 이름으로 나눌 때 Nginx 는 server_name 으로 요청에 담긴 도메인 이름을 보고 server 설정 묶음을 고릅니다. IP 로 접속하면 어느 서비스로 보낼지 이름으로 나눌 수 없습니다 위 예시의 첫째·둘째 줄처럼, 같은 IP 에 서비스마다 다른 이름
HTTPS 인증서를 확인할 때 인증서는 도메인 이름을 기준으로 발급됩니다. IP 로 접속하면 인증서의 이름과 맞지 않아 브라우저가 경고합니다 인증서에 적힌 도메인과 개발 서버 IP
서버를 옮기기 전에 새 서버를 확인할 때 DNS 레코드를 바꾸면 모든 사용자가 새 서버로 접속하고, 문제가 생겨도 TTL 동안은 옛 값으로 되돌리기 어렵습니다 위 예시의 셋째 줄처럼, 운영 도메인과 새 서버 IP. 내 PC 에서만 새 서버로 접속합니다
아래 “내부 DNS” 가 없는 팀에서 서버에 이름을 붙일 때 IP 는 외우기 어렵고, 서버 IP 가 바뀌면 그 IP 를 적어 둔 설정을 모두 고쳐야 합니다 192.168.0.30 db.example.test 처럼 서버마다 이름

hosts 파일은 DNS 보다 먼저 적용되므로, 확인이 끝난 뒤 지우지 않으면 내 PC 만 계속 그 IP 로 접속합니다. “다른 사람은 정상인데 내 PC 만 옛 서버로 접속된다”면 hosts 파일을 먼저 확인합니다.

.test 는 테스트용으로 예약된 최상위 도메인이라, 인터넷의 실제 도메인과 겹치지 않습니다.

리졸버 설정

섹션 제목: “리졸버 설정”

조회 과정 2단계의 “네트워크 설정에 적힌 리졸버”는 PC 와 서버마다 따로 정합니다. 이 값이 비어 있으면 IP 로는 통신이 되는데 도메인 조회만 모두 실패합니다.

넣을 수 있는 리졸버

섹션 제목: “넣을 수 있는 리졸버”
종류 예 특징
공유기 192.168.0.1 많은 공유기가 리졸버 역할을 겸하고, 받은 질문을 통신사 DNS 로 넘깁니다
회사 내부 DNS 회사가 정한 내부 IP 인터넷 도메인과 함께 아래 “내부 DNS” 의 내부 이름까지 답합니다
통신사 DNS 통신사가 안내한 주소 인터넷에 연결할 때 자동으로 받는 경우가 많습니다
공용 DNS 8.8.8.8(Google), 1.1.1.1(Cloudflare) 어느 네트워크에서나 쓸 수 있습니다. 내부 이름은 모르고, 외부 DNS 를 막은 회사 네트워크에서는 응답하지 않습니다

리졸버는 보통 두 개 이상 적습니다. 첫 번째 리졸버가 응답하지 않으면 두 번째 리졸버로 조회를 이어 가기 때문입니다.

설정 파일의 nameserver

섹션 제목: “설정 파일의 nameserver”

설정 파일에서는 리졸버를 nameserver 라는 이름으로 적는 경우가 많습니다. 리눅스와 여러 도구가 “물어볼 DNS 서버”를 관례적으로 이렇게 불러 왔기 때문입니다. 설정 파일의 nameserver 는 위 “네임서버” 절의 권한 있는 네임서버가 아니라, 이 PC 나 서버가 물어볼 리졸버를 뜻합니다.

적는 곳 값의 예 뜻
서버의 /etc/resolv.conf 의 nameserver, netplan 의 nameservers 8.8.8.8 이 서버가 물어볼 리졸버
도메인의 NS 레코드 ns1.dns-provider.example. 이 도메인의 레코드를 가진 권한 있는 네임서버

리눅스 서버의 리졸버

섹션 제목: “리눅스 서버의 리졸버”

Ubuntu 같은 리눅스 서버에서는 서버 안에서 실행되는 systemd-resolved 라는 프로그램이 리졸버 역할을 합니다. 서버의 프로그램은 이 프로그램에 묻고, systemd-resolved 는 위 표의 공유기나 8.8.8.8 처럼 서버 밖에 있는 리졸버에 다시 묻습니다. 아래에서는 서버 안의 systemd-resolved 와 구분해 이 리졸버를 바깥 리졸버라고 부릅니다.

바깥 리졸버의 주소는 systemd-resolved 가 스스로 정하지 않고, 네트워크 설정을 거쳐 전달받습니다. 이 설정에는 netplan 과 렌더러가 관여합니다.

이름 하는 일
netplan Ubuntu 에서 IP, 게이트웨이, 리졸버 같은 네트워크 설정을 적는 YAML 파일(/etc/netplan/*.yaml)과, 그 파일을 렌더러에 넘겨주는 도구입니다. 직접 네트워크 카드를 설정하지는 않습니다
렌더러(renderer) netplan 의 설정을 받아 실제로 네트워크 카드에 IP 와 게이트웨이를 설정하고, 리졸버 목록을 systemd-resolved 에 전달하는 프로그램입니다. netplan 파일의 renderer: 항목으로 정합니다

렌더러는 두 가지가 있고, 하는 일은 같습니다.

렌더러 기본으로 쓰는 곳 특징
networkd (systemd-networkd) Ubuntu Server 설정 파일만 읽고 적용합니다. 설정이 잘 바뀌지 않는 서버에 맞습니다
NetworkManager Ubuntu Desktop Wi-Fi 선택, VPN 연결, 화면의 네트워크 메뉴, nmcli 명령처럼 연결을 수시로 바꾸는 기능이 있습니다

두 렌더러는 설정 형식이 서로 다릅니다. netplan 은 사용자가 그 차이를 몰라도 되도록, 한 가지 YAML 형식으로 적으면 정한 렌더러의 형식으로 바꿔 넘겨줍니다. 렌더러가 어느 쪽이든 리졸버 역할은 systemd-resolved 가 그대로 맡습니다.

설정은 다음 순서로 전달됩니다.

순서 위치 하는 일
1 netplan 설정 파일 nameservers 아래에 바깥 리졸버를 적어 둡니다
2 netplan apply 파일 내용을 렌더러의 설정 형식으로 바꿔 넘깁니다
3 렌더러 (networkd 또는 NetworkManager) 네트워크 카드에 설정을 적용하고, 바깥 리졸버 목록을 systemd-resolved 에 전달합니다
4 systemd-resolved 전달받은 바깥 리졸버 목록을 가지고 조회를 넘깁니다
5 /etc/resolv.conf nameserver 127.0.0.53 이 적혀 있습니다. 127.0.0.53 은 서버 자신 안의 systemd-resolved 를 가리키고, 서버의 프로그램은 이 주소로 묻습니다
항목 뜻 비어 있을 때
renderer 설정을 적용할 렌더러 기본값 networkd 를 씁니다
addresses (맨 위) 이 서버의 IP. /24 는 앞 세 자리 192.168.0 이 같은 주소를 같은 대역으로 본다는 뜻입니다 네트워크에 연결되지 않습니다
routes 의 to: default 와 via 두 줄이 규칙 하나입니다. to: default 는 따로 경로를 정하지 않은 나머지 목적지 전부(인터넷과 다른 대역)이고, via 는 그 패킷을 넘겨줄 게이트웨이(같은 대역 안의 공유기나 라우터 주소)입니다. 예시는 “나머지 목적지로 가는 패킷은 전부 192.168.0.1 에게 넘긴다”는 뜻입니다 같은 대역 밖으로 나가지 못해 IP 로도 인터넷에 도달하지 않습니다
nameservers 의 addresses 도메인을 물어볼 리졸버 IP 로는 통신이 되고 도메인 조회만 실패합니다

예시에서 via 와 nameservers 에 같은 192.168.0.1 이 들어간 것은 공유기 한 대가 게이트웨이와 리졸버 역할을 함께 하기 때문입니다.

설정 파일에 리졸버가 적혀 있어도, 적용되지 않았으면 systemd-resolved 의 목록은 비어 있습니다. 실제로 쓰는 값은 resolvectl status 로 확인합니다.

이 명령의 출력이 비어 있으면 systemd-resolved 가 질문을 넘길 곳이 없어 모든 도메인 조회가 실패합니다. 설정 파일의 nameservers 를 확인하고 sudo netplan apply 로 다시 적용한 뒤, 같은 명령으로 목록이 채워졌는지 확인합니다. netplan apply 는 네트워크를 다시 적용하므로 SSH 접속이 잠깐 끊길 수 있습니다.

다시 적용해도 목록이 비어 있으면, 설정을 받은 렌더러와 실제로 네트워크 카드를 관리하는 렌더러가 다른 경우입니다. 예를 들어 netplan 은 renderer: networkd 로 설정을 넘기는데 카드는 NetworkManager 가 관리하고 있으면, networkd 가 받은 리졸버 목록은 그 카드에 적용되지 않습니다. nmcli device status 에서 카드가 connected 이면 NetworkManager 가, unmanaged 이면 networkd 가 관리하는 것입니다. NetworkManager 가 설치되지 않은 서버에는 이 명령이 없고, networkd 가 관리합니다. 리졸버 설정은 실제로 카드를 관리하는 렌더러 쪽에 적습니다.

위 설정은 직접 설치한 서버처럼 사람이 고정 IP 를 직접 적는 서버에 해당합니다. 클라우드에서 만든 서버는 IP 와 리졸버를 자동으로 받으므로, 보통 netplan 을 직접 고치지 않습니다.

항목 직접 설치한 서버 클라우드 서버 (AWS, GCP, Azure 등)
IP, 게이트웨이, 리졸버 설치할 때 사람이 적습니다 서버가 시작될 때 DHCP(네트워크에 연결된 기기에 IP, 게이트웨이, 리졸버를 자동으로 할당하는 방식)로 받습니다
netplan 파일 설치 프로그램이 만들거나 사람이 적습니다 cloud-init(클라우드 서버가 처음 시작될 때 네트워크, 계정, SSH 키를 설정하는 프로그램)이 만듭니다
리졸버를 바꾸는 곳 netplan 파일 클라우드 콘솔의 네트워크(VPC) 설정. cloud-init 이 만든 파일은 다시 만들어질 수 있어, 직접 고친 내용이 사라질 수 있습니다

어느 쪽이든 resolvectl status 로 리졸버를 확인하는 방법과, 아래 “Docker 네트워크의 이름 조회” 에서 볼 컨테이너의 리졸버 동작은 같습니다.

Windows PC 는 ipconfig /all 의 “DNS 서버” 항목에서 쓰고 있는 리졸버를 확인합니다.

내부 DNS

섹션 제목: “내부 DNS”

회사는 내부 네트워크 안에서만 쓰는 DNS 서버를 두기도 합니다. 내부 DNS 에는 db.corp.example.test → 192.168.0.30 처럼 내부 서버의 이름이 들어 있고, 인터넷에서는 이 이름을 조회할 수 없습니다.

상황 내부 이름 조회
사무실 내부 네트워크 조회됩니다. 네트워크 설정이 내부 DNS 를 리졸버로 씁니다
집에서 VPN 접속 VPN 이 내부 DNS 를 리졸버로 지정해 주면 조회됩니다
집에서 VPN 없이 조회되지 않습니다. 인터넷의 리졸버는 내부 이름을 모릅니다

VPN 에 접속했는데 IP 로는 접속되고 내부 이름으로는 접속되지 않는다면, VPN 이 DNS 설정을 넘겨주지 않은 경우입니다. ipconfig /all 에서 VPN 어댑터의 DNS 서버 항목을 확인합니다.

Docker 네트워크의 이름 조회

섹션 제목: “Docker 네트워크의 이름 조회”

IP 주소와 포트에서 같은 도커 네트워크의 컨테이너는 api:8000 처럼 이름으로 접속할 수 있다고 했습니다. 이것도 DNS 입니다. Docker 는 사용자가 만든 네트워크마다 내장 DNS 서버(127.0.0.11)를 두고, 컨테이너 이름을 그 컨테이너의 IP 로 알려 줍니다.

기본 bridge 네트워크에는 이 이름 조회가 없어서, docker network create 로 만든 네트워크에서만 컨테이너 이름으로 접속할 수 있습니다.

컨테이너 이름이 아닌 인터넷 도메인은 서버의 리졸버 설정을 따릅니다. 컨테이너 안에서는 서버의 127.0.0.53 에 접근할 수 없으므로, Docker 는 위 “리눅스 서버의 리졸버” 에서 systemd-resolved 가 쓰는 바깥 리졸버 목록을 가져와 씁니다.

서버의 리졸버 설정 컨테이너가 쓰는 리졸버
systemd-resolved 에 바깥 리졸버가 있음 그 리졸버
바깥 리졸버가 비어 있음 Docker 의 기본값 8.8.8.8, 8.8.4.4

그래서 서버의 리졸버 설정이 비어 있으면 docker pull 이 이미지 저장소의 도메인을 조회하지 못하고, 빌드 중 RUN apt-get 같은 단계는 8.8.8.8 로 묻게 됩니다. 외부 DNS 를 막은 회사 네트워크에서는 이 단계도 실패합니다. 이때는 서버의 리졸버 설정을 먼저 채우고, 컨테이너에 특정 리졸버를 지정해야 하면 docker run --dns 192.168.0.1 이나 Docker 설정 파일(/etc/docker/daemon.json)의 "dns" 항목을 씁니다.

조회 결과 확인

섹션 제목: “조회 결과 확인”
줄 뜻
Server 이번 조회에 쓴 리졸버
Non-authoritative answer 권한 있는 네임서버가 아니라 리졸버가 캐시나 대신 조회한 결과로 답했다는 뜻
Address 조회된 IP

CNAME 이 설정된 도메인을 dig +short 로 조회하면 CNAME 의 값과 마지막 IP 가 차례로 출력됩니다. 위 “CNAME” 에서 본 두 번의 조회를 결과로 확인할 수 있습니다.

nslookup 과 dig 는 DNS 서버에 직접 묻기 때문에 hosts 파일을 확인하지 않습니다. hosts 파일에 적은 값이 nslookup 에 표시되지 않는 것은 정상입니다. hosts 파일까지 반영한 결과는 ping 이 표시하는 IP 로 확인합니다.

내 PC 의 DNS 캐시는 다음 명령으로 지웁니다.

도메인 접속 문제 확인 순서

섹션 제목: “도메인 접속 문제 확인 순서”
증상 확인할 것
브라우저에 DNS_PROBE_FINISHED_NXDOMAIN 그 이름의 레코드가 없습니다. 도메인 오타, 레코드 등록 여부를 nslookup 으로 확인
IP 로는 접속되는데 도메인으로는 접속되지 않음 DNS 문제입니다. nslookup 결과가 그 IP 인지 확인
서버에서 모든 도메인 조회가 실패함 (docker pull 실패, Temporary failure in name resolution) ping 8.8.8.8 이 성공하고 dig 도메인 @8.8.8.8 도 성공하면, 인터넷 연결은 정상이고 서버의 리졸버 설정이 빠진 것입니다. resolvectl status 의 DNS 서버 목록을 확인
레코드를 바꿨는데 옛 서버로 접속됨 TTL 동안의 캐시입니다. dig @8.8.8.8 로 새 값이 반영됐는지 확인하고, 내 PC 캐시를 지웁니다
내 PC 만 다른 서버로 접속됨 hosts 파일에 그 도메인이 적혀 있는지 확인
VPN 접속 후 내부 이름이 조회되지 않음 VPN 어댑터의 DNS 서버 설정 확인
