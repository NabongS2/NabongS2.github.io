Nginx, HTTPS부터 WebSocket 프록시까지

2026년 10월 1일 · 읽는 데 9분
nabong

시리즈Nginx

  1. Nginx, 정적 파일부터 API 프록시까지
  2. Nginx, HTTPS부터 WebSocket 프록시까지

앞 글에서 화면 파일을 내보내고 /api 를 백엔드로 넘기는 최소 설정을 만들었습니다. 이 글은 그 설정을 서버에 올릴 때 더하는 것들입니다. 설정 파일에 있는 줄마다 왜 있는지를 목적별로 나눠 봅니다.

HTTPS

섹션 제목: “HTTPS”
줄 하는 일
listen 443 ssl 443 포트에서 HTTPS 로 받습니다
ssl_certificate 인증서. 브라우저에 보여주는 공개 파일
ssl_certificate_key 인증서의 비밀키. 밖으로 나가면 안 되는 파일
ssl_protocols 쓸 TLS 버전. 오래된 1.0·1.1 을 빼고 1.2·1.3 만 엽니다

ssl_certificate 에는 서버 인증서만이 아니라 인증 기관이 준 중간 인증서까지 이어 붙인 파일(fullchain)을 넣습니다. 서버 인증서만 넣으면 브라우저에서는 열리는데, 다른 서버나 앱이 이 주소를 호출할 때 인증서 오류가 나는 경우가 있습니다. 브라우저는 빠진 중간 인증서를 스스로 찾아오지만 다른 클라이언트는 대개 그러지 않기 때문입니다.

컨테이너로 띄운다면 인증서 폴더를 볼륨으로 연결하고 443 포트를 엽니다. 비밀키는 읽기 전용(:ro)으로 둡니다.

사내 개발 서버에서 직접 만든 인증서(자체 서명 인증서)를 쓰면 암호화는 되지만, 브라우저는 믿을 수 있는 기관이 발급한 게 아니라며 경고를 띄웁니다.

이때 HSTS 는 켜지 않습니다. HSTS 는 Strict-Transport-Security 응답 헤더로 “이 주소는 앞으로 https 로만 열라” 고 브라우저에 알려 두는 설정입니다. 이 헤더를 받은 브라우저는 인증서 경고 화면에서 그대로 진행하는 버튼을 없앱니다. 자체 서명 인증서는 경고가 늘 뜨기 때문에, HSTS 를 켜면 그 주소로 아예 들어갈 수 없게 됩니다.

http 로 들어온 요청

섹션 제목: “http 로 들어온 요청”

주소창에 http:// 로 들어오는 사람도 있습니다. 두 경우가 있습니다.

80 과 443 을 따로 열었을 때는 80 쪽 server 가 https 주소로 보내기만 합니다.

한 포트만 HTTPS 로 열었을 때, 그 포트로 http:// 요청이 오면 Nginx 는 “The plain HTTP request was sent to HTTPS port” 라는 400 오류 화면을 돌려줍니다. Nginx 안에서는 이 경우를 497 이라는 코드로 구분해서, 이 코드를 https 주소로 보내게 바꿀 수 있습니다.

$http_host 는 브라우저가 보낸 호스트와 포트 그대로라, :8443 같은 포트가 붙은 주소도 유지됩니다.

http 설정과 달라지는 줄

섹션 제목: “http 설정과 달라지는 줄”

http 로 쓰던 설정을 https 로 바꿀 때 고치는 곳은 많지 않습니다.

http https
listen listen 8080; listen 8080 ssl;
인증서 없음 ssl_certificate, ssl_certificate_key, ssl_protocols
http 로 들어온 요청 해당 없음 80 → 443 return 301, 또는 같은 포트면 error_page 497
X-Forwarded-Proto 백엔드에 http 가 넘어감 백엔드에 https 가 넘어감
컨테이너 실행 포트와 dist·설정 파일 볼륨 인증서 폴더 볼륨을 더함
캐시, 압축, location 그대로 그대로

X-Forwarded-Proto 는 앞 글의 프록시 헤더에 이미 들어 있어서 줄을 고칠 필요는 없고, 값만 https 로 바뀝니다. 백엔드는 Nginx 와 http 로 통신하기 때문에, 이 헤더가 없으면 브라우저가 https 로 들어왔다는 걸 알 수 없습니다. 그러면 백엔드가 만드는 리다이렉트 주소가 http:// 로 나가거나, https 에서만 보내는 쿠키(Secure)를 다루지 못합니다. 백엔드도 이 헤더를 읽도록 설정돼 있어야 합니다. Spring Boot 는 server.forward-headers-strategy 로 정합니다.

캐시

섹션 제목: “캐시”

브라우저는 한 번 받은 파일을 저장해 두고 다음에 다시 받지 않을 수 있습니다. 얼마나 오래 저장할지는 서버가 Cache-Control 헤더로 알려 줍니다. 화면 파일은 두 종류를 다르게 다룹니다.

파일 설정 이유
/assets/ 아래 JS·CSS 1년 저장, 다시 묻지 않음 빌드할 때마다 파일 이름이 바뀝니다. 이름이 같으면 내용도 같습니다
index.html 저장은 하되 쓸 때마다 바뀌었는지 서버에 확인 이름이 늘 같습니다. 새로 배포한 JS·CSS 의 이름이 이 안에 적혀 있습니다

앞 글에서 본 것처럼 빌드하면 index-3f9a1c2e.js 같은 이름이 나오고, 코드를 고치면 이름이 바뀝니다. 그래서 assets/ 파일은 오래 저장해도 옛 파일을 쓸 일이 없습니다. 새 버전은 새 이름으로 받기 때문입니다.

문제는 index.html 입니다. 이 파일이 옛 것으로 저장돼 있으면 옛 JS 이름을 가리키고, 배포했는데 화면이 안 바뀌는 일이 생깁니다. 그래서 index.html 은 매번 서버에 확인합니다.

no-cache 는 “저장하지 말라” 가 아니라 “쓰기 전에 확인하라” 입니다. 바뀌지 않았으면 서버가 304 로 짧게 답하고 브라우저는 저장해 둔 것을 씁니다. 아예 저장하지 않게 하는 건 no-store 이고, 이쪽은 매번 전체를 다시 받습니다.

/assets/ 를 따로 떼어 둔 이유가 하나 더 있습니다. 이 블록이 없으면 없는 JS 파일 요청도 location / 의 try_files 를 타서 index.html 이 돌아옵니다. 브라우저는 HTML 을 JS 로 읽으려다 알아보기 어려운 오류를 냅니다. try_files $uri =404 로 없는 파일은 404 를 돌려주게 합니다.

location 안에 add_header 를 하나라도 적으면, 바깥 server 에 적은 add_header 는 그 location 에 적용되지 않습니다. 보안 헤더 같은 걸 server 에 두었다면 이 점을 같이 봅니다.

압축

섹션 제목: “압축”

JS·CSS 같은 텍스트 파일은 gzip 으로 줄여 보내면 크기가 크게 줄어듭니다. 브라우저는 요청에 Accept-Encoding: gzip 을 붙여 압축을 받을 수 있다고 알리고, Nginx 는 압축해서 돌려줍니다.

줄 하는 일
gzip on 압축을 켭니다
gzip_types 압축할 파일 종류. text/html 은 적지 않아도 늘 들어갑니다
gzip_min_length 이보다 작은 응답은 압축하지 않습니다. 작은 파일은 줄어드는 양보다 압축하는 비용이 큽니다
gzip_vary 응답에 Vary: Accept-Encoding 을 붙입니다

PNG·JPG 는 이미 압축된 형식이라 gzip_types 에 넣지 않습니다. 다시 압축해도 거의 줄지 않습니다.

gzip_vary 는 Nginx 앞에 캐시하는 프록시나 CDN 이 있을 때 필요합니다. 같은 주소에 압축본과 원본이 따로 있다는 걸 알려서, 압축을 못 받는 클라이언트에 압축본이 가지 않게 합니다.

Nginx 앞에 로드 밸런서 같은 프록시가 하나 더 있으면, Nginx 는 기본적으로 그 요청은 압축하지 않습니다. 이때는 gzip_proxied any; 를 더합니다.

압축이 되는지는 응답 헤더로 확인합니다.

gzip_comp_level 로 압축 정도를 1~9 로 정할 수 있습니다. 기본값은 1 입니다. 높이면 조금 더 작아지는 대신 CPU 를 더 씁니다.

WebSocket

섹션 제목: “WebSocket”

WebSocket 은 연결을 한 번 맺어 두고 서버와 브라우저가 계속 메시지를 주고받는 방식입니다. 실시간 알림이나 모니터링 화면에 씁니다. 앞 글의 /api 설정만으로는 연결되지 않고, 줄이 몇 개 더 필요합니다.

WebSocket 은 처음에 평범한 HTTP 요청으로 시작해서, Upgrade: websocket 헤더로 “이 연결을 WebSocket 으로 바꾸자” 고 요청합니다. 그런데 Nginx 는 기본적으로 백엔드와 HTTP/1.0 으로 통신하고, Upgrade 와 Connection 헤더는 백엔드로 넘기지 않습니다. 그래서 백엔드는 바꾸자는 요청을 받지 못하고 연결이 실패합니다.

줄 하는 일
proxy_http_version 1.1 백엔드와 HTTP/1.1 로 통신합니다. 연결 전환은 1.1 에서만 됩니다
Upgrade, Connection 헤더 브라우저의 전환 요청을 백엔드에 그대로 전합니다
proxy_read_timeout 주고받는 게 없어도 이 시간까지는 연결을 유지합니다

proxy_read_timeout 의 기본값은 60초입니다. WebSocket 은 한동안 조용할 수 있어서, 60초 동안 아무 메시지도 없으면 Nginx 가 연결을 끊습니다. 이 값을 길게 두거나, 클라이언트와 서버가 주기적으로 짧은 신호(heartbeat)를 주고받게 합니다. 값을 길게 두면 끊긴 연결을 늦게 정리하는 대신 조용한 연결이 끊기지 않습니다.

로컬 개발에서도 같습니다. Vite 설정의 proxy 에 WebSocket 경로를 넘길 때는 ws: true 를 붙여야 합니다. 앞 글에서 말한 대로 경로 규칙은 두 곳에 같이 적어야 합니다.

SSE

섹션 제목: “SSE”

SSE(Server-Sent Events)는 서버가 브라우저로만 이벤트를 계속 내려보내는 방식입니다. WebSocket 과 달리 평범한 HTTP 응답 하나가 끝나지 않고 이어지는 형태라, 연결 전환 헤더는 필요 없습니다. 대신 다른 줄이 필요합니다.

줄 하는 일
proxy_buffering off 백엔드 응답을 모으지 않고 바로 브라우저로 넘깁니다
proxy_http_version 1.1, Connection "" 백엔드와의 연결을 응답 하나로 닫지 않고 유지합니다
proxy_read_timeout 이벤트가 한동안 없어도 연결을 끊지 않습니다

Nginx 는 기본적으로 백엔드 응답을 버퍼에 모았다가 보냅니다. 보통 응답은 이게 효율적이지만, SSE 는 이벤트가 버퍼에 쌓이기만 하고 브라우저에는 한참 뒤에 한꺼번에 도착합니다. 그래서 proxy_buffering off 로 끕니다. 백엔드가 응답에 X-Accel-Buffering: no 헤더를 붙여도 그 응답만 버퍼링을 끌 수 있습니다.

같은 이유로 gzip_types 에 text/event-stream 은 넣지 않습니다. 압축하려고 모으는 동안 이벤트가 늦게 도착합니다.

타임아웃

섹션 제목: “타임아웃”

백엔드로 넘긴 요청을 Nginx 가 얼마나 기다릴지는 세 가지로 나뉩니다.

지시어 기다리는 것 기본값
proxy_connect_timeout 백엔드와 연결을 맺기까지 60초
proxy_send_timeout 백엔드로 요청을 보내는 동안, 한 번 보내고 다음을 보내기까지 60초
proxy_read_timeout 백엔드 응답을 읽는 동안, 한 번 받고 다음을 받기까지 60초

셋 다 전체 시간이 아니라 두 동작 사이의 간격입니다. 응답이 조금씩이라도 계속 오면 60초가 넘어도 끊기지 않습니다.

앞 글의 504 Gateway Timeout 이 proxy_read_timeout 에 걸린 경우입니다. 큰 파일을 만들어 내려주는 API 처럼 오래 걸리는 게 있다면 그 location 만 늘릴 수 있습니다. 전체를 늘리면 백엔드가 멈췄을 때 요청이 그만큼 오래 붙잡혀 있습니다.

파일 업로드가 있다면 client_max_body_size 도 봅니다. 요청 본문의 최대 크기이고 기본값이 1MB 라, 그보다 큰 파일을 올리면 백엔드에 닿기 전에 Nginx 가 413 Request Entity Too Large 를 돌려줍니다.

nginx.conf 와 conf.d

섹션 제목: “nginx.conf 와 conf.d”

공식 이미지에는 설정 파일이 두 층으로 있습니다.

파일 담는 것
/etc/nginx/nginx.conf Nginx 전체에 한 번만 적는 설정. 프로세스 수, 로그 형식과 위치, 아래 폴더를 불러오는 줄
/etc/nginx/conf.d/default.conf 사이트 하나의 설정. server 블록과 그 안의 listen, 인증서, root, location

nginx.conf

섹션 제목: “nginx.conf”

Nginx 가 켜질 때 가장 먼저 읽는 파일입니다. 공식 이미지에 들어 있는 내용을 줄이면 이렇습니다.

http 블록 끝의 include 가 conf.d/ 의 파일을 그 자리에 불러옵니다. 그래서 default.conf 의 server 블록은 이 http 블록 안에 적은 것과 같습니다.

파일 이름

섹션 제목: “파일 이름”

두 파일의 이름이 정해진 정도는 다릅니다.

파일 이름
nginx.conf 정해져 있습니다. Nginx 는 /etc/nginx/nginx.conf 를 읽도록 만들어져 있습니다
default.conf 정해져 있지 않습니다. include 가 conf.d/*.conf 라서 .conf 로 끝나면 이름과 관계없이 모두 읽습니다

default.conf 는 공식 이미지가 넣어 둔 파일의 이름일 뿐입니다. 이 파일에는 80 포트로 Nginx 기본 환영 화면을 보여주는 server 블록이 들어 있습니다.

그래서 내 설정을 다른 이름(app.conf 같은)으로 연결하면, 원래 있던 default.conf 도 같이 읽힙니다. 두 server 블록이 같은 포트를 쓰면 요청이 원하지 않는 쪽으로 갈 수 있습니다. 내 설정을 default.conf 자리에 그대로 덮어 연결하면 이 문제가 없습니다.

저장소에서는 환경별로 nginx.dev.conf, default.prod.conf 처럼 이름을 나눠 두고, 컨테이너에 연결할 때 정해진 경로로 맞추는 경우가 많습니다.

Nginx 가 보는 건 컨테이너 안의 경로이므로, 밖의 파일 이름은 무엇이든 됩니다.

어느 파일에 적을지

섹션 제목: “어느 파일에 적을지”

이 글과 앞 글의 설정은 모두 default.conf 에 적을 수 있습니다. gzip, client_max_body_size 도 server 블록 안에 적으면 됩니다. 앱 하나를 띄우는 경우 default.conf 만 고치고, nginx.conf 는 로그 형식이나 위치를 바꿀 때 연결합니다.

두 파일에 같은 지시어를 적을 때는 주의할 점이 있습니다. 안쪽 블록에 같은 지시어가 있으면 바깥 값은 통째로 무시됩니다. 일부만 덮어쓰는 게 아닙니다.

경로가 같아서 같은 설정처럼 보이지만, server 블록에는 main 형식이 적용되지 않습니다. 생략한 값은 바깥에서 물려받지 않고 기본값으로 돌아갑니다. 캐시에서 본 add_header 도 같은 규칙입니다. 그래서 로그 설정은 nginx.conf 한 곳에만 적습니다.

어느 파일을 고쳤든 반영은 앞 글과 같이 nginx -t 로 검사한 뒤 nginx -s reload 입니다.
