Nginx 로그 설정과 관리

2026년 10월 8일 · 읽는 데 6분
nabong

시리즈Nginx

  1. Nginx, 정적 파일부터 API 프록시까지
  2. Nginx, HTTPS부터 WebSocket 프록시까지
  3. Nginx 로그 설정과 관리

앞 글에서 로그 설정은 nginx.conf 한 곳에만 적는다고 했습니다. 이 글은 그 로그 설정입니다. Nginx 가 어떤 로그를 남기는지, 한 줄을 어떻게 읽는지, 남길 것을 어떻게 고르고 어디에 남기는지를 봅니다.

access 로그와 error 로그

섹션 제목: “access 로그와 error 로그”

Nginx 의 로그는 두 가지입니다.

로그 남기는 것 지시어
access 로그 들어온 요청 하나마다 한 줄. 누가, 언제, 어떤 주소를, 어떤 결과로 access_log, log_format
error 로그 Nginx 가 처리하다 생긴 문제. 백엔드 연결 실패, 설정 오류, 없는 파일 error_log

화면에 502 나 504 가 떴을 때 access 로그에는 502 라는 결과만 남고, 왜 그랬는지는 error 로그에 남습니다. 둘을 같이 봅니다.

access 로그 형식

섹션 제목: “access 로그 형식”

log_format 은 access 로그 한 줄에 무엇을 어떤 순서로 적을지 정하고, 그 모양에 이름을 붙입니다. 이름은 아무렇게나 지어도 됩니다. 공식 이미지의 nginx.conf 에는 main 이라는 이름으로 하나가 들어 있습니다.

access_log 는 경로 다음에 이 이름을 적어서, 그 파일에 어떤 모양으로 남길지 고릅니다. 이름을 적지 않으면 Nginx 에 미리 들어 있는 combined 모양으로 남습니다. combined 는 main 에서 마지막 $http_x_forwarded_for 만 빠진 모양입니다.

한 줄 읽기

섹션 제목: “한 줄 읽기”

main 모양으로 남은 한 줄입니다.

칸 변수 이 줄의 값
보낸 곳의 IP $remote_addr 192.168.0.15
인증 사용자 $remote_user - (없음)
시각 $time_local 01/Oct/2026:14:03:21 +0900
요청 $request GET /api/history/12 HTTP/1.1
상태 코드 $status 200
보낸 본문 크기 $body_bytes_sent 532 바이트
이전 페이지 $http_referer https://app.example.com/history
브라우저 정보 $http_user_agent Mozilla/5.0 ...
원래 클라이언트 IP $http_x_forwarded_for - (앞에 다른 프록시가 없음)

값이 없는 칸은 - 로 남습니다.

Nginx 앞에 로드 밸런서 같은 프록시가 하나 더 있으면 $remote_addr 는 그 프록시의 IP 가 됩니다. 이때 실제 브라우저 IP 는 프록시가 붙여 준 X-Forwarded-For 헤더, 즉 마지막 칸에 남습니다.

상태 코드로 찾기

섹션 제목: “상태 코드로 찾기”

main 모양에서는 공백으로 나눴을 때 9번째 칸이 상태 코드입니다. awk 로 원하는 줄만 볼 수 있습니다.

응답 시간 남기기

섹션 제목: “응답 시간 남기기”

main 모양에는 요청이 얼마나 걸렸는지가 없습니다. 느린 API 를 찾으려면 시간 변수를 넣은 모양을 하나 더 정의하고 이름을 붙입니다. 아래는 with_time 이라는 이름을 붙인 예입니다.

변수 재는 것
$request_time Nginx 가 요청을 받기 시작해서 응답을 다 보낼 때까지. 초 단위, 소수점 셋째 자리까지
$upstream_response_time 그중 백엔드가 응답하는 데 걸린 시간. 백엔드로 넘기지 않은 요청은 -

두 값이 비슷하면 시간은 백엔드에서 쓰인 것입니다. rt 만 크면 브라우저와 주고받는 데 시간이 쓰인 것으로, 네트워크가 느렸거나 올리고 내려받는 파일이 컸던 경우입니다. 앞 글의 504 가 났다면 urt 가 proxy_read_timeout 근처에 찍힙니다.

error 로그

섹션 제목: “error 로그”

마지막 칸은 남길 수준입니다. 적은 수준과 그보다 심각한 것이 남습니다.

수준 남는 것
debug, info 처리 과정의 자세한 기록. 평소에는 쓰지 않습니다
notice 시작, 종료, 설정 다시 읽기 같은 알림. 공식 이미지의 값
warn 동작은 하지만 확인할 만한 것
error 요청 하나를 처리하지 못한 것. 수준을 적지 않으면 이 값
crit, alert, emerg Nginx 자체가 제대로 돌지 못하는 것

자주 보는 메시지는 앞 글들의 오류 코드와 이어집니다.

메시지 일부 화면에 보인 것 뜻
connect() failed (111: Connection refused) while connecting to upstream 502 백엔드 주소로 연결했지만 그 포트에 받는 쪽이 없습니다. 백엔드가 꺼졌거나 주소가 틀렸습니다
upstream timed out (110: Connection timed out) while reading response header from upstream 504 백엔드가 proxy_read_timeout 안에 응답하지 않았습니다
client intended to send too large body 413 요청 본문이 client_max_body_size 보다 큽니다

메시지 끝에는 client:, request:, upstream: 이 함께 남아서, 어느 요청이 어느 백엔드 주소로 가다 실패했는지까지 볼 수 있습니다.

access 로그와 함께 읽기

섹션 제목: “access 로그와 함께 읽기”

화면에서 목록이 안 뜨고 개발자 도구에 502 가 보였다고 해 봅니다. 같은 시각의 두 로그는 이렇게 남습니다.

access 로그에서는 /api/history/12 요청이 502 로 끝났다는 것까지만 알 수 있습니다. 같은 시각, 같은 request 를 error 로그에서 찾으면 이유가 나옵니다.

error 로그의 칸 값 알 수 있는 것
시각과 수준 2026/10/01 14:05:02 [error] access 로그와 같은 시각의 오류
메시지 connect() failed (111: Connection refused) 백엔드에 연결하지 못했습니다
client, request 192.168.0.15, GET /api/history/12 access 로그의 그 요청입니다
upstream http://192.168.0.20:8100/api/history/12 Nginx 가 연결하려던 백엔드 주소입니다

다음으로 볼 곳은 upstream 에 적힌 주소입니다. 그 서버의 8100 포트에 백엔드가 떠 있는지(docker ps), 설정의 주소가 맞는지를 확인합니다.

남기지 않을 요청

섹션 제목: “남기지 않을 요청”

access 로그는 요청마다 한 줄이라, 화면 하나를 열 때 JS·CSS·이미지 요청까지 모두 남습니다. 필요 없는 줄을 거르는 방법이 둘 있습니다.

경로로 끄기

섹션 제목: “경로로 끄기”

정적 파일은 access_log off 로 그 location 만 끕니다.

조건으로 거르기

섹션 제목: “조건으로 거르기”

access_log 에 if= 를 붙이면 조건 값이 0 이거나 비어 있는 요청은 남지 않습니다. 조건 값은 http 블록의 map 으로 만듭니다. 아래는 성공한 GET 은 버리고, GET 이 아닌 요청과 오류만 남기는 예입니다.

요청 $log_method:$log_status 남는지
성공한 GET 0:0 남지 않음
실패한 GET (404, 502) 0:1 남음
POST, PUT, DELETE 1:0, 1:1 남음

map 은 왼쪽 값을 보고 오른쪽 값을 정하는 표입니다. ~ 로 시작하면 정규식으로 비교합니다. 로그를 거르면 파일은 작아지지만, 성공한 요청의 흐름은 볼 수 없게 됩니다. 어느 쪽이 필요한지는 환경마다 다릅니다.

꺼 두면 보이지 않는 것

섹션 제목: “꺼 두면 보이지 않는 것”

/assets/ 를 access_log off 로 끄면 그 경로의 오류도 함께 사라집니다.

앞 글의 캐시 상황을 떠올려 봅니다. 배포하면서 옛 JS 파일을 지웠는데, 브라우저에 옛 index.html 이 남아 있으면 그 안에 적힌 옛 JS 를 요청합니다. 이 요청은 try_files $uri =404 로 404 가 됩니다. 그런데 access 로그는 꺼져 있고, =404 로 돌려준 404 는 error 로그에도 남지 않습니다. 화면은 깨졌는데 로그에는 아무 흔적이 없습니다.

정적 파일 로그를 줄이면서 이런 오류는 남기려면, 끄는 대신 위의 $log_status 를 조건으로 씁니다.

location 안에 access_log 를 적으면 바깥의 access_log 는 통째로 무시되므로, 경로와 모양 이름까지 다시 적습니다.

컨테이너에서 로그가 가는 곳

섹션 제목: “컨테이너에서 로그가 가는 곳”

공식 이미지에서 /var/log/nginx/access.log 와 error.log 는 실제 파일이 아닙니다. 각각 표준 출력과 표준 에러로 연결돼 있습니다.

그래서 기본 상태에서는 docker logs 로 봅니다.

이 로그는 도커의 로그 드라이버가 받아서 저장합니다. 컨테이너를 --log-driver none 으로 띄우면 docker logs 에는 아무것도 남지 않습니다. 이때는 Nginx 가 파일에 직접 쓰게 하고, 그 폴더를 호스트에 연결합니다.

/var/log/nginx 에 호스트 폴더를 연결하면 이미지 안의 연결 파일이 가려지고, Nginx 는 같은 이름의 실제 파일을 만들어 씁니다. 로그는 호스트의 /opt/web/log/access.log 에 쌓입니다. nginx.conf 에서 경로를 다른 곳으로 바꿨다면 그 폴더를 연결합니다.

로그 위치 확인

섹션 제목: “로그 위치 확인”

남이 만든 서버에서 로그가 어디에 쌓이는지 모를 때는 두 단계로 찾습니다. 먼저 nginx -T 로 지금 적용된 설정 전체를 출력해서 로그 줄만 뽑습니다. nginx.conf 와 include 로 불러온 파일이 모두 합쳐져 나옵니다.

여기 나온 경로는 컨테이너 안의 경로입니다. 호스트의 어느 폴더인지는 볼륨 연결에서 찾습니다.

/home/nginx/log 가 호스트의 /opt/web/log 로 연결돼 있으니, 로그는 /opt/web/log/web.log 에 있습니다. 경로가 /var/log/nginx/ 그대로이고 연결된 볼륨도 없다면 docker logs 로 봅니다.

로그 파일 정리

섹션 제목: “로그 파일 정리”

파일로 남기면 로그는 계속 커집니다. 리눅스 서버에서는 logrotate 로 날짜별로 나누고 오래된 것을 지웁니다. 호스트에 설정 파일을 하나 둡니다.

줄 하는 일
daily 하루에 한 번 나눕니다
rotate 14 나눈 파일을 14개까지 두고, 그보다 오래된 것은 지웁니다
compress, delaycompress 나눈 파일을 gzip 으로 압축합니다. 바로 전 파일 하나는 압축하지 않고 둡니다
missingok, notifempty 파일이 없거나 비어 있으면 넘어갑니다
postrotate 나눈 뒤 실행할 명령

postrotate 의 nginx -s reopen 이 필요한 이유가 있습니다. logrotate 가 access.log 를 access.log.1 로 이름을 바꿔도, Nginx 는 열어 둔 파일에 계속 씁니다. 이름이 바뀐 access.log.1 에 로그가 이어서 쌓이고 새 access.log 는 비어 있게 됩니다. reopen 은 Nginx 가 로그 파일을 다시 열게 해서 새 access.log 에 쓰게 합니다.

보관 기간과 주기는 로그 양과 디스크에 맞춰 정합니다.

설정 한눈에

섹션 제목: “설정 한눈에”
하려는 것 설정
한 줄 모양 정하기 log_format main '...';
access 로그 남기기 access_log /var/log/nginx/access.log main;
응답 시간 남기기 모양에 $request_time, $upstream_response_time
error 로그 수준 error_log /var/log/nginx/error.log notice;
정적 파일은 남기지 않기 location /assets/ { access_log off; }
조건으로 거르기 map + access_log ... if=$loggable;
정적 파일은 오류만 남기기 location /assets/ { access_log ... main if=$log_status; }
컨테이너 밖 파일로 남기기 -v /opt/web/log:/var/log/nginx
로그 위치 확인 nginx -T | grep _log + docker inspect 의 Mounts
로그 파일 다시 열기 nginx -s reopen
