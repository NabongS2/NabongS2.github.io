세션과 토큰

2026년 10월 14일 · 읽는 데 6분
nabong

시리즈로그인과 인증

  1. 쿠키, localStorage, sessionStorage
  2. 세션과 토큰
  3. 액세스 토큰과 리프레시 토큰

앞 글에서 브라우저에 값을 저장하는 쿠키, localStorage, sessionStorage 를 봤습니다. 이 글은 로그인한 뒤 서버가 사용자를 알아보는 두 방식인 세션과 토큰이 어떻게 다르고, 각각 어떻게 동작하는지 보고자 합니다.

백엔드 예시는 Spring Boot 로 씁니다.

인증과 인가

섹션 제목: “인증과 인가”

로그인과 관련된 일은 두 가지로 나뉩니다.

뜻 예
인증 (Authentication) 요청한 사람이 누구인지 확인 아이디와 비밀번호가 맞는지 확인
인가 (Authorization) 그 사람이 이 일을 해도 되는지 확인 관리자만 사용자 목록을 볼 수 있음

인증이 먼저이고, 인가는 누구인지 안 다음에 합니다. 실패했을 때의 상태 코드도 다릅니다. 인증에 실패하면 401, 인증은 됐지만 권한이 없으면 403 을 돌려줍니다. 두 코드의 차이는 HTTP 상태 코드 글에 정리했습니다.

이 글의 세션과 토큰은 인증, 그중에서도 한 번 로그인한 사용자를 다음 요청에서 다시 알아보는 방법입니다.

HTTP 와 로그인 상태

섹션 제목: “HTTP 와 로그인 상태”

HTTP 는 상태를 저장하지 않습니다(stateless). 서버는 요청 하나를 받아 응답하면 그 요청을 기억하지 않고, 다음 요청을 처음 보는 요청처럼 처리합니다.

요청 1 에서 로그인에 성공해도, 요청 2 에는 “요청 1 을 보낸 사람”이라는 정보가 없습니다. 그래서 로그인에 성공하면 서버가 브라우저에 증표를 하나 주고, 브라우저는 이후 요청마다 그 증표를 함께 보냅니다.

증표로 무엇을 주는지에 따라 방식이 나뉩니다.

방식 증표 사용자 정보가 있는 곳
세션 세션 ID (의미 없는 임의의 문자열) 서버
토큰 토큰 (사용자 정보를 담고 서명한 문자열) 토큰 안

세션 방식

섹션 제목: “세션 방식”

세션(session)은 서버가 로그인한 사용자의 정보를 저장해 두는 공간입니다. 서버는 세션마다 세션 ID 를 붙이고, 브라우저에는 세션 ID 만 줍니다.

  1. 브라우저가 아이디와 비밀번호를 보냅니다.
  2. 서버가 확인한 뒤 세션을 만들고, 세션 저장소에 사용자 정보를 저장합니다.
  3. 서버가 응답의 Set-Cookie 로 세션 ID 를 보냅니다.
  4. 브라우저는 이후 요청마다 쿠키로 세션 ID 를 보냅니다. 화면 코드가 따로 하는 일은 없습니다.
  5. 서버는 세션 ID 로 세션 저장소에서 사용자 정보를 찾습니다.

세션 ID 는 a1b2c3 처럼 그 자체로는 아무 뜻이 없는 문자열입니다. 실제로는 추측할 수 없을 만큼 긴 임의의 값을 씁니다. 누가 로그인했는지는 서버의 세션 저장소에만 있습니다.

Spring 에서 세션 사용

섹션 제목: “Spring 에서 세션 사용”

Spring Boot 의 내장 Tomcat 은 세션을 서버 메모리에 저장하고, 세션 ID 를 JSESSIONID 라는 쿠키로 보냅니다. 아래는 흐름을 보기 위해 세션을 직접 다루는 예입니다. Spring Security 를 쓰면 로그인 확인과 세션 저장을 Spring Security 가 대신합니다.

세션 쿠키의 속성과 세션이 유지되는 시간은 설정 파일에서 정합니다.

timeout 은 마지막 요청부터 잽니다. 사용자가 계속 요청을 보내면 세션이 계속 유지되고, 요청 없이 30분이 지나면 로그아웃됩니다.

토큰 방식

섹션 제목: “토큰 방식”

토큰 방식은 서버가 세션을 저장하지 않습니다. 대신 사용자 정보를 문자열 하나에 담고, 서버만 만들 수 있는 서명을 붙여서 브라우저에 줍니다. 이 문자열이 토큰입니다.

  1. 브라우저가 아이디와 비밀번호를 보냅니다.
  2. 서버가 확인한 뒤, 사용자 정보를 담은 토큰을 만들어 서명합니다.
  3. 서버가 응답 본문으로 토큰을 보냅니다.
  4. 브라우저는 토큰을 저장해 두고, 이후 요청마다 Authorization 헤더에 넣어 보냅니다.
  5. 서버는 토큰의 서명이 맞는지 확인하고, 토큰 안의 사용자 정보를 그대로 씁니다.

Authorization 은 인증 정보를 보내는 HTTP 헤더이고, Bearer 는 “이 토큰을 가진 사람”이라는 뜻의 형식 이름입니다. 쿠키와 달리 브라우저가 자동으로 넣지 않으므로, 화면 코드가 요청마다 넣습니다. fetch 와 axios 글의 요청 인터셉터가 이 일을 하는 예입니다.

토큰 형식은 여러 가지이고, 웹에서 가장 많이 쓰는 것이 JWT 입니다.

JWT 의 구조

섹션 제목: “JWT 의 구조”

JWT(JSON Web Token)는 점(.)으로 나뉜 세 부분으로 이루어집니다.

부분 들어 있는 것
헤더 (header) 서명 방식. HS256 은 비밀 키 하나로 서명하고 확인하는 방식
페이로드 (payload) 토큰에 담은 정보. 항목 하나하나를 클레임(claim)이라고 함
서명 (signature) 헤더와 페이로드를 서버의 비밀 키로 계산한 값

페이로드에 자주 넣는 클레임입니다.

클레임 뜻 예
sub 토큰의 주인 (subject). 보통 사용자 ID "42"
iat 발급 시각 (issued at). 1970년부터 센 초 1791968400 (2026-10-14 18:00)
exp 만료 시각 (expiration) 1791970200 (2026-10-14 18:30)

role 처럼 필요한 정보를 직접 정해서 넣을 수도 있습니다.

서명

섹션 제목: “서명”

서명은 헤더와 페이로드를 서버만 아는 비밀 키로 계산한 값입니다. 서버는 토큰을 받으면 같은 계산을 다시 해서, 결과가 토큰의 서명과 같은지 비교합니다.

누군가 페이로드의 role 을 ADMIN 으로 고치면, 서명도 새로 계산해야 맞습니다. 하지만 비밀 키가 없으면 맞는 서명을 만들 수 없습니다. 그래서 서명이 맞는 토큰은 서버가 만든 그대로라고 믿을 수 있고, 서버는 세션 저장소를 찾지 않고도 토큰 안의 정보를 씁니다.

서명은 고쳤는지를 확인할 뿐, 내용을 숨기지 않습니다. 헤더와 페이로드는 Base64URL 이라는 방식으로 글자만 바꾼 것이라, 되돌리면 누구나 JSON 을 읽을 수 있습니다. 그래서 페이로드에는 비밀번호나 개인 정보를 넣지 않습니다.

Spring 에서 JWT 사용

섹션 제목: “Spring 에서 JWT 사용”

Spring 에서 JWT 를 만들고 확인하는 라이브러리는 jjwt, Nimbus JOSE + JWT(Spring Security 가 사용) 등이 있습니다. 아래는 jjwt 0.12 로 쓴 예입니다.

parseSignedClaims 는 서명이 맞지 않거나 exp 가 지난 토큰이면 예외를 던집니다. 실제로는 요청마다 이 확인을 하는 필터를 두고, 실패하면 401 을 돌려줍니다.

비밀 키는 코드에 쓰지 않고 환경 변수나 설정 서버로 넣습니다. 비밀 키가 새어 나가면 누구나 맞는 서명을 만들 수 있습니다.

세션과 토큰 비교

섹션 제목: “세션과 토큰 비교”
세션 토큰 (JWT)
서버가 저장하는 것 로그인한 사용자마다 세션 없음 (비밀 키만)
요청을 받으면 세션 저장소에서 세션 ID 로 찾음 서명과 만료 시각을 확인
증표를 보내는 방법 주로 쿠키 (브라우저가 자동으로) 주로 Authorization 헤더 (코드가 직접)
로그아웃, 강제 로그아웃 세션을 지우면 바로 끝남 토큰은 exp 까지 유효함
권한이 바뀌었을 때 다음 요청부터 반영 새 토큰을 받을 때 반영
서버가 여러 대일 때 세션 저장소를 함께 써야 함 같은 비밀 키만 있으면 어느 서버든 확인

서버가 여러 대일 때

섹션 제목: “서버가 여러 대일 때”

세션은 기본으로 서버 메모리에 저장됩니다. 서버가 두 대이고 로그인 요청은 서버 A 가, 다음 요청은 서버 B 가 받으면, 서버 B 에는 그 세션이 없습니다. 그래서 Spring Session 과 Redis 처럼 모든 서버가 함께 쓰는 세션 저장소를 둡니다.

토큰은 서버에 저장하는 것이 없어서, 같은 비밀 키를 가진 서버라면 어느 서버든 토큰을 확인할 수 있습니다.

로그아웃

섹션 제목: “로그아웃”

세션은 서버에서 세션을 지우면, 그 세션 ID 를 가진 요청은 바로 로그인 상태가 아니게 됩니다.

토큰은 서버가 아무것도 저장하지 않으므로, 이미 발급한 토큰을 서버가 무효로 만들 방법이 없습니다. 브라우저에서 토큰을 지워도, 누군가 토큰을 복사해 두었다면 exp 까지는 그 토큰으로 요청할 수 있습니다. 그래서 토큰의 유효 기간을 짧게 두고, 리프레시 토큰으로 새 토큰을 받는 방식을 함께 씁니다. 이 내용은 다음 글에서 다룹니다.

쿠키와 세션

섹션 제목: “쿠키와 세션”

“쿠키를 쓰면 세션 방식”은 아닙니다. 쿠키는 증표를 보내는 방법이고, 세션과 토큰은 로그인 상태를 기억하는 방법이라 서로 따로 정합니다. JWT 를 HttpOnly 쿠키에 넣어 보낼 수도 있고, 세션 ID 를 헤더로 보낼 수도 있습니다. 토큰을 어디에 두고 어떻게 보낼지도 다음 글에서 다룹니다.

정리

섹션 제목: “정리”
세션 토큰
로그인 상태를 기억하는 곳 서버 토큰 안
서버가 사용자를 알아보는 방법 세션 ID 로 찾음 서명을 확인하고 내용을 읽음
잘 맞는 경우 화면과 API 가 같은 서버에 있고, 바로 로그아웃시킬 수 있어야 할 때 서버가 여러 대이거나, 앱·다른 서비스도 같은 API 를 호출할 때

어느 쪽이 더 낫다기보다, 서버 구성과 로그아웃을 얼마나 바로 반영해야 하는지에 따라 고릅니다.
