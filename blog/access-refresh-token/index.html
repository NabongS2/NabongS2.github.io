액세스 토큰과 리프레시 토큰

2026년 10월 14일 · 읽는 데 8분
nabong

시리즈로그인과 인증

  1. 쿠키, localStorage, sessionStorage
  2. 세션과 토큰
  3. 액세스 토큰과 리프레시 토큰

앞 글에서 토큰 방식은 서버가 아무것도 저장하지 않아서, 이미 발급한 토큰을 서버가 무효로 만들 수 없다고 했습니다. 이 글은 이 문제를 줄이기 위해 토큰을 액세스 토큰과 리프레시 토큰으로 나누는 방법과, 두 토큰을 어디에 두고 어떻게 갱신하는지 보고자 합니다.

예시는 화면과 API 가 같은 origin 에 있다고 가정합니다. 다른 origin 이면 쿠키 글의 설정이 더 필요합니다.

토큰을 둘로 나누는 이유

섹션 제목: “토큰을 둘로 나누는 이유”

토큰의 유효 기간은 하나만 정해서는 맞추기 어렵습니다.

유효 기간 좋은 점 문제
길게 (예: 14일) 사용자가 다시 로그인하지 않아도 됨 토큰이 새어 나가면 14일 동안 다른 사람이 쓸 수 있음
짧게 (예: 30분) 새어 나가도 30분 뒤면 쓸 수 없음 30분마다 다시 로그인해야 함

그래서 역할이 다른 토큰 두 개를 씁니다.

액세스 토큰 리프레시 토큰
하는 일 API 요청에 사용자를 증명 새 액세스 토큰을 받음
보내는 곳 모든 API 요청 갱신 요청(/auth/refresh)에만
유효 기간 짧게 (예: 15~30분) 길게 (예: 1~2주)
형식 보통 JWT JWT 또는 임의의 긴 문자열
서버 저장 하지 않음 저장함 (데이터베이스, Redis)
  • 액세스 토큰은 요청마다 오가므로 새어 나갈 기회가 많습니다. 대신 유효 기간이 짧아서 새어 나가도 피해가 짧게 끝납니다.
  • 리프레시 토큰은 갱신할 때만 보내므로 새어 나갈 기회가 적습니다. 서버가 저장해 두기 때문에, 서버에서 지우면 바로 쓸 수 없게 됩니다.

리프레시 토큰을 서버에 저장한다는 점에서, 이 방식은 토큰 방식에 세션 방식의 장점을 일부 더한 것입니다. 요청마다 저장소를 찾지 않고(액세스 토큰), 로그아웃은 서버에서 처리합니다(리프레시 토큰).

유효 기간을 얼마로 할지는 정답이 없습니다. 액세스 토큰을 짧게 할수록 새어 나갔을 때의 피해는 줄지만 갱신 요청이 늘고, 리프레시 토큰을 길게 할수록 다시 로그인하는 일은 줄지만 새어 나갔을 때 쓸 수 있는 기간이 길어집니다.

토큰을 보내는 방법

섹션 제목: “토큰을 보내는 방법”

토큰을 서버로 보내는 방법은 두 가지입니다.

Authorization 헤더 쿠키
넣는 쪽 화면 코드가 요청마다 넣음 브라우저가 자동으로 넣음
화면 코드가 토큰을 가지고 있어야 하는지 예 아니요 (HttpOnly 면 읽을 수도 없음)
다른 사이트가 보낸 요청에 붙는지 붙지 않음 붙을 수 있음 (SameSite 로 막음)

앞 글에서 본 것처럼, 보내는 방법은 세션과 토큰 중 무엇을 쓰는지와 따로 정합니다. JWT 도 쿠키로 보낼 수 있습니다.

저장 위치

섹션 제목: “저장 위치”

로그인하면 액세스 토큰과 리프레시 토큰을 받습니다. 두 토큰을 브라우저의 어디에 둘지 정해야 합니다. 둘 수 있는 곳은 localStorage, 브라우저 메모리, HttpOnly 쿠키입니다.

브라우저 메모리에 둔다는 것은 브라우저 저장소에 쓰지 않고, 지금 열려 있는 탭에서 실행 중인 자바스크립트 변수에만 넣어 둔다는 뜻입니다. 서버에 두는 것이 아닙니다. 페이지를 새로고침하거나 탭을 닫으면 코드가 처음부터 다시 실행되면서 값이 사라집니다.

두는 곳 메모리인지
모듈 안의 변수 (let accessToken), React 상태, Zustand 스토어 메모리
Zustand 스토어에 persist 를 쓴 경우 메모리가 아님. persist 가 값을 localStorage 에 저장함

어디에 두느냐에 따라, 공격을 받았을 때 토큰이 얼마나 위험해지는지가 달라집니다.

XSS 와 CSRF

섹션 제목: “XSS 와 CSRF”

토큰이 위험해지는 경우는 두 가지입니다. 둘 다 쿠키 글에서 본 공격입니다.

토큰을 훔쳐 가는 경우 (XSS): 공격자가 게시글 내용에 스크립트를 숨겨 두면, 그 글을 연 사용자의 브라우저에서 스크립트가 실행됩니다. 이 스크립트가 토큰을 읽어 공격자의 서버로 보냅니다.

공격자는 자기 컴퓨터에서 이 토큰으로 API 를 호출합니다. 토큰이 만료될 때까지 사용자인 것처럼 요청할 수 있습니다.

토큰을 몰래 쓰게 하는 경우 (CSRF): 쿠키는 브라우저가 요청에 자동으로 넣습니다. 사용자가 로그인한 상태로 공격자의 사이트를 열면, 그 사이트가 우리 서버로 요청을 보내게 할 수 있고, 이 요청에도 사용자의 쿠키가 붙습니다. 공격자는 토큰 값을 모르지만, 사용자의 브라우저를 통해 토큰을 쓰게 됩니다.

저장 위치 비교

섹션 제목: “저장 위치 비교”
저장 위치 훔쳐 가기 (XSS) 몰래 쓰기 (CSRF) 새로고침하면
localStorage 스크립트가 읽을 수 있음 자동으로 보내지 않아서 해당 없음 남음
메모리 변수에 접근하기 어려움 해당 없음 사라짐
HttpOnly 쿠키 스크립트가 읽을 수 없음 자동으로 보내지므로 SameSite 등으로 막아야 함 남음

세 곳 모두 장단점이 있어서, 두 토큰을 각각 다른 곳에 둡니다.

두 토큰의 저장 위치

섹션 제목: “두 토큰의 저장 위치”

리프레시 토큰은 HttpOnly 쿠키에 둡니다. 리프레시 토큰은 14일처럼 오래 유효해서, 훔쳐 가면 그동안 계속 새 액세스 토큰을 받을 수 있습니다. 그래서 스크립트가 읽을 수 없는 HttpOnly 쿠키에 두고, 몰래 쓰는 것은 쿠키 속성으로 막습니다.

  • SameSite=Strict: 다른 사이트에서 시작된 요청에는 쿠키를 보내지 않습니다.
  • Path=/auth: 갱신과 로그아웃 요청에만 쿠키를 보냅니다. 다른 API 요청에는 실리지 않습니다.

액세스 토큰은 메모리나 localStorage 에 둡니다. 화면 코드가 요청마다 Authorization 헤더에 넣어야 하므로, 코드가 읽을 수 있는 곳에 둘 수밖에 없습니다. 대신 30분처럼 짧게 유효해서, 훔쳐 가도 30분 뒤에는 쓸 수 없습니다.

메모리 localStorage
훔쳐 가기 어려움 쉬움
새로고침, 새 탭 사라져서 갱신 요청으로 다시 받아야 함 남아 있어서 바로 씀

토큰을 어디에 두어도 XSS 자체를 막지는 못합니다. 스크립트가 실행되는 동안에는 토큰을 읽지 못해도 사용자인 것처럼 요청을 보낼 수 있습니다. XSS 는 사용자 입력을 HTML 로 그대로 넣지 않고, CSP(Content Security Policy) 헤더로 실행할 수 있는 스크립트를 제한하여 막습니다.

CORS 설정

섹션 제목: “CORS 설정”

공격자의 사이트가 사용자의 브라우저에서 우리 서버의 /auth/refresh 를 호출하게 만들 수도 있습니다. 공격자의 사이트와 우리 서버는 다른 사이트이므로 SameSite=Strict 쿠키는 보내지지 않습니다. 쿠키가 실려 가는 설정이더라도, 새 액세스 토큰이 담긴 응답은 브라우저가 공격자의 사이트에 보여 주지 않습니다. 다른 origin 의 응답을 읽으려면 서버가 CORS 로 허락해야 하기 때문입니다.

이 보호는 서버가 CORS 를 좁게 허용할 때만 성립합니다. 모든 origin 을 허용하면서 Access-Control-Allow-Credentials: true 를 보내면, 공격자의 사이트도 응답을 읽어 새 액세스 토큰을 가져갈 수 있습니다.

CORS 설정은 화면과 API 의 주소에 따라 정합니다.

화면과 API CORS 설정
같은 origin (Nginx·개발 서버 프록시로 /api, /auth 를 넘기는 경우) 필요 없음. 설정하지 않음
다른 origin (app.example.com 과 api.example.com) 화면 주소만 허용

다른 origin 이면 허용할 origin 을 목록으로 적습니다. Spring 에서는 이렇게 설정합니다.

Spring Security 를 쓰면 http.cors(Customizer.withDefaults()) 로 이 설정을 적용합니다.

구성 예

섹션 제목: “구성 예”

이 글의 예시는 지금까지의 내용을 합쳐 이렇게 구성합니다.

항목 구성
리프레시 토큰 HttpOnly; Secure; SameSite=Strict; Path=/auth 쿠키
액세스 토큰 브라우저 메모리(자바스크립트 변수). 새로고침하면 /auth/refresh 로 다시 받음
CORS 같은 origin 이면 설정하지 않고, 다른 origin 이면 화면 주소만 허용
XSS 사용자 입력을 HTML 로 그대로 넣지 않고, CSP 헤더를 둠

액세스 토큰은 localStorage 에 두어도 동작합니다. 새로고침할 때마다 갱신 요청을 보내지 않아도 되는 대신, XSS 가 생기면 남은 유효 기간 동안 토큰을 가져가 쓸 수 있습니다.

이 구성은 화면 코드가 액세스 토큰을 직접 다루는 방식 중 하나이고, 다른 구성도 있습니다.

구성 브라우저가 가진 것 특징
이 글의 구성 액세스 토큰(메모리), 리프레시 토큰(HttpOnly 쿠키) 화면 코드가 액세스 토큰을 다룸
두 토큰 모두 HttpOnly 쿠키 쿠키 두 개 화면 코드가 토큰을 다루지 않음. 모든 API 요청에 CSRF 대비가 필요
BFF (Backend for Frontend) 세션 쿠키 하나 화면 전용 서버가 토큰을 보관하고 API 를 대신 호출함. 브라우저에는 토큰이 없지만 서버가 하나 더 필요
세션 방식 세션 ID 쿠키 토큰을 쓰지 않음. 앞 글에서 다룸

토큰 갱신 흐름

섹션 제목: “토큰 갱신 흐름”

액세스 토큰이 만료되면 API 가 401 을 돌려줍니다. 화면 코드는 이 401 을 받으면 리프레시 토큰으로 새 액세스 토큰을 받고, 실패한 요청을 다시 보냅니다.

갱신 요청에도 실패하면 리프레시 토큰까지 만료된 것이므로, 로그인 화면으로 보냅니다.

Spring 에서 발급과 갱신

섹션 제목: “Spring 에서 발급과 갱신”
  • 액세스 토큰은 응답 본문으로, 리프레시 토큰은 Set-Cookie 로 보냅니다.
  • @CookieValue 는 요청의 쿠키에서 값을 꺼냅니다. 리프레시 토큰은 HttpOnly 라서 화면 코드는 값을 모르고, 브라우저가 쿠키로 넣어 보냅니다.
  • jwtProvider.createAccessToken 은 앞 글의 JWT 발급 코드입니다.

리프레시 토큰 회전

섹션 제목: “리프레시 토큰 회전”

위의 rotate 는 받은 리프레시 토큰을 확인한 뒤, 저장소에서 지우고 새 리프레시 토큰을 발급합니다. 갱신할 때마다 리프레시 토큰을 바꾸는 이 방식을 리프레시 토큰 회전(rotation)이라고 합니다.

리프레시 토큰이 새어 나가 두 사람이 같은 토큰을 가지게 되면, 한 사람이 먼저 갱신한 뒤 다른 사람이 이미 지워진 토큰을 보내게 됩니다. 서버는 지운 토큰이 다시 오면 누군가 토큰을 복사했다고 보고, 그 사용자의 리프레시 토큰을 모두 지워 다시 로그인하게 할 수 있습니다.

axios 에서 갱신

섹션 제목: “axios 에서 갱신”

액세스 토큰을 메모리에 두는 예입니다. 갱신 요청은 인터셉터가 없는 인스턴스로 보냅니다. 같은 인스턴스로 보내면, 갱신 요청이 401 을 받았을 때 다시 갱신을 시도하며 끝없이 반복됩니다.

이 코드는 흐름만 보여 줍니다. 화면이 요청 여러 개를 동시에 보내고 모두 401 을 받으면 갱신 요청도 여러 번 나갑니다. 리프레시 토큰을 회전하면 두 번째 갱신 요청부터는 이미 지워진 토큰을 보내게 되므로, 실제로는 갱신이 끝날 때까지 다른 요청을 기다리게 하는 처리가 필요합니다.

액세스 토큰을 메모리에 두면 새로고침할 때 사라지므로, 앱이 시작될 때 auth.post('/refresh') 를 한 번 호출해 액세스 토큰을 받아 둡니다.

로그아웃

섹션 제목: “로그아웃”

로그아웃은 두 토큰을 모두 쓸 수 없게 만드는 일입니다.

토큰 로그아웃할 때
리프레시 토큰 서버 저장소에서 지우고, Max-Age=0 쿠키로 브라우저에서도 지움
액세스 토큰 화면 코드가 메모리(또는 localStorage)에서 지움

쿠키를 지우는 Set-Cookie 는 만들 때와 Path 가 같아야 같은 쿠키로 처리됩니다.

이미 발급한 액세스 토큰은 서버가 무효로 만들 수 없어서, 누군가 복사해 두었다면 남은 유효 기간 동안은 쓸 수 있습니다. 액세스 토큰의 유효 기간을 짧게 두는 이유입니다. 바로 막아야 한다면 서버에 차단한 토큰 목록을 두고 요청마다 확인할 수 있지만, 그만큼 요청마다 저장소를 찾게 되어 세션 방식과 비슷해집니다.

여기까지가 화면 쪽에서 본 토큰의 흐름입니다. 서버가 요청마다 토큰을 확인하고 401·403 을 돌려주는 과정은 다음 글에서 Spring Security 로 구현하며 봅니다.
