Nginx, from HTTPS to a WebSocket proxy

Oct 1, 2026 - 12 min read
nabong

SeriesNginx

  1. Nginx, from static files to an API proxy
  2. Nginx, from HTTPS to a WebSocket proxy

The previous post built a minimal setup that serves the frontend files and forwards /api to the backend. This post covers what you add to that setup when it goes onto a server, grouped by purpose, so each line in the configuration file has a reason next to it.

HTTPS

Section titled “HTTPS”
Line What it does
listen 443 ssl Accepts HTTPS on port 443
ssl_certificate The certificate. A public file shown to the browser
ssl_certificate_key The certificate’s private key. A file that must not leave the server
ssl_protocols The TLS versions to allow. Leaves out the old 1.0 and 1.1 and opens only 1.2 and 1.3

ssl_certificate takes not just the server certificate but a file with the intermediate certificates from the certificate authority appended (the fullchain). With the server certificate alone the site opens in a browser, but other servers or apps calling the address can get certificate errors. Browsers fetch a missing intermediate certificate on their own; most other clients don’t.

If Nginx runs in a container, mount the certificate folder as a volume and open port 443. Mount the private key read-only (:ro).

A certificate you make yourself for an internal dev server (a self-signed certificate) still encrypts the connection, but browsers show a warning because it was not issued by a trusted authority.

Don’t turn on HSTS in that case. HSTS is a Strict-Transport-Security response header that tells the browser “open this address over https only from now on”. A browser that has received it removes the button for proceeding past a certificate warning. A self-signed certificate always triggers the warning, so with HSTS on, the address can’t be opened at all.

Requests that arrive over http

Section titled “Requests that arrive over http”

Some people type http:// into the address bar. There are two cases.

When ports 80 and 443 are open separately, the server on 80 only redirects to the https address.

When only one port is open, with HTTPS, an http:// request to that port gets a 400 error page saying “The plain HTTP request was sent to HTTPS port”. Inside Nginx this case has its own code, 497, and you can redirect that code to the https address.

$http_host is the host and port exactly as the browser sent them, so an address with a port such as :8443 keeps it.

Lines that differ from the http setup

Section titled “Lines that differ from the http setup”

Moving an http setup to https changes only a few places.

http https
listen listen 8080; listen 8080 ssl;
Certificate none ssl_certificate, ssl_certificate_key, ssl_protocols
Requests arriving over http not applicable 80 → 443 return 301, or error_page 497 on the same port
X-Forwarded-Proto the backend receives http the backend receives https
Running the container port plus dist and config file volumes add the certificate folder volume
Cache, compression, location unchanged unchanged

X-Forwarded-Proto is already among the proxy headers in the previous post, so the line stays as it is and only its value becomes https. The backend talks to Nginx over http, so without this header it can’t tell that the browser came in over https. Redirect addresses the backend builds then go out as http://, and cookies meant only for https (Secure) are not handled. The backend also has to be set to read the header. In Spring Boot this is server.forward-headers-strategy.

Caching

Section titled “Caching”

A browser can keep a file it has downloaded and skip downloading it next time. The server says how long to keep it with the Cache-Control header. The frontend files fall into two groups that are handled differently.

File Setting Reason
JS and CSS under /assets/ keep for a year, don’t ask again The file name changes on every build. Same name means same content
index.html keep, but check with the server before each use The name never changes. It holds the names of the newly deployed JS and CSS

As the previous post showed, a build produces names like index-3f9a1c2e.js, and the name changes when the code changes. So files in assets/ can be kept for a long time without an old file ever being used. A new version arrives under a new name.

The problem is index.html. If an old copy is kept, it points to the old JS name, and you get a deploy that doesn’t change what the user sees. So index.html is checked with the server every time.

no-cache doesn’t mean “don’t store”; it means “check before using”. If nothing changed, the server answers with a short 304 and the browser uses its stored copy. Not storing at all is no-store, which downloads the whole file every time.

There is one more reason to give /assets/ its own block. Without it, a request for a JS file that doesn’t exist also goes through the try_files in location / and gets index.html back. The browser tries to read HTML as JS and reports an error that is hard to make sense of. try_files $uri =404 returns 404 for missing files instead.

Once a location has even one add_header, the add_header lines in the enclosing server no longer apply to that location. If you put security headers in server, keep this in mind.

Compression

Section titled “Compression”

Text files such as JS and CSS shrink a lot when sent gzipped. The browser adds Accept-Encoding: gzip to the request to say it accepts compressed responses, and Nginx compresses what it sends back.

Line What it does
gzip on Turns compression on
gzip_types File types to compress. text/html is always included without being listed
gzip_min_length Responses smaller than this are not compressed. For small files the cost of compressing outweighs the saving
gzip_vary Adds Vary: Accept-Encoding to the response

PNG and JPG are already compressed formats, so they stay out of gzip_types. Compressing them again saves almost nothing.

gzip_vary matters when a caching proxy or CDN sits in front of Nginx. It says that the same address has a compressed and an uncompressed version, so a client that can’t take compressed responses doesn’t get the compressed one.

If there is another proxy in front of Nginx, such as a load balancer, Nginx by default doesn’t compress those requests. Add gzip_proxied any; in that case.

Check compression with the response headers.

gzip_comp_level sets the compression level from 1 to 9. The default is 1. A higher level makes files a little smaller and uses more CPU.

WebSocket

Section titled “WebSocket”

WebSocket opens a connection once and lets the server and browser keep sending messages over it. It is used for live notifications and monitoring screens. The /api setup from the previous post doesn’t connect it; it needs a few more lines.

A WebSocket starts as an ordinary HTTP request and asks to “switch this connection to WebSocket” with an Upgrade: websocket header. But by default Nginx talks to the backend over HTTP/1.0 and doesn’t pass the Upgrade and Connection headers on. The backend never receives the switch request, and the connection fails.

Line What it does
proxy_http_version 1.1 Talks to the backend over HTTP/1.1. Switching connections only works in 1.1
Upgrade, Connection headers Pass the browser’s switch request on to the backend
proxy_read_timeout Keeps the connection open this long even when nothing is sent

proxy_read_timeout defaults to 60 seconds. A WebSocket can be quiet for a while, and after 60 seconds with no message Nginx closes the connection. Either set the value longer, or have the client and server exchange a short signal (a heartbeat) at intervals. A longer value means dead connections are cleaned up later, but quiet connections stay open.

Local development is the same. When the Vite proxy setting forwards a WebSocket path, it needs ws: true. As the previous post said, path rules have to be written in both places.

SSE

Section titled “SSE”

SSE (Server-Sent Events) is the server sending a continuous stream of events to the browser, in one direction only. Unlike WebSocket it is one ordinary HTTP response that just doesn’t end, so it needs no connection-switch headers. It needs different lines instead.

Line What it does
proxy_buffering off Passes the backend response straight to the browser instead of collecting it
proxy_http_version 1.1, Connection "" Keeps the connection to the backend open instead of closing it after one response
proxy_read_timeout Keeps the connection open even when there are no events for a while

By default Nginx collects the backend response in a buffer before sending it. That is efficient for ordinary responses, but with SSE the events pile up in the buffer and reach the browser much later, all at once. So proxy_buffering off turns it off. The backend can also turn buffering off for a single response by adding an X-Accel-Buffering: no header to it.

For the same reason, text/event-stream stays out of gzip_types. While Nginx collects data to compress, the events arrive late.

Timeouts

Section titled “Timeouts”

How long Nginx waits on a request it forwarded to the backend is split into three settings.

Directive What it waits for Default
proxy_connect_timeout Opening a connection to the backend 60s
proxy_send_timeout Sending the request to the backend, from one write to the next 60s
proxy_read_timeout Reading the backend response, from one read to the next 60s

None of the three is a total time. Each is the gap between two operations. If the response keeps arriving, even in small pieces, the connection isn’t closed after 60 seconds.

The 504 Gateway Timeout from the previous post is a request that hit proxy_read_timeout. If something legitimately takes long, such as an API that builds and returns a large file, you can raise the value for that location only. Raising it everywhere means that when the backend hangs, requests are held that much longer.

If there are file uploads, also look at client_max_body_size. It is the maximum request body size and defaults to 1MB, so uploading a larger file gets 413 Request Entity Too Large from Nginx before the request reaches the backend.

nginx.conf and conf.d

Section titled “nginx.conf and conf.d”

The official image has its configuration in two layers.

File What it holds
/etc/nginx/nginx.conf Settings written once for all of Nginx. Process count, log format and location, and the line that loads the folder below
/etc/nginx/conf.d/default.conf Settings for one site. The server block with its listen, certificates, root and locations

nginx.conf

Section titled “nginx.conf”

This is the first file Nginx reads when it starts. Trimmed down, the one in the official image looks like this.

The include at the end of the http block pulls in the files from conf.d/ at that spot. So the server block in default.conf is the same as one written inside this http block.

File names

Section titled “File names”

The two files differ in how fixed their names are.

File Name
nginx.conf Fixed. Nginx is built to read /etc/nginx/nginx.conf
default.conf Not fixed. The include is conf.d/*.conf, so any file ending in .conf is read, whatever its name

default.conf is just the name of the file the official image ships. It holds a server block that shows the Nginx welcome page on port 80.

So if you mount your configuration under a different name (such as app.conf), the original default.conf is read as well. If the two server blocks use the same port, requests can end up in the wrong one. Mounting your configuration over default.conf avoids this.

Repositories often keep per-environment names such as nginx.dev.conf and default.prod.conf, and map them to the fixed paths when mounting them into the container.

Nginx only sees the paths inside the container, so the file names outside can be anything.

Which file to write in

Section titled “Which file to write in”

Everything in this post and the previous one can go in default.conf. gzip and client_max_body_size can be written inside the server block too. When running a single app, edit only default.conf, and mount nginx.conf when you want to change the log format or location.

There is one thing to watch when the same directive appears in both files. If an inner block has the same directive, the outer value is ignored entirely. It isn’t partly overridden.

The path is the same, so it looks like the same setting, but the main format doesn’t apply in the server block. A value you leave out isn’t inherited from outside; it goes back to the default. add_header from Caching follows the same rule. That’s why log settings go in nginx.conf only.

Whichever file you changed, apply it the same way as in the previous post: check with nginx -t, then nginx -s reload.

Settings at a glance

Section titled “Settings at a glance”
Goal Setting
Accept HTTPS listen 443 ssl; + ssl_certificate, ssl_certificate_key
Send http to https return 301 https://$host$request_uri;
Send http on the same port to https error_page 497 =301 https://$http_host$request_uri;
Always check index.html add_header Cache-Control "no-cache";
Keep assets for a long time add_header Cache-Control "public, max-age=31536000, immutable";
Compression gzip on; + gzip_types …
WebSocket proxy_http_version 1.1; + Upgrade, Connection headers
SSE proxy_buffering off; + a long proxy_read_timeout
Wait longer for the backend proxy_read_timeout 300s;
Allow larger uploads client_max_body_size 20m;
