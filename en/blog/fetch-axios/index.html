fetch and axios

Oct 13, 2026 - 7 min read
nabong

SeriesWorking with API data

  1. Synchronous and asynchronous
  2. fetch and axios
  3. Zustand and React Query

The CSR post said that with CSR the browser receives an empty HTML page, and then JS fetches data from an API and builds the page. This post is about that “fetches data from an API” part. It looks at how fetch and axios, the two tools used to send requests from browser code to a server, differ, and how to use each.

The await and Promises in the example code are covered in the Synchronous and asynchronous post.

HTTP clients

Section titled “HTTP clients”

An HTTP client is a tool that sends HTTP requests to a server and receives the responses. When you type a URL into the address bar, the browser does this; in code, you call an HTTP client function to do the same.

The examples in this post use a server address, /api/posts, that returns a list of blog posts. A request and its response look like this.

What the status codes mean is covered in the HTTP status codes post. For this post, all you need is that 2xx means success and 4xx and 5xx mean failure.

There are several HTTP clients for JavaScript.

Description
fetch A function built into browsers and Node.js 18+
axios The most widely used HTTP client library
ky, ofetch, etc. Libraries that wrap fetch to make it as convenient as axios

This post covers fetch and axios.

fetch

Section titled “fetch”

GET requests

Section titled “GET requests”
  • res is short for response. Once fetch(url) receives a response, it returns a Response object holding the whole thing: the status code (res.status), the headers (res.headers) and the body.
  • The body hasn’t been read yet. Calling res.json() reads it and turns it into a JavaScript value. Reading the body also takes time, so res.json() doesn’t hand back the value right away; it returns a Promise, and you await it to get the value.
  • posts is the body taken out that way: the list of posts.

Reading the response body

Section titled “Reading the response body”

Logged with console.log, res looks like this.

The status code and headers can be read right away, but the body is a stream of data (ReadableStream) that may still be downloading. res.json() reads that body to the end and, in the same step, turns the text it read, '[{"id":1,"title":"First post"}]', into the JavaScript value [{ id: 1, title: 'First post' }].

Which function reads the body depends on its format.

Function Returns Used for
res.json() A JavaScript object or array JSON responses
res.text() A string HTML, plain text
res.blob() File data Images, file downloads

The body can be read only once. After that, bodyUsed becomes true and trying to read it again throws an error. So you call just one of the three.

POST requests

Section titled “POST requests”

To send data, put the method, headers and body in the second argument.

  • body must be a string, so the object is converted with JSON.stringify.
  • The Content-Type header tells the server the body is JSON.

Checking the response

Section titled “Checking the response”

fetch counts it as success as long as the server sends back a response. A 404 or 500 is still a response, so it doesn’t throw. That’s why you check the status code yourself.

res.ok is true when the status code is 200–299. res.status holds the status code as a number.

fetch throws when no response arrives: the connection dropped, the server address is wrong, or the browser blocked the response because of a CORS error.

axios

Section titled “axios”

axios isn’t built in like fetch, so you install the package.

GET requests

Section titled “GET requests”

axios’s res is the whole response too. If the body is JSON, axios reads it ahead of time, turns it into a JavaScript value and puts it in res.data. So res.data is the list of posts, and there’s no separate res.json() call.

POST requests

Section titled “POST requests”

Pass an object as the second argument and axios turns it into a JSON string and adds the Content-Type: application/json header.

Handling errors

Section titled “Handling errors”

axios throws when the response’s status code isn’t 2xx. So failures are handled in one place, try...catch.

  • error.response holds the response the server sent back. It’s empty when no response arrived.
  • axios.isAxiosError(error) checks whether the error came from axios. In TypeScript you need this check before using error.response.

Compared with fetch

Section titled “Compared with fetch”
fetch axios
Install Not needed Install the package
Response body Call await res.json() yourself Already in res.data
Data to send Set JSON.stringify and Content-Type yourself Pass the object as is
4xx and 5xx responses Treated as success; check res.ok yourself Throws an error
Shared settings Set on every request Set once on an instance
Intercepting requests and responses No Interceptors
Timeout Pass AbortSignal.timeout() yourself timeout option

The last three rows are the main reasons to use axios. They come next.

axios instances

Section titled “axios instances”

Most of the APIs an app calls live on the same server and use the same headers and timeout. To avoid repeating those settings on every request, you use axios.create to make an axios with the settings fixed. This is called an instance: one concrete copy made from axios. You can make several instances from the same axios, each with different settings.

  • baseURL: the address put in front of every request path. If the development and production servers have different addresses, this is the only value you change.
  • timeout: the longest time, in milliseconds, to wait for a response. The default is 0, which means waiting with no limit. A short value gives up quickly on a server that doesn’t answer; too short, and slow but healthy requests fail too.

If there are two servers, make two instances and use each for its server.

Interceptors

Section titled “Interceptors”

An interceptor is something that catches things on their way through. In axios, it’s a function that runs before every request sent through an instance goes out, or before every response reaches your code. It puts work you’d otherwise repeat on every request in one place.

Request interceptors

Section titled “Request interceptors”

An example that adds the logged-in user’s token to the header of every request.

config is this request’s settings (address, headers and so on). The request goes out with the config the function returns.

Response interceptors

Section titled “Response interceptors”

An example that sends the user to the login page when the login has expired and a 401 comes back.

  • The first function receives 2xx responses; the second receives errors.
  • Returning Promise.reject(error) from the second function passes the error on to the catch of the code that made the request. Shared handling goes in the interceptor, and handling that differs per screen goes in each catch.

To show an error alert from one place, have the response interceptor record the error in a state management library’s store, and display that value in one spot on the page.

Interceptors are also used to return only the body of a successful response.

This saves taking out res.data wherever you make a request. The trade-off is that values received through this instance no longer carry the status code or headers.

Summary

Section titled “Summary”
fetch axios
What it does Sends HTTP requests to a server and receives responses Same
What counts as failure Any response is success; check the status code yourself Anything other than 2xx throws
Shared settings None Instances (axios.create)
Shared handling None Interceptors

If you only make requests in a few places and need no shared settings, fetch alone is enough. If many places call the same server and you want token and error handling in one place, axios instances and interceptors cut that work down. You can also build the same structure on fetch yourself, or use a library such as ky.
