IP addresses and ports

Oct 22, 2026 - 7 min read
nabong

SeriesNetwork basics

  2. IP addresses and ports
  3. NAT and port forwarding
  4. VPN
  5. DNS and domains

In an address like http://192.168.0.20:8080, 192.168.0.20 is the IP address and 8080 is the port. In terms of the layers from the previous post, the IP address is used at the internet layer and the port at the transport layer. This post looks at what each of them points to, and what to check when you can’t connect to a server.

IP addresses and ports

Section titled “IP addresses and ports”

An IP address is a number that identifies a computer on a network. IPv4, the version most in use, is written as four numbers between 0 and 255, like 192.168.0.20.

A port is a number that identifies the program receiving a request within one computer. It is between 0 and 65535; a server program picks a port when it starts and waits for requests on it.

Part of the address Points to
192.168.0.20 The computer receiving the request
8080 The program on that computer receiving the request

Nginx, a backend app and Redis can run on the same server because they use different ports, so requests reach the right program without getting mixed up.

Default ports

Section titled “Default ports”

Commonly used programs have a default port they use when none is specified.

Port Program that uses it by default
22 SSH
80 HTTP
443 HTTPS
3306 MySQL, MariaDB
5432 PostgreSQL
6379 Redis
8080 Spring Boot, Tomcat

A browser uses 80 for an http:// address with no port, and 443 for an https:// address with no port. So https://example.com is the same as https://example.com:443.

Public and private IPs

Section titled “Public and private IPs”

A public IP is an address that is unique across the whole internet. Internet service providers hand them out, and any computer on the internet can reach that address.

A private IP is an address used only inside an internal network, such as an office or a home. These three ranges are reserved for private IPs.

Range Example
10.0.0.0 – 10.255.255.255 10.0.0.5
172.16.0.0 – 172.31.255.255 172.17.0.2 (Docker’s default container range)
192.168.0.0 – 192.168.255.255 192.168.0.20

Each internal network uses private IPs on its own, so 192.168.0.20 at one company and 192.168.0.20 at another are different computers. That is why a private IP can’t be reached from the internet. How computers on an internal network get out to the internet, and how requests from outside get in to an internal server, are covered in the next post on NAT and port forwarding.

localhost and 0.0.0.0

Section titled “localhost and 0.0.0.0”

localhost

Section titled “localhost”

localhost is the name for the computer running the command itself; its IP is 127.0.0.1. Requests to it don’t leave for the network but go to a program on the same computer.

The address a server listens on

Section titled “The address a server listens on”

A server program decides not only the port but also which address it accepts requests on. This is called binding.

Bind address Who can connect
127.0.0.1 Only programs on the same computer
0.0.0.0 Every network address of that computer. Other computers can connect too
192.168.0.20 Only requests arriving at that address

Even on the same port 8080, a server bound to 127.0.0.1 can’t be reached from another PC. Defaults differ by program.

Program Default binding To allow other PCs
Vite dev server localhost npm run dev -- --host
Spring Boot All addresses Nothing to change
Redis 127.0.0.1 (per its config file) Change bind, set a password
Docker -p 8080:80 0.0.0.0 -p 127.0.0.1:8080:80 keeps it to the same PC

0.0.0.0 is a bind value meaning “accept on every address”. It isn’t an address to type into a browser; to connect, use localhost or the computer’s IP.

localhost inside containers

Section titled “localhost inside containers”

In terms of networking, a container behaves like a small computer inside the server. Each container has its own IP and its own 127.0.0.1. So where localhost points depends on where you use it.

Where localhost is used What it points to
The server’s terminal The server itself
Inside the app container The app container itself
Inside the api container The api container itself

Even on the same server, connecting to localhost:8000 from the app container looks for app’s own port 8000, not api’s. No program is listening there, so the connection is refused. Reach another container in one of these two ways.

Method Address used from app Condition
Through the server 192.168.0.20:9000 api runs with -p 9000:8000
Docker network api:8000 Both containers on the same Docker network. The container name becomes the address

For the same reason, a program inside a container binds to 0.0.0.0, not 127.0.0.1. -p sends requests arriving at the server to the container’s IP (172.18.0.3), so a program bound only to 127.0.0.1 inside the container never receives them. Who can connect from outside the container is decided by the server address in front of -p: -p 9000:8000 lets other PCs connect, and -p 127.0.0.1:9000:8000 only allows connections from that server.

This is also why writing the backend address as localhost in an Nginx container’s config doesn’t connect. The actual setup for both methods is in Connecting containers in the Nginx post.

Port conflicts

Section titled “Port conflicts”

One port on one address can be used by only one program. Start another program on a port already in use, and it fails to start and exits.

Find the program using that port and stop it, or change the new program’s port.

Checking open ports

Section titled “Checking open ports”

Which program is listening on which address and port on a server is checked with ss.

Option Meaning
-t tcp. TCP connections only
-l listening. Only ports waiting for requests
-n numeric. Ports as numbers instead of names like http
-p process. The program using the port. Programs of other accounts only show with sudo

The Local Address:Port column is the bind address and port. In this output, Nginx (80) and SSH (22) are on 0.0.0.0, so other PCs can connect; Redis (6379) is on 127.0.0.1, so only this server can.

Firewalls

Section titled “Firewalls”

Even when a server is listening on 0.0.0.0, a firewall blocking requests to that port means no one can connect. A firewall is a program that allows or blocks incoming and outgoing connections by rules you set.

Where Examples
On the server ufw and firewalld on Linux, Windows Firewall
Network equipment A company firewall, a home router
Cloud Rules in front of the server, such as AWS security groups

Order for checking connection errors

Section titled “Order for checking connection errors”

The message you get when a connection fails narrows down the cause.

Message Meaning Likely causes
Connection refused Reached the server computer, but no program is listening on that port The program is down, the port number is wrong, it is bound to 127.0.0.1
Connection timed out No response came back A firewall is blocking, the IP is wrong, a private IP from another network was used

Check from the server side outward.

  1. On the server, use ss -tlnp to see whether a program is listening on the port.
  2. Check that the bind address isn’t 127.0.0.1.
  3. On the server, check that curl localhost:8080 gets a response. If it does, the program is fine.
  4. From another PC, check with nc or Test-NetConnection whether the port can be reached. If not, look at the firewall or the network.

Command summary

Section titled “Command summary”
Task Command
Check your PC’s IP ipconfig (Windows), ip addr (Linux)
Check the public IP curl ifconfig.me
Check open ports and programs sudo ss -tlnp
Find the program using a port ss -tlnp | grep :8080, netstat -ano | findstr :8080
Check the response on the server curl localhost:8080
Check port reachability from another PC nc -zv IP port, Test-NetConnection IP -Port port
