Configuring and managing Nginx logs

Oct 8, 2026 - 8 min read
nabong

SeriesNginx

  1. Nginx, from static files to an API proxy
  2. Nginx, from HTTPS to a WebSocket proxy
  3. Configuring and managing Nginx logs

The previous post said log settings go in nginx.conf only. This post covers those settings: which logs Nginx writes, how to read a line, and how to choose what to keep and where to keep it.

Access log and error log

Section titled “Access log and error log”

Nginx writes two logs.

Log What it records Directives
Access log One line per incoming request. Who, when, which address, with what result access_log, log_format
Error log Problems Nginx ran into while handling requests. Failed backend connections, configuration errors, missing files error_log

When the page shows a 502 or 504, the access log only records the result, 502; the reason is in the error log. Read them together.

Access log format

Section titled “Access log format”

log_format sets what goes on one access log line and in what order, and gives that layout a name. The name can be anything you like. The official image’s nginx.conf has one named main.

access_log takes that name after the path to choose the layout for that file. Without a name, lines are written in combined, a layout built into Nginx. combined is main without the final $http_x_forwarded_for.

Reading a line

Section titled “Reading a line”

Here is one line in the main layout.

Field Variable Value in this line
Sender’s IP $remote_addr 192.168.0.15
Authenticated user $remote_user - (none)
Time $time_local 01/Oct/2026:14:03:21 +0900
Request $request GET /api/history/12 HTTP/1.1
Status code $status 200
Body size sent $body_bytes_sent 532 bytes
Previous page $http_referer https://app.example.com/history
Browser $http_user_agent Mozilla/5.0 ...
Original client IP $http_x_forwarded_for - (no other proxy in front)

Empty fields are written as -.

If another proxy such as a load balancer sits in front of Nginx, $remote_addr becomes that proxy’s IP. The real browser IP then appears in the X-Forwarded-For header the proxy added, which is the last field.

Finding lines by status code

Section titled “Finding lines by status code”

In the main layout, the status code is the 9th field when split on spaces. awk can pick out just the lines you want.

Recording response times

Section titled “Recording response times”

The main layout doesn’t say how long a request took. To find slow APIs, define another layout with the timing variables and give it a name. The example below names it with_time.

Variable What it measures
$request_time From when Nginx starts receiving the request until it has sent the whole response. In seconds, to three decimal places
$upstream_response_time The part of that spent waiting on the backend. - for requests not forwarded to a backend

If the two values are close, the time was spent in the backend. If only rt is large, the time went into talking to the browser: a slow network, or a large upload or download. When the 504 from the previous posts happens, urt shows a value near proxy_read_timeout.

Error log

Section titled “Error log”

The last field is the level to record. That level and everything more severe is written.

Level What gets recorded
debug, info Detailed records of processing. Not used day to day
notice Notices such as start, stop and configuration reload. The official image’s value
warn Things that still work but are worth checking
error A single request that couldn’t be handled. The default when no level is given
crit, alert, emerg Nginx itself not running properly

The messages you see most often map to the error codes from the previous posts.

Part of the message What the page showed Meaning
connect() failed (111: Connection refused) while connecting to upstream 502 Nginx reached the backend address, but nothing was listening on that port. The backend is down or the address is wrong
upstream timed out (110: Connection timed out) while reading response header from upstream 504 The backend didn’t answer within proxy_read_timeout
client intended to send too large body 413 The request body is larger than client_max_body_size

The end of each message also carries client:, request: and upstream:, so you can see which request failed on its way to which backend address.

Reading it with the access log

Section titled “Reading it with the access log”

Say a list fails to load and the developer tools show a 502. The two logs at that moment look like this.

The access log only tells you that /api/history/12 ended in a 502. Look up the same time and the same request in the error log, and the reason is there.

Error log field Value What it tells you
Time and level 2026/10/01 14:05:02 [error] An error at the same time as the access log line
Message connect() failed (111: Connection refused) Nginx couldn’t connect to the backend
client, request 192.168.0.15, GET /api/history/12 The same request as in the access log
upstream http://192.168.0.20:8100/api/history/12 The backend address Nginx tried to reach

The next place to look is the address in upstream. Check whether a backend is running on port 8100 on that server (docker ps), and whether the address in the configuration is right.

Requests not to record

Section titled “Requests not to record”

The access log has a line per request, so opening one page also records every JS, CSS and image request. There are two ways to filter out lines you don’t need.

Turning it off by path

Section titled “Turning it off by path”

For static files, access_log off turns logging off for that location only.

Filtering by condition

Section titled “Filtering by condition”

Adding if= to access_log skips any request where the condition value is 0 or empty. The condition value comes from a map in the http block. The example below drops successful GETs and keeps non-GET requests and errors.

Request $log_method:$log_status Recorded
Successful GET 0:0 no
Failed GET (404, 502) 0:1 yes
POST, PUT, DELETE 1:0, 1:1 yes

A map is a table that sets the value on the right from the value on the left. Entries starting with ~ are compared as regular expressions. Filtering makes the file smaller, but you lose the trail of successful requests. Which matters more depends on the environment.

What disappears when it’s off

Section titled “What disappears when it’s off”

Turning /assets/ off with access_log off also hides errors on that path.

Recall the caching case from the previous post. A deploy removed the old JS files, but a browser still holding the old index.html requests the old JS named in it. try_files $uri =404 turns that request into a 404. But the access log is off, and a 404 returned by =404 isn’t written to the error log either. The page is broken and the logs show nothing.

To cut down static file logging while keeping these errors, use $log_status from above as the condition instead of turning logging off.

An access_log inside a location makes the outer access_log be ignored entirely, so write the path and the layout name again.

Where logs go in a container

Section titled “Where logs go in a container”

In the official image, /var/log/nginx/access.log and error.log aren’t real files. They are linked to standard output and standard error.

So by default you read them with docker logs.

These logs are collected and stored by Docker’s logging driver. If the container runs with --log-driver none, nothing reaches docker logs. In that case have Nginx write to files directly, and mount that folder from the host.

Mounting a host folder on /var/log/nginx hides the links that came with the image, and Nginx creates real files with the same names. The logs collect in /opt/web/log/access.log on the host. If nginx.conf points the logs somewhere else, mount that folder instead.

Finding where the logs are

Section titled “Finding where the logs are”

On a server someone else set up, finding the logs takes two steps. First, print the whole configuration in effect with nginx -T and pull out the log lines. It combines nginx.conf and every file it includes.

Those are paths inside the container. To find the host folder, look at the volume mounts.

/home/nginx/log is mounted from /opt/web/log on the host, so the log is at /opt/web/log/web.log. If the path is still /var/log/nginx/ and no volume is mounted there, read it with docker logs.

Rotating log files

Section titled “Rotating log files”

Logs written to files keep growing. On a Linux server, logrotate splits them by date and removes old ones. Put one configuration file on the host.

Line What it does
daily Rotates once a day
rotate 14 Keeps up to 14 rotated files and deletes older ones
compress, delaycompress Gzips rotated files, leaving the most recent one uncompressed
missingok, notifempty Skips files that are missing or empty
postrotate Commands to run after rotating

There is a reason for nginx -s reopen in postrotate. When logrotate renames access.log to access.log.1, Nginx keeps writing to the file it already has open. Logs keep piling up in the renamed access.log.1 while the new access.log stays empty. reopen makes Nginx open its log files again, so it writes to the new access.log.

Choose the retention and interval to fit your log volume and disk.

Settings at a glance

Section titled “Settings at a glance”
Goal Setting
Define a line layout log_format main '...';
Write an access log access_log /var/log/nginx/access.log main;
Record response times $request_time, $upstream_response_time in the layout
Error log level error_log /var/log/nginx/error.log notice;
Don’t log static files location /assets/ { access_log off; }
Filter by condition map + access_log ... if=$loggable;
Log only errors for static files location /assets/ { access_log ... main if=$log_status; }
Write logs to files outside the container -v /opt/web/log:/var/log/nginx
Find where the logs are nginx -T | grep _log + Mounts from docker inspect
Reopen log files nginx -s reopen
