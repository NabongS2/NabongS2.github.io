Sessions and tokens

Oct 14, 2026 - 8 min read
nabong

SeriesLogin and authentication

  1. Cookies, localStorage, sessionStorage
  2. Sessions and tokens
  3. Access tokens and refresh tokens

The previous post looked at cookies, localStorage and sessionStorage, the places a browser stores values. This post looks at how sessions and tokens, the two ways a server recognises a user after login, differ and how each one works.

The backend examples use Spring Boot.

Authentication and authorization

Section titled “Authentication and authorization”

Login involves two separate jobs.

Meaning Example
Authentication Checking who sent the request Checking that the username and password match
Authorization Checking whether that person may do this Only admins can see the user list

Authentication comes first; authorization happens once you know who it is. The status codes for failure differ too. A failed authentication returns 401, and an authenticated user without permission gets 403. The difference between the two codes is in the HTTP status codes post.

The sessions and tokens in this post are about authentication, specifically how a user who has logged in once is recognised again on the next request.

HTTP and login state

Section titled “HTTP and login state”

HTTP is stateless. Once the server answers a request, it doesn’t remember it, and treats the next request as if it had never seen the sender before.

Even if login succeeds in request 1, request 2 carries nothing that says “this is the person who sent request 1”. So when login succeeds, the server gives the browser a credential, and the browser sends it with every request after that.

The approaches differ in what that credential is.

Approach Credential Where the user’s details live
Sessions A session ID (a meaningless random string) On the server
Tokens A token (a signed string holding the user’s details) Inside the token

Session-based login

Section titled “Session-based login”

A session is space where the server keeps the details of a logged-in user. The server gives each session a session ID, and hands only the session ID to the browser.

  1. The browser sends the username and password.
  2. The server checks them, creates a session and stores the user’s details in the session store.
  3. The server sends the session ID with Set-Cookie in the response.
  4. The browser sends the session ID as a cookie with every later request. The page code does nothing extra.
  5. The server finds the user’s details in the session store by the session ID.

A session ID like a1b2c3 means nothing on its own. In practice it is a random value long enough that it can’t be guessed. Who is logged in is recorded only in the server’s session store.

Token-based login

Section titled “Token-based login”

With tokens, the server doesn’t store a session. Instead it puts the user’s details in a single string, adds a signature only the server can produce, and gives that to the browser. That string is the token.

  1. The browser sends the username and password.
  2. The server checks them, then creates a token holding the user’s details and signs it.
  3. The server sends the token in the response body.
  4. The browser keeps the token and puts it in the Authorization header of every later request.
  5. The server checks that the token’s signature is valid and uses the user’s details from the token as is.

Authorization is the HTTP header for sending credentials, and Bearer is the name of the scheme, meaning “whoever holds this token”. Unlike cookies, the browser doesn’t add it automatically, so the page code adds it to every request. The request interceptor in the fetch and axios post is an example of doing that.

There are several token formats; the most widely used on the web is JWT.

JWT structure

Section titled “JWT structure”

A JWT (JSON Web Token) is made of three parts separated by dots (.).

Part Contents
Header The signing algorithm. HS256 signs and verifies with a single secret key
Payload The data in the token. Each item is called a claim
Signature A value computed from the header and payload with the server’s secret key

Claims that often go in the payload:

Claim Meaning Example
sub Who the token belongs to (subject), usually the user ID "42"
iat When it was issued (issued at), in seconds since 1970 1791968400 (2026-10-14 18:00 KST)
exp When it expires (expiration) 1791970200 (2026-10-14 18:30 KST)

You can also add claims of your own, such as role.

Signature

Section titled “Signature”

The signature is a value computed from the header and payload with a secret key only the server knows. When the server receives a token, it runs the same computation again and checks that the result matches the token’s signature.

If someone changes role in the payload to ADMIN, the signature has to be recomputed to match. Without the secret key, a matching signature can’t be produced. So a token with a valid signature can be trusted to be exactly what the server issued, and the server uses the details in it without looking anything up in a session store.

The signature only shows whether the token was changed; it doesn’t hide the contents. The header and payload are just characters converted with Base64URL, so anyone who converts them back can read the JSON. That’s why passwords and personal information don’t go in the payload.

Sessions and tokens compared

Section titled “Sessions and tokens compared”
Sessions Tokens (JWT)
What the server stores A session per logged-in user Nothing (just the secret key)
On each request Look up the session ID in the session store Check the signature and expiry
How the credential is sent Usually a cookie (automatically, by the browser) Usually the Authorization header (by the code)
Logout, forced logout Deleting the session ends it immediately The token stays valid until exp
When permissions change Applied from the next request Applied when a new token is issued
With multiple servers They need a shared session store Any server with the same secret key can verify

With multiple servers

Section titled “With multiple servers”

By default, sessions are kept in server memory. With two servers, if server A handles the login and server B handles the next request, server B doesn’t have that session. So a session store shared by all servers is used, such as Spring Session with Redis.

Tokens store nothing on the server, so any server holding the same secret key can verify them.

Logout

Section titled “Logout”

With sessions, once the server deletes the session, requests carrying that session ID are immediately no longer logged in.

With tokens, the server stores nothing, so it has no way to invalidate a token it has already issued. Even if the browser deletes the token, anyone who copied it can keep making requests with it until exp. That’s why tokens are given short lifetimes and paired with refresh tokens for getting new ones, which the next post covers.

Cookies and sessions

Section titled “Cookies and sessions”

“Using cookies means using sessions” isn’t true. Cookies are a way to send the credential; sessions and tokens are ways to remember the login state, and the two are chosen separately. A JWT can be sent in an HttpOnly cookie, and a session ID can be sent in a header. Where to keep a token and how to send it is also in the next post.

Summary

Section titled “Summary”
Sessions Tokens
Where the login state is kept On the server Inside the token
How the server recognises the user Looks up the session ID Verifies the signature and reads the contents
Good fit The page and API are on the same server, and logouts must take effect immediately There are several servers, or apps and other services call the same API

Neither is simply better; the choice depends on how the servers are set up and how quickly a logout has to take effect.
