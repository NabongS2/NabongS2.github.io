Nginx, from static files to an API proxy

Sep 28, 2026 - 11 min read
nabong

When one Java app that served both pages and an API is split into a frontend and a backend, two jobs appear that did not exist before: who serves the built frontend files, and who forwards the browser’s API requests to the backend. This post covers how those two jobs work in each environment, and how to do them on a server with Nginx.

Single application and split structure

Section titled “Single application and split structure”

A service built as one Spring Boot app has that one app receive every request. A request to / gets HTML built by the app; a request to /api gets JSON. One container, one address.

Build the frontend separately with React or Vue and things change. Running npm run build on the frontend produces a dist/ folder with index.html plus JS and CSS files. These are just files; they cannot receive requests on their own. Something has to serve them to the browser. The backend now handles only the API.

Single application Split structure
Pages The Java app builds and returns HTML Built files. A separate program has to serve them
API The Java app The backend
What runs One thing Two things

That raises two questions. Who serves the frontend files? And how does a /api request from the page reach the backend?

One address, split by path

Section titled “One address, split by path”

Put the pages and the API at different addresses and the browser gets in the way. A browser treats two addresses as the same origin only when the scheme, host and port all match. With the pages on :8080 and the API on :8100 the origins differ, and unless the backend sends back CORS headers, the browser will not let the page read the response. Passing login cookies back and forth gets complicated too.

So the usual setup is to put one program in front, collect everything under one address, and split by path.

From the browser’s side there is only one address, so there is no origin problem. The program in front looks at the path, forwards /api to the backend, and answers everything else with the frontend files. A program like this is called a reverse proxy.

Proxies and reverse proxies

Section titled “Proxies and reverse proxies”

A proxy is a program in the middle that receives a request on someone’s behalf, passes it on, and returns the response it gets back. The English word literally means acting on someone’s behalf.

Proxies split into two kinds by which side they sit on.

Proxy (forward proxy) Reverse proxy
Which side The requesting side. In front of the browser The receiving side. In front of the servers
Who knows it exists The browser is configured to use it The browser does not know. It thinks that address is the server
What it hides The requester. Servers see the proxy as the one asking The servers behind it. The browser never learns the backend’s address
Example The proxy a company network routes outbound traffic through Nginx forwarding /api to the backend

Plain “proxy” usually means the first kind, a forward proxy. What Nginx does in this post is act as a reverse proxy. The browser only knows app.example.com and has no idea the frontend files and the backend live separately behind it.

The proxy in setting names means the same thing. Nginx’s proxy_pass and the proxy in Vite’s config are both reverse-proxy settings that forward requests to the backend behind them.

Who does it in each environment

Section titled “Who does it in each environment”

That reverse proxy is a different program in each environment.

Serving the frontend files Forwarding /api
Local development The Vite dev server (npm run dev) server.proxy in vite.config.ts
Dev server · production Nginx Nginx’s proxy_pass

You can develop locally without Nginx because the Vite dev server does the same job. The dev server started by npm run dev serves the pages and forwards the paths listed under proxy in its config to the backend.

The backend runs separately, started from the IDE or Gradle. The browser only sees localhost:5173, and the dev server forwards anything starting with /api to localhost:8100.

The dev server is for development only. It includes features that reflect code changes on screen immediately, and it is not meant to be deployed. On a server, Nginx serves the dist/ built by npm run build.

Because the two environments do the same job with different config files, the path rules have to be written in both places. Add /auth to the forwarding rules in vite.config.ts, forget it in the Nginx config, and it works locally but returns 404 on the server.

Building dist

Section titled “Building dist”

The files Nginx serves are built from the frontend project. This assumes Vite.

npm ci instead of npm install installs the same versions every time. Use it when building on a server or in CI.

A finished build leaves a folder like this.

One index.html and a few bundled JS and CSS files. The string after each file name is derived from the contents, so rebuilding after a code change changes the names.

Build modes and environment variables

Section titled “Build modes and environment variables”

If dev and production settings differ, build with a mode. Building with --mode dev reads the .env.dev file.

Values starting with VITE_ are written into the JS files at build time. They are not read while running on the server, so changing one means rebuilding.

That is why it is easier to write the API address as a path only, like /api, rather than putting something like https://api.example.com in an environment variable. With the pages and the API at the same address, a path alone reaches the API, and the same build output works on the dev server and in production.

Putting it on the server

Section titled “Putting it on the server”

Put dist/ in the folder Nginx’s root points to. There are three ways.

Mount as a volume Copy into the image Build inside the image
Build npm run build outside the container npm run build outside the container Inside the Dockerfile
Image The official nginx image as is nginx + dist/ nginx + dist/
Deploying a new version Replace the host’s dist/ folder Build outside, then rebuild the image Rebuild the image
Build environment Can differ per PC or CI Can differ per PC or CI Fixed in the Dockerfile

Mounting as a volume means adding -v /opt/web/dist:/usr/share/nginx/html to docker run. The examples in “Connecting containers” below use this.

Copying into the image just puts a dist/ built elsewhere into the image.

The Dockerfile is short and the image is small. The catch is that the build machine needs Node, and different Node versions on different machines can produce different results.

Building inside the image splits the build and the runtime.

The first stage builds with Node; the second carries over only dist/ and the config. Neither Node nor the source code ends up in the final image. Splitting one Dockerfile into stages like this is called a multi-stage build.

Skip the stages and do both building and serving in a single node image, and Node, node_modules and the source code all stay in the final image, pushing it to hundreds of megabytes. None of that is used on the server.

Nginx configuration

Section titled “Nginx configuration”

A minimal config that serves the frontend files and forwards /api. With the official image it goes in /etc/nginx/conf.d/default.conf.

server and location

Section titled “server and location”

A server block is the set of settings for one port. The location blocks inside it decide what happens per path.

When a request path matches several locations, the longest match wins. /api/users matches both / and /api/, but the longer /api/ handles it. So / can stand for “everything else” and only the paths that need special handling get their own block.

Static files — root and try_files

Section titled “Static files — root and try_files”

root is the folder to look for files in. A request for /logo.png returns /usr/share/nginx/html/logo.png.

Without try_files, refreshing the page returns 404. Page addresses in a React or Vue app are not files. An address like /history/12 is something the JS in the browser created while changing the screen; there is no such file in dist/. Navigating inside the app works fine, but refresh at that address and the browser asks the server for a /history/12 file, which Nginx does not have.

try_files $uri $uri/ /index.html tries each in order.

Order Looks for Example: /logo.png Example: /history/12
1 $uri — a file with that name Found → returned Not found
2 $uri/ — a folder with that name Not found
3 /index.html Returned → the JS draws the /history/12 screen

API proxy — proxy_pass

Section titled “API proxy — proxy_pass”

proxy_pass forwards the request to the backend. upstream gives the backend address a name. You can also write the address directly, as in proxy_pass http://192.168.0.20:8100;.

Once requests go through Nginx, the client the backend sees is Nginx, not the browser. These four headers carry the original request’s details to the backend.

Header Carries
Host The domain the browser requested
X-Real-IP The browser’s IP
X-Forwarded-For The list of IPs along the way. The first is the browser
X-Forwarded-Proto Whether the browser came in over http or https

The backend reads these when it logs client IPs or builds redirect URLs. Leave them out and every request appears to come from Nginx’s IP.

Whether proxy_pass ends in / changes the path the backend receives. Follow a browser request for /api/users.

  • Without the /, the request path is passed along untouched. /api/users goes as is
  • With the /, the /api/ that matched the location is removed and replaced with the / written in proxy_pass. /api/ in /api/users becomes /, giving /users

Which one to use depends on the backend’s controller paths.

If the backend returns 404 while the Nginx log shows the request arriving, look here first.

Connecting containers

Section titled “Connecting containers”

With Nginx and the backend in separate containers, the question is what to write as the backend address in the Nginx config.

localhost does not work. Inside a container, localhost is that container itself. There is no backend inside the Nginx container, so the connection is refused.

There are two ways.

Using the host IP

Section titled “Using the host IP”

No Docker network needs to be created. Publish the backend’s port on the host with -p, and write the server’s IP and that port in the Nginx config.

Nginx goes out of its container to port 8100 on the server, and that port leads into the backend container. If the backend is on a different server, only the IP changes.

The IP to write is the server’s IP. A container IP like 172.17.0.x shown by docker inspect can change when the container is recreated, so it does not go in the config.

Using a Docker network

Section titled “Using a Docker network”

On the same Docker network, Docker resolves container names to addresses. Create a network and start both containers on it.

Here the backend does not need to publish its port with -p. The browser only goes through Nginx, and Nginx reaches the backend inside the network.

The difference

Section titled “The difference”
Host IP Docker network
Setup None docker network create
Address in the config 192.168.0.20:8100 backend-app:8100
Publishing the backend port Required Not needed
Backend on another server Works Does not. Same server, same network only
If the server’s IP changes The config has to change No effect

How to run the containers themselves is in the Docker post.

Checking and applying the configuration

Section titled “Checking and applying the configuration”

After editing the config, check the syntax first, then have Nginx reload it if the check passes.

Reload while nginx -t is failing and Nginx keeps running on the old config. When a change seems not to take effect, look at nginx -t first.

The official image sends its access and error logs to the container’s output, so docker logs shows them directly.

These are the response codes you will see most.

Code Meaning Where to look first
404 (only on refresh) No file for that page address try_files
404 (from the backend) The backend received a different path The / at the end of proxy_pass
502 Bad Gateway Nginx could not connect to the backend The backend address and port, whether the backend container is running
504 Gateway Timeout The backend did not answer in time How long the backend takes. The default wait is 60 seconds

Section titled “Command reference”
What you want Command / setting
