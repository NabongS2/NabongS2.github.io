Access tokens and refresh tokens

Oct 14, 2026 - 10 min read
nabong

SeriesLogin and authentication

  1. Cookies, localStorage, sessionStorage
  2. Sessions and tokens
  3. Access tokens and refresh tokens

The previous post said that with tokens the server stores nothing, so it can’t invalidate a token it has already issued. This post looks at splitting tokens into access tokens and refresh tokens to reduce that problem, and at where to keep the two tokens and how to refresh them.

The examples assume the page and the API are on the same origin. If they’re on different origins, the settings in the cookies post are also needed.

Why two tokens

Section titled “Why two tokens”

A single token lifetime is hard to get right.

Lifetime Upside Problem
Long (e.g. 14 days) Users don’t have to log in again A leaked token can be used by someone else for 14 days
Short (e.g. 30 minutes) A leaked token is useless after 30 minutes Users have to log in again every 30 minutes

So two tokens with different jobs are used.

Access token Refresh token
Job Proves the user on API requests Gets a new access token
Sent to Every API request Only the refresh request (/auth/refresh)
Lifetime Short (e.g. 15–30 minutes) Long (e.g. 1–2 weeks)
Format Usually a JWT A JWT or a long random string
Stored on the server No Yes (database, Redis)
  • The access token travels with every request, so it has many chances to leak. In exchange its lifetime is short, so a leak does damage only briefly.
  • The refresh token is sent only when refreshing, so it has few chances to leak. Because the server stores it, deleting it on the server makes it unusable immediately.

Since the refresh token is stored on the server, this approach adds some of the benefits of sessions to tokens. Requests don’t need a store lookup (access token), while logout is handled on the server (refresh token).

There’s no single right lifetime. A shorter access token means less damage if it leaks but more refresh requests; a longer refresh token means fewer logins but a longer window in which a leaked token can be used.

Sending tokens

Section titled “Sending tokens”

There are two ways to send a token to the server.

Authorization header Cookie
Who adds it The page code, on every request The browser, automatically
Does the page code need to hold the token Yes No (with HttpOnly it can’t even read it)
Is it attached to requests sent by other sites No It can be (blocked with SameSite)

As in the previous post, how the token is sent is chosen separately from whether you use sessions or tokens. A JWT can be sent in a cookie too.

Where to store tokens

Section titled “Where to store tokens”

On login you receive an access token and a refresh token, and you have to decide where in the browser to keep each. The options are localStorage, browser memory and an HttpOnly cookie.

Keeping something in browser memory means not writing it to browser storage, only to a JavaScript variable in the code running in the open tab. It isn’t on the server. When the page reloads or the tab closes, the code starts over and the value is gone.

Where Is it memory
A module variable (let accessToken), React state, a Zustand store Memory
A Zustand store using persist Not memory. persist saves the value to localStorage

Where a token is kept determines how dangerous an attack becomes.

XSS and CSRF

Section titled “XSS and CSRF”

A token becomes dangerous in two ways. Both are attacks from the cookies post.

The token is stolen (XSS): If an attacker hides a script in a post’s content, the script runs in the browser of any user who opens that post. The script reads the token and sends it to the attacker’s server.

The attacker then calls the API from their own computer with that token, acting as the user until the token expires.

The token is used without the user knowing (CSRF): The browser adds cookies to requests automatically. If the user opens the attacker’s site while logged in, that site can make a request to our server, and the user’s cookie goes with it. The attacker never learns the token’s value, but uses the token through the user’s browser.

Comparing storage locations

Section titled “Comparing storage locations”
Location Stolen (XSS) Used without the user knowing (CSRF) After a reload
localStorage Scripts can read it Not sent automatically, so not applicable Kept
Memory The variable is hard to reach Not applicable Gone
HttpOnly cookie Scripts can’t read it Sent automatically, so it must be blocked with SameSite and so on Kept

Each has trade-offs, so the two tokens go in different places.

Where each token goes

Section titled “Where each token goes”

The refresh token goes in an HttpOnly cookie. It’s valid for a long time, say 14 days, so if it’s stolen, new access tokens can be obtained for that whole period. So it goes in an HttpOnly cookie that scripts can’t read, and cookie attributes block it from being used without the user knowing.

  • SameSite=Strict: the cookie isn’t sent with requests that start from another site.
  • Path=/auth: the cookie is sent only with refresh and logout requests, not with other API requests.

The access token goes in memory or localStorage. The page code has to put it in the Authorization header of every request, so it has to be somewhere the code can read. In exchange it’s short-lived, say 30 minutes, so a stolen one is useless 30 minutes later.

Memory localStorage
Stealing it Hard Easy
Reload, new tab Gone, so it has to be fetched again with a refresh request Still there, used right away

No storage location stops XSS itself. While a script is running, it can send requests as the user even without reading the token. XSS is prevented by never inserting user input into HTML as is, and by limiting which scripts may run with a CSP (Content Security Policy) header.

CORS settings

Section titled “CORS settings”

The attacker’s site can also make the user’s browser call our server’s /auth/refresh. The attacker’s site and our server are different sites, so a SameSite=Strict cookie isn’t sent. Even with a setting that lets the cookie go along, the browser doesn’t show the response holding the new access token to the attacker’s site, because reading a response from another origin requires the server’s permission through CORS.

This protection holds only while the server allows CORS narrowly. If it allows every origin and also sends Access-Control-Allow-Credentials: true, the attacker’s site can read the response and take the new access token.

The CORS setting depends on where the page and the API live.

Page and API CORS setting
Same origin (Nginx or a dev server proxy forwards /api and /auth) Not needed. Leave it unset
Different origins (app.example.com and api.example.com) Allow only the page’s address

With Spring Security, this setting is applied with http.cors(Customizer.withDefaults()).

An example setup

Section titled “An example setup”

The examples in this post put everything above together like this.

Item Setup
Refresh token HttpOnly; Secure; SameSite=Strict; Path=/auth cookie
Access token Browser memory (a JavaScript variable). Fetched again from /auth/refresh after a reload
CORS Unset on the same origin; on different origins, allow only the page’s address
XSS Never insert user input into HTML as is, and set a CSP header

The access token also works in localStorage. That saves a refresh request on every reload, but if XSS happens, the token can be taken and used for the rest of its lifetime.

This is one way of setting things up where the page code handles the access token itself; there are others.

Setup What the browser holds Characteristics
This post’s setup Access token (memory), refresh token (HttpOnly cookie) The page code handles the access token
Both tokens in HttpOnly cookies Two cookies The page code never touches a token. Every API request needs CSRF protection
BFF (Backend for Frontend) One session cookie A server dedicated to the page keeps the tokens and calls the API on its behalf. No token in the browser, but one more server
Sessions A session ID cookie No tokens. Covered in the previous post

Refreshing tokens

Section titled “Refreshing tokens”

When the access token expires, the API returns 401. On that 401, the page code gets a new access token with the refresh token and sends the failed request again.

If the refresh request fails too, the refresh token has also expired, so the user is sent to the login page.

Issuing and refreshing in Spring

Section titled “Issuing and refreshing in Spring”
  • The access token goes in the response body; the refresh token goes in Set-Cookie.
  • @CookieValue reads a value from the request’s cookies. The refresh token is HttpOnly, so the page code never knows its value; the browser sends it as a cookie.
  • jwtProvider.createAccessToken is the JWT issuing code from the previous post.

Refresh token rotation

Section titled “Refresh token rotation”

rotate above checks the refresh token it receives, deletes it from the store and issues a new refresh token. Replacing the refresh token on every refresh like this is called refresh token rotation.

If a refresh token leaks and two people hold the same token, one of them refreshes first, and the other then sends a token that has already been deleted. When a deleted token comes back, the server can treat it as a sign that someone copied the token, delete all of that user’s refresh tokens and make them log in again.

With the access token in memory, it’s gone after a reload, so call auth.post('/refresh') once when the app starts to get an access token.

Logout

Section titled “Logout”

Logging out means making both tokens unusable.

Token On logout
Refresh token Deleted from the server’s store, and from the browser with a Max-Age=0 cookie
Access token Cleared from memory (or localStorage) by the page code

The Set-Cookie that deletes the cookie must have the same Path as when it was created to be treated as the same cookie.

The server can’t invalidate an access token it has already issued, so anyone who copied it can use it for the rest of its lifetime. That’s why access tokens are kept short-lived. If they must be blocked immediately, the server can keep a list of blocked tokens and check it on every request, but then every request needs a store lookup, which makes it much like sessions.

Summary

Section titled “Summary”
Access token Refresh token
Job Proves the user on API requests Gets a new access token
Lifetime Short Long
How it’s sent Authorization header Cookie (Path=/auth)
Where the browser keeps it Memory or localStorage HttpOnly cookie
Stored on the server No Yes
When it expires Get a new one with the refresh token Log in again
Logout Cleared on the page; usable for the rest of its lifetime Deleted on the server; unusable immediately

That covers the flow of tokens as seen from the page. How the server checks the token on every request and returns 401 or 403 is the subject of the next post, which implements it with Spring Security.
