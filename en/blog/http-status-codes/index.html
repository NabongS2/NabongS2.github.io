HTTP status codes and where an error came from

Oct 12, 2026 - 11 min read
nabong

When the browser sends a request, the server puts a three-digit number at the very start of its response. That number is the status code. This post covers what the common status codes mean, and how to find where an error came from when one shows up on the page.

Status codes

Section titled “Status codes”

The first line of a response looks like this.

Part Value Meaning
Protocol HTTP/1.1 The version of the protocol in use
Status code 404 How the request was handled
Reason phrase Not Found A human-readable name for the status code

The numbers and names are defined by the HTTP specification (currently RFC 9110). So every server uses 404 with the same meaning: “what you asked for wasn’t found”. Programs look only at the number; the name is there for people.

The 1xx to 5xx classes

Section titled “The 1xx to 5xx classes”

The first digit sorts status codes into five classes. Even for a code you’ve never seen, the first digit tells you whether it succeeded, or failed because of the request or the server.

Class Meaning Where to look
1xx A notice that processing continues Rarely seen. Mainly 101 when a connection switches to WebSocket
2xx Success Nothing wrong
3xx Redirection. A response telling the browser to request another address. 304 is a little different: it means use the stored copy Redirect settings, caching
4xx The request was wrong or not allowed The request. Address, values, login state, permissions
5xx The request was fine but the server couldn’t handle it The server. Backend logs, Nginx logs

Common status codes

Section titled “Common status codes”

2xx

Section titled “2xx”
Code Name When
200 OK A request such as a read or an update succeeded and there is a response body
201 Created A request that creates something (POST) succeeded
204 No Content It succeeded but there’s no body to return. Common for deletes

3xx

Section titled “3xx”
Code Name When
301 Moved Permanently The address has changed permanently; the client should request the new one. The http → https redirect in Nginx part 2
302 Found This request only is sent to another address. Sending a user who isn’t logged in to the login page
304 Not Modified Nothing changed, so the stored copy can be used. Not an error

A 3xx response carries the address to go to in the Location header. The browser requests that address next, so the developer tools show two lines for one request.

4xx

Section titled “4xx”
Code Name When
400 Bad Request The request values are wrong. Malformed JSON, a missing required value, a value of the wrong type
401 Unauthorized It isn’t known who is asking. Not logged in, no token, an expired token
403 Forbidden It’s known who is asking, but they aren’t allowed to make this request
404 Not Found Nothing exists at that address
405 Method Not Allowed The address exists but the method is wrong. A GET sent to an address that only takes POST
413 Content Too Large The request body is too large. A big file upload

5xx

Section titled “5xx”
Code Name When
500 Internal Server Error The backend threw an exception while handling the request
502 Bad Gateway A proxy in between (Nginx) didn’t get a valid response from the backend
503 Service Unavailable The server can’t take requests for now. Maintenance, overload
504 Gateway Timeout A proxy in between ran out of time waiting for the backend

Similar codes compared

Section titled “Similar codes compared”

401 and 403

Section titled “401 and 403”

Both reject the request, but for different reasons.

401 403
Meaning It isn’t known who is asking It’s known who is asking, but it isn’t allowed
Common cause Not logged in, expired token A regular user calling an admin API
Fix Log in again Get the permission, or use an account that has it

The name of 401 is Unauthorized, which is confusing; what it actually means is “not authenticated”. Lacking permission is 403. That’s why a frontend can send the user to the login page on 401, and show a “no permission” message on 403.

404 and 405

Section titled “404 and 405”

404 means the address doesn’t exist; 405 means the address exists but the method, such as GET or POST, doesn’t match. A 405 means the address was right, so compare the frontend’s request method with the backend’s @GetMapping or @PostMapping.

301 and 302

Section titled “301 and 302”

Browsers remember a 301. Once they get one, they go straight to the new address next time without asking the server. So a 301 set up by mistake stays in users’ browsers for a while even after you fix the configuration. If the redirect might change, use 302.

For sending a POST request to another address there are also 307 (temporary) and 308 (permanent). With 301 and 302 the browser may switch the request to GET; 307 and 308 keep the method and body as they were.

502 and 504

Section titled “502 and 504”

Both are returned by a proxy such as Nginx.

502 504
Meaning No valid response came back from the backend Time ran out waiting for the backend’s response
Common cause The backend is down, the address or port is wrong The backend takes too long, the backend hung
Time until it appears Usually immediately After proxy_read_timeout (60 seconds by default)

How long the error took to appear is a clue too. If it shows up immediately it’s likely a 502; after about a minute, likely a 504. The detailed cause is in the Nginx error log.

500 and 502

Section titled “500 and 502”

500 means the backend received the request and failed while handling it; 502 means the request never reached the backend, or the backend didn’t finish its response. With a 500 the backend log has the exception; with a 502 the backend log often has no trace of the request at all.

Finding where an error came from

Section titled “Finding where an error came from”

In a browser → Nginx → backend setup, an error comes from one of those three places. The same 404 needs a different fix depending on where it came from.

The Network tab in the developer tools

Section titled “The Network tab in the developer tools”

In the Network tab of the browser’s developer tools (F12), click the failed request and check three places.

Tab What to check
Headers The status code and name on the Status Code line, Content-Type
Response The response body. HTML or JSON
Timing How long the response took. To gauge whether it’s a 504

Comparing response bodies

Section titled “Comparing response bodies”

The same 404 comes with a different response body depending on where it came from.

An error response from Nginx is a short HTML page, with nginx shown at the bottom.

An error response from Spring Boot is JSON. Unless it has been customized, it looks like this.

Response body Came from Where to look
HTML with nginx shown Nginx Nginx configuration, Nginx error log
JSON with status, error, path Backend Backend log, controller paths
JSON in the project’s own format (code, message, etc.) The backend’s exception handling Backend log

The Server: nginx response header can’t tell them apart. When Nginx passes a backend response on, it drops the backend’s Server header and adds its own, so responses the backend made also show Server: nginx.

Two 404 cases come up often. A 404 for a frontend file (/assets/index-3f9a1c2e.js) means the deployed dist and the browser’s index.html don’t match; a JSON 404 for an API (/api/...) means the address the frontend called differs from the backend’s path.

Browser errors

Section titled “Browser errors”

A request the browser blocked, or one that never reached the server, has no status code, or has one but the page’s code can’t read the response. The Status column in the Network tab shows something other than a number.

Shown in the Network tab Meaning Where to look
(failed) net::ERR_CONNECTION_REFUSED No server is running at that address and port Whether the server or container is up, whether the port is right
(failed) net::ERR_CERT_AUTHORITY_INVALID The certificate isn’t trusted Whether it’s a self-signed certificate, the certificate settings
CORS error The browser blocked a response that came from somewhere other than the page. See below Whether the page and the API use the same address

CORS errors

Section titled “CORS errors”

The console message

Section titled “The console message”

When a page on localhost:5173 calls a backend on localhost:8000 directly in local development, the browser console shows a message like this.

It means the page opened on 5173 tried to read a response from 8000, and the browser blocked it because there was no sign that this was allowed. The backend responded normally, but the page treats it as a failure.

The same-origin policy

Section titled “The same-origin policy”

The browser blocks the response for security.

Say you’re logged in to a bank site, bank.example.com, and open evil.example.com in another tab. If JS on evil.example.com runs fetch('https://bank.example.com/api/account'), the browser automatically attaches your login cookie to the request to bank.example.com. If JS on evil.example.com could read that response, your account details would go straight to it.

So browsers have a basic rule: JS on a page can only read responses from the same origin as the page. This rule is called the same-origin policy.

CORS

Section titled “CORS”

There are legitimate cases where a page needs to read a response from another origin. CORS (Cross-Origin Resource Sharing) is how the server explicitly allows that.

If the server adds an Access-Control-Allow-Origin: http://localhost:5173 header to its response, the browser treats this page as allowed to read it and hands it over. Without that header, it blocks the response. That’s a CORS error.

So a CORS error isn’t a server error; it’s the browser following a security rule and not handing the response to the page’s code. The backend has already sent its response, so the backend log may show the request as normal (200).

Origin

Section titled “Origin”

The browser decides “is this the same place?” by origin. The origin is just the protocol, host and port taken from a URL; the path and query aren’t part of it.

Covers Example
URL The whole address. Protocol, host, port, path, query http://localhost:5173/history/12?tab=info
Origin Protocol, host, port http://localhost:5173

If all three match it’s the same origin; if any one differs it’s a different origin. With the page open on http://localhost:5173, here is how different API addresses compare.

API address Origin What differs
http://localhost:5173/api/users same only the path
http://localhost:8000/api/users different port (5173, 8000)
https://localhost:5173/api/users different protocol (http, https)
http://192.168.0.20:5173/api/users different host

localhost:5173 and localhost:8000 are the same machine, but their ports differ, so they are different origins. That’s the case in the console message above.

Fixes

Section titled “Fixes”
Approach What it does Example
Make it the same origin Take the page and the API at one address and forward to the backend inside the server Vite proxy, Nginx proxy
Allow it on the server The backend adds an Access-Control-Allow-Origin header to its responses Spring’s @CrossOrigin, CORS configuration

The first approach is the setup from Nginx part 1. The page’s code writes only a path, like fetch('/api/users'), and the browser sends it to the same address as the page. Forwarding to the backend happens inside the server, in Nginx, so the browser never knows about it.

From the browser’s point of view it only ever talked to app.example.com, so CORS never comes into play. The Vite proxy in local development works the same way: a request from the page on localhost:5173 to /api is received by the Vite dev server and forwarded to 8000.

Checks by symptom

Section titled “Checks by symptom”
Symptom Likely Check first
Sent straight back to the login page right after logging in 401 Whether the token goes out in the request header, its expiry
Only certain menus won’t open 403 Account permissions
Fails only on the save button 400, 405 The values sent, the request method
Blank white page right after a deploy Static file 404 The browser’s old index.html, the dist deploy
Every API fails immediately 502 Whether the backend is up, the backend address in Nginx
One API fails after about a minute 504 That API’s processing time, proxy_read_timeout
Only file uploads fail 413 Nginx client_max_body_size
CORS error with no number CORS The origins of the page and the API
