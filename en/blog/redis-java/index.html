Using Redis from Spring

Sep 28, 2026 - 9 min read
nabong

SeriesRedis

  1. Redis, from the idea to data types and commands
  2. Connecting to a Redis container and checking its state
  3. Using Redis from Spring

What Redis is and how to look at it in redis-cli is in the earlier post. This one covers how to use Redis from Spring.

Dependency and connection settings

Section titled “Dependency and connection settings”

If the Redis has a password, set password. Do not write it into the config file as is; take it from an environment variable. Leave it out and the first command fails with NOAUTH; get it wrong and the connection fails with WRONGPASS.

These are the settings you will use most.

Setting Meaning Default
host Redis address localhost
port Port 6379
password Password none
database Database number. Used when several apps share one Redis by number (0–15) 0
timeout How long to wait for a single command’s reply 60 seconds
connect-timeout How long to wait while first establishing a connection 10 seconds

Leave timeout out and it is 60 seconds. If Redis stalls, requests wait that long along with it. A short timeout fails fast when something goes wrong, but a command that legitimately takes a while can also fail partway. Decide by how long the commands your app sends actually take. A bare number like 3000 is read as milliseconds.

In Spring Boot 2.x the setting was spring.redis.host. In 3.x it became spring.data.redis.host. If the old name is still there, the value is not applied and the app tries localhost:6379 and fails.

With the starter on the classpath, a StringRedisTemplate is created for you. Inject it.

opsForXxx and Redis data types

Section titled “opsForXxx and Redis data types”

RedisTemplate and opsForXxx() are names Spring Data Redis chose, not Redis. What Redis defines is the commands — SET, HSET and so on — and the job of actually sending them belongs to the driver underneath, Lettuce (the Spring Boot default). Spring Data Redis sits on top, handles connections and serialization, and groups the commands by data type into methods.

Method Returns Redis data type
opsForValue() ValueOperations String
opsForHash() HashOperations Hash
opsForList() ListOperations List
opsForSet() SetOperations Set
opsForZSet() ZSetOperations Sorted Set

The first row is the confusing one. What Redis calls the String type, Spring calls Value. The rest share the same names.

Commands that act on a key regardless of its data type, like DEL, EXPIRE and TYPE, sit directly on the template: redis.delete(), redis.expire().

You can chain onto opsForXxx() every time. With opsForHash(), though, chaining leaves the field and value types as Object. The types are taken from the variable that receives the result, and a chained call has no such variable.

Assign it to a variable once and the types are fixed.

The others — opsForValue(), opsForList() and so on — use the template’s types as they are, so chaining them needs no cast.

Serialization

Section titled “Serialization”

Inject a plain RedisTemplate instead of StringRedisTemplate and the keys and values become unreadable in redis-cli.

This is what redis-cli shows.

Even the key name is unrecognizable.

That is because RedisTemplate serializes with JDK serialization by default. It turns Java objects into bytes, so outside Java the data can neither be read nor found under the same key.

StringRedisTemplate stores keys and values as plain strings.

When you need to store a whole object, serialize it to JSON and store the string. Then redis-cli can read it too.

Stored as a string, the value can be read directly in redis-cli or a GUI tool. You need that when checking whether something like a session went in wrong. A value stored with JDK serialization can only be read through Java code.

String

Section titled “String”

A missing key starts from 0. A second argument raises it by that much. The return value is a Long, and Redis stores it as a string.

Calling it on a key that holds something other than a number is an error — for example increment on session:a1b2c3, which holds "user=1000".

Hash

Section titled “Hash”

HashOperations<H, HK, HV> takes three type arguments: the key type, the field type and the value type, in that order.

List

Section titled “List”

For a list of recent items, trim right after pushing.

Set

Section titled “Set”

There are two ways to check membership, and the gap grows with the number of members.

isMember takes about the same time whether there are ten members or a million. A Set goes straight to the value internally instead of walking from the start. With members, a million members means a million values over the network before the search even starts.

Sorted Set

Section titled “Sorted Set”

reverseRange returns only the values; reverseRangeWithScores includes the scores. A leaderboard has to show scores too, so the second one is the usual pick.

Expiry

Section titled “Expiry”

getExpire returns -1 for a key with no expiry and -2 for a key that does not exist.

Setting the expiry together with the value is safer. Call set and then expire separately, and an exception or a dead process in between leaves a key with no expiry.

What happens to the expiry when you change a value depends on the data type. Overwriting a String with set clears the expiry it had. To keep an expiry, pass it again when you overwrite.

Changing a Hash field with put does not touch the key’s expiry. The expiry time you set stays as it was.

Key lookup

Section titled “Key lookup”

redis.keys() looks like an ordinary method, but it sends the KEYS command as is. KEYS walks every key in the database, not just the ones matching the pattern, and Redis handles no other command while it does. The concepts post said KEYS * is not used in production; adding a pattern like session:* does not narrow what gets walked. The reason is in Commands are lined up and handled one at a time in the concepts post.

Application code rarely needs to find keys. It knows the ID, so it builds the key and reads it directly. When you need a list, do not search for keys — store the list as well when you store the data. If you need the list of active sessions, it looks like this.

Reading the list means reading sessions:active alone. It does not matter how many other keys the same Redis holds.

One catch: Set members have no expiry. When the session key expires after 30 minutes, its ID is still in sessions:active. Remove IDs whose session key is gone when you read the list, or clean them up periodically.

When you occasionally have to walk the keys — checking keys in production, or cleaning up old keys in bulk — use scan(). It fetches in small pieces, so Redis keeps serving other commands.

Close the Cursor when you are done so its connection is released.

Concurrent updates

Section titled “Concurrent updates”

To raise a number, use increment instead of reading with get and writing back with set. With more than one server, the latter drifts.

Here is visit counting without increment. Do not write it this way.

On a single server there is no problem. With two servers running this at the same time, it goes like this.

Step Server A Server B Value in Redis
1 get → 10 10
2 get → 10 10
3 set 11 11
4 set 11 11

Two increments, and the value is 11. Both read 10 before either wrote.

increment does the read, the add and the write inside Redis as a single command. Redis handles commands one at a time, so nothing can slip in between the two servers’ increment calls, and the result is 12.

Storing an object as one JSON string, then get, change a field, set, has the same problem. One server overwrites the field another just changed with the old value. For an object whose fields change separately, store it as a Hash and write only that field with opsForHash().put(). The concepts post shows this as a diagram in JSON string, or a data type.

A number inside JSON cannot use increment. Take settings stored as one JSON blob, with a version raised by one on every save.

To Redis this value is one string, not a number, so increment cannot raise just the version field. If two people save the same settings at nearly the same time, the table above plays out. Both read version 5 and both write 6. On top of that, the JSON saved last overwrites everything saved first. One person’s changes are gone, and since the version went up only once, nothing shows it was saved twice.

To prevent it, send the version the screen read along with the save request, and compare it with the current version before saving. If they differ, someone saved in between, so reject the save. This is called optimistic locking.

A small gap still remains between the comparison and the set. If two requests pass the comparison at once, one still overwrites the other. Closing that gap means doing the comparison and the save inside Redis in one go: watch the key with WATCH and cancel the save if it changed in between, or run the comparison and the save as a Lua script that behaves like a single command. Where simultaneous saves are rare, such as an admin screen, the comparison above is usually enough.

redis-cli commands and their methods

Section titled “redis-cli commands and their methods”
What you want redis-cli Java
Store a value SET k v opsForValue().set(k, v)
With an expiry SET k v EX 1800 opsForValue().set(k, v, Duration.ofMinutes(30))
Read a value GET k opsForValue().get(k)
Increment a number INCR k opsForValue().increment(k)
Set an object field HSET k f v opsForHash().put(k, f, v)
Read a whole object HGETALL k opsForHash().entries(k)
Append to a list RPUSH k v opsForList().rightPush(k, v)
Slice a list LRANGE k 0 9 opsForList().range(k, 0, 9)
Cap a list’s length LTRIM k 0 9 opsForList().trim(k, 0, 9)
Add to a set SADD k v opsForSet().add(k, v)
Is it in there SISMEMBER k v opsForSet().isMember(k, v)
Add with a score ZADD k 120 v opsForZSet().add(k, v, 120)
Top 10 ZREVRANGE k 0 9 opsForZSet().reverseRange(k, 0, 9)
Set an expiry EXPIRE k 1800 expire(k, Duration.ofMinutes(30))
Time remaining TTL k getExpire(k, TimeUnit.SECONDS)
Delete DEL k delete(k)
Check the data type TYPE k type(k)
Find keys SCAN 0 MATCH k* scan(ScanOptions)
