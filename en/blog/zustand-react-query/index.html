Zustand and React Query

Oct 13, 2026 - 13 min read
nabong

SeriesWorking with API data

  1. Synchronous and asynchronous
  2. fetch and axios
  3. Zustand and React Query

The React hook basics post used props and useContext to pass values between components. When several components need to share the same value, you can manage it with a state management library instead of React’s built-in features. Data received from a server can likewise be managed with a library made for it.

This post covers two of those libraries, Zustand and React Query. It looks at how the two differ and how to use each.

Client state and server state

Section titled “Client state and server state”

The values a page keeps fall into two kinds, depending on where the data is stored.

  • Client state: data stored only in the browser. Whether the sidebar is open, which tab is selected, what’s typed in the search box. It’s fine for it to disappear on reload, and the server doesn’t know about it.
  • Server state: data stored in the server’s database. The page fetches it and displays it. A list of posts, user details and order statistics are examples.

What makes server state different

Section titled “What makes server state different”

Client state doesn’t change unless you change it. Server state does. While the page is showing the data it fetched, another user may write a post; the data on the server changes, and the data the page holds becomes out of date.

So server state comes with work that client state doesn’t have.

  • Showing whether it’s still loading or has failed
  • Requesting only once when several screens use the same data
  • Deciding the fetched data is out of date and requesting it again
  • Fetching related lists again after changing data

The two kinds of state are handled by different libraries.

Libraries Covered in this post
Client state Redux, Zustand, Jotai, etc. Zustand
Server state React Query, SWR, RTK Query, etc. React Query

Zustand

Section titled “Zustand”

Zustand is a state management library for client state. It keeps values in a store outside the components, and several components take values from that store and share them.

Libraries that do the same job differ in how they gather values together.

  • Store-based: the app’s state is gathered in an object called a store. Redux and Zustand work this way. Redux sets a rule that values change through actions (objects describing what to do) and reducers (functions that take an action and produce the new state); Zustand changes them directly with functions inside the store.
  • Atom-based: an atom is the smallest unit, one that can’t be split further. Each value shared by several components is made into its own atom, and each component picks only the atoms it needs. Jotai works this way.

Which one is more convenient depends on how the shared values relate to each other.

Atom-based Store-based
How the values relate Each changes on its own Changing one changes others too
Example Theme, font size, sidebar open A cart’s item list, count and total

Changing the theme leaves the font size alone, so each value can simply be its own atom. In a cart, adding one item has to change the list, the count and the total together. With the three values and a function such as addItem in one store, changing all three when an item is added is handled in that one function.

Creating a store

Section titled “Creating a store”

A store is an object that gathers values and the functions that change them in one place. You create it with create.

  • set is the function that changes the store’s values. The object you pass is merged into the existing state. Unlike setState from useState, you don’t spread the remaining values in yourself.
  • If you need the previous value, pass a function: set((state) => ...).

Using it in a component

Section titled “Using it in a component”

The useSidebarStore that create returns is a hook, starting with use like useState. Call it inside a component and pass a function that picks the value you need, and you get that value back.

The two components don’t need to be parent and child. Each takes what it needs from the store instead of receiving props, so the props drilling seen in the React hook basics post doesn’t happen.

Selectors

Section titled “Selectors”

A function such as (state) => state.isOpen, which picks the value you need out of the store, is called a selector. A component re-renders only when the value its selector returns changes.

In the example above, pressing toggle changes isOpen and only Sidebar re-renders. The toggle function that SidebarButton picked is unchanged, so it doesn’t re-render.

Taking the whole store without a selector loses this benefit.

Picking values one at a time is all you need. Only when you pick several values bundled into one object or array is there something to watch for.

This selector makes a new object with { ... } every time it’s called. Zustand compares the selector’s result with the previous one using ===, and a new object is a different object every time even when the values inside are the same, so Zustand decides the value has changed. In Zustand v5, this repeats and can end in a Maximum update depth exceeded error.

In that case, wrap the selector in useShallow. Instead of comparing the object as a whole, useShallow compares the values inside one by one, and if they’re all the same it hands back the previous object.

Section titled “Using it outside a component”

Sometimes a store’s value has to be changed somewhere that isn’t a component. For example, when an API request function hits an error, you may want to record it in a store and have one place on the page show an error dialog based on that value.

Compared with useContext

Section titled “Compared with useContext”

Sharing values across several components is something useContext does too. There are two differences.

useContext Zustand
Setup Must wrap with a Provider Just create
What re-renders Every component using that Context when value changes Only components whose selected value changed

Here’s an example of the second difference: an app that shares the logged-in user (user) and the number of items in the cart (cartCount). UserName at the top of the page uses only user, and CartBadge uses only cartCount.

When an item is added to the cart and cartCount changes, this happens.

useContext Zustand
CartBadge Re-renders Re-renders
UserName Re-renders (even though user is unchanged) Doesn’t re-render

useContext only looks at whether the value object changed, so every component using that Context re-renders even when the value it uses is the same. Zustand compares what each selector returns and re-renders only the components whose value changed.

So values that rarely change, such as the logged-in user or the theme, are fine in useContext. For something that changes often and is shared by several components, such as the cart count, useContext re-renders components that don’t even use it every time, while Zustand re-renders only the components that use it.

React Query

Section titled “React Query”

React Query is a library that fetches server state, keeps it in a cache and manages when to fetch it again. Its current name is TanStack Query, and this post is based on v5.

How it differs from axios

Section titled “How it differs from axios”

axios and the browser’s fetch are HTTP clients. All they do is send requests to a server and receive responses (fetch and axios post). React Query doesn’t send requests itself. The function you hand it sends the request, and React Query manages when to request and where to keep the result.

axios, fetch React Query
What it does Sends requests and receives responses Keeps responses in a cache and decides when to request again
What it knows about Address, headers, request body Query keys, the cache, where the data is used on the page

That’s why the two are used together. In the code below, the part that sends the request is axios.

useQuery

Section titled “useQuery”
  • queryKey: the name of this data. Covered below.
  • queryFn: the function that fetches the data. It just needs to return a Promise.
  • isPending: there is no data yet.
  • isError: the request failed. By default, a failed request is retried three more times before it gets here.

You don’t need separate useState values for loading and failure.

To use React Query, wrap the app once in a QueryClientProvider. The cache lives inside the QueryClient created here.

Query keys and the cache

Section titled “Query keys and the cache”

A cache is storage that keeps fetched data so it can be used again later. React Query tells cache entries apart by their query key.

  • When several components use the same query key, only one request goes out. They all share the data it returns.
  • A query key is an array, and it includes the request’s conditions too, because different conditions mean different data.

If a value queryFn uses is left out of the query key, the key stays the same when the condition changes, and the data for the old condition keeps showing. Every value used inside queryFn goes in the query key.

staleTime and gcTime

Section titled “staleTime and gcTime”

Data in the cache has two timers.

  • staleTime: how long fetched data counts as fresh. After that, the data is stale (out of date).
  • gcTime: how long to wait, once no component uses the data any more, before removing it from the cache.
Default Longer Shorter
staleTime 0 Fewer requests, but old data is shown for that long even if the server has changed Always close to fresh, but more requests
gcTime 5 minutes Reopening a screen can show cached data right away, but uses more memory Uses less memory, but reopening loads from scratch

With the default staleTime of 0, data is stale as soon as it arrives. Stale data is requested again when:

  • a component using that query appears on screen
  • the browser window gets focus again
  • the network reconnects

While it’s being requested again, the data already in the cache is shown first. So isPending is false, and whether a request is in flight is shown by isFetching.

For data that rarely changes (code lists, settings), a longer staleTime cuts down requests. How long to set it depends on how often the data changes and whether showing old values for a moment is acceptable.

useMutation and invalidation

Section titled “useMutation and invalidation”

Requests that create, change or delete data use useMutation. Unlike useQuery, it doesn’t run when the component appears; it runs when you call mutate.

After a new post is written, the cached list of posts is out of date. That’s when you invalidate the query with invalidateQueries. To invalidate means to mark as no longer valid: it marks the cached data as stale and, if the page is currently using it, requests it again right away.

Invalidating with queryKey: ['posts'] targets every query that starts with ['posts']. ['posts', { page: 1 }] and ['posts', { page: 2 }] are invalidated together.

Name changes between v3 and v5

Section titled “Name changes between v3 and v5”

Up to v3 the package was called react-query; from v4 it’s @tanstack/react-query. When reading code in older projects, these names differ.

v3 (react-query) v5 (@tanstack/react-query)
useQuery('posts', fetchPosts, options) useQuery({ queryKey: ['posts'], queryFn: fetchPosts })
isLoading (no data yet) isPending
cacheTime gcTime
invalidateQueries('posts') invalidateQueries({ queryKey: ['posts'] })
onSuccess, onError on useQuery Removed; still on useMutation

Using them together

Section titled “Using them together”

When using both libraries, there’s one rule for deciding: if the data is stored only in the browser, it goes in Zustand; if it’s stored on the server, it goes in React Query.

Not copying server data into a store

Section titled “Not copying server data into a store”

Some code takes the data from useQuery and puts it into a Zustand store again in onSuccess or useEffect. The intent is to use it in several components, but it leaves the same data in two places, the cache and the store.

  • When invalidation brings new data into the cache, the copy in the store stays as it was.
  • Finding out which one is current means tracing through the code.

To use the data in several components, call useQuery with the same query key. Only one request goes out and the cache is shared. Wrapping it in a hook like useOrderStats above means the query key isn’t written out in several places.

Real-time data

Section titled “Real-time data”

Not all server state suits React Query. React Query is built around data you request. Data the server keeps pushing over a WebSocket, such as chat messages or live prices, has no moment when you request it.

For data like this, you either put incoming messages into a Zustand store for the page to subscribe to, or change the React Query cache directly with queryClient.setQueryData. If a page fetches the initial list with a request and then receives only changes over the WebSocket, changing the cache keeps it all in one place; if a page is filled only by messages with no request, keeping it in a store is simpler.

Summary

Section titled “Summary”
Zustand React Query
State it handles Client state Server state
Where the data is stored Browser Server
How values change set Request the server, then invalidate
What re-renders Components whose selected value changed Components using that query key
Examples Sidebar open, selected tab, chosen range Post list, user details, statistics by range

Sending requests is the job of axios or fetch; caching the results and deciding when to fetch again is React Query’s job. Values that live only in the browser go in Zustand, and when you use such a value as a request condition, you put it in the query key.
