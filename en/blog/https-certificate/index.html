HTTPS and certificates

Oct 29, 2026 - 17 min read
nabong

SeriesNetwork basics

  1. Network layers
  2. IP addresses and ports
  3. NAT and port forwarding
  4. VPN
  5. DNS and domains
  6. HTTPS and certificates

The previous post looked at how a domain is turned into an IP through DNS. But connecting to the IP that DNS returned doesn’t tell you whether that server really belongs to the domain, or whether someone in between is reading the traffic. This post looks at how HTTPS solves this problem, and what the certificate at its center is and how it is verified.

HTTP and HTTPS

Section titled “HTTP and HTTPS”

HTTP sends requests and responses as plain text, without encryption. Between the browser and the server there are many devices, such as routers and the internet provider’s equipment, as well as other devices on the same Wi-Fi. Anyone on this path can see HTTP requests.

Risk What happens
Eavesdropping Login passwords, cookies and request contents are read in transit
Tampering Another script is inserted into the response, or its contents are changed
Impersonation A fake server responds as if it were the real server

HTTPS sends HTTP wrapped in TLS. As covered in network layers, TLS (Transport Layer Security) is the protocol that encrypts data and uses a certificate to check that the server you connected to is the real one. It addresses each of the three risks above.

What TLS does Risk it prevents
Encryption Eavesdropping. Devices in between see only the IP and port, and can’t read the request path or contents
Integrity check Tampering. Data changed in transit is treated as an error by the receiver
Server authentication Impersonation. The certificate is used to check that the server you connected to owns the domain

The default port for HTTPS is 443, and addresses start with https://. TLS was previously called SSL, so ssl still appears in many configuration entries and tool names.

Public and private keys

Section titled “Public and private keys”

Understanding certificates starts with the two kinds of keys TLS uses. The two keys are created as a pair, and what one key does is checked with the other.

Key Held by What it does
Private key Only the server Signs data. A signature is a mark meaning “the owner of this private key produced this data”
Public key Anyone; it is published Checks whether a signature made with the private key is valid

A signature can be checked only with the matching public key, and the private key can’t be derived from the public key. So when the server sends data signed with its private key, the receiver checks it with the public key and knows that the data came from the server holding the private key.

If the private key leaks, someone else can pose as that server. The server’s private key file has restricted permissions and is not put into repositories or images.

Certificates

Section titled “Certificates”

A public key alone doesn’t tell you whose public key it is. A fake server can also send its own public key and claim it is the public key of app.example.com. So a file in which a trusted organization has confirmed and signed “this public key belongs to this domain” is sent along with it. This file is a certificate, and the organization that signs it is a certificate authority (CA).

Field Content Example
Subject The owner of the certificate CN=app.example.com
Subject Alternative Name (SAN) The list of names this certificate can be used to connect with app.example.com, www.example.com
Issuer The certificate authority that signed it CN=R11, O=Let's Encrypt
Validity period Start and expiry dates 2026-10-01 ~ 2026-12-30
Public key The pair of the server’s private key
Signature The issuer’s signature over all of the above

The browser checks whether the domain it connected to is in the SAN (Subject Alternative Name). The subject’s CN was once used for name checks, but browsers now look only at the SAN. The SAN can also hold a wildcard such as *.example.com, and this name matches subdomains one level down, such as api.example.com. It does not match example.com itself or a.b.example.com.

Certificate authorities and the certificate chain

Section titled “Certificate authorities and the certificate chain”

Certificate authorities are usually split into two levels.

Type What it does Where it is kept
Root CA Signs the certificates of intermediate CAs The root certificate is included in the OS and browser trust store from the start
Intermediate CA Signs server certificates The server sends it along with its own certificate

A trust store is a list that says “certificates that lead to these root certificates are trusted”. Windows, macOS, Linux, Firefox and Java each have their own list.

The line of signatures from the server certificate through the intermediate certificate up to the root certificate is called the certificate chain. The chain is complete only when the server sends both its own certificate and the intermediate certificate. This is why Nginx uses a file with the two certificates joined together (fullchain), and the setup is covered in the Nginx post.

Certificate verification

Section titled “Certificate verification”

When the browser receives the server certificate, it checks the items below. If any one of them fails, it stops the connection and shows a warning.

Check What is checked
Chain Whether following the signatures reaches a root certificate in the trust store
Name Whether the domain or IP in the address bar is in the SAN
Validity period Whether the current time is between the start and expiry dates
Private key Whether the server holds the private key that pairs with the certificate’s public key. This is checked in the handshake below

TLS handshake

Section titled “TLS handshake”

Before sending an HTTP request, the browser and the server first go through a process that checks the certificate and decides the keys used for encryption. This process is called the TLS handshake. In short, for TLS 1.3, the order is as follows.

  1. The browser sends the TLS versions and cipher suites it supports, values for key exchange, and the domain name it wants to connect to. This domain name is called SNI (Server Name Indication).
  2. The server sends the certificate and chain that match the SNI domain, and its values for key exchange. It also signs the handshake messages exchanged so far with its private key and sends the signature.
  3. The browser checks the items from “Certificate verification” above, and checks the signature with the certificate’s public key. If the signature is valid, the other side is the server holding that certificate’s private key.
  4. The browser and the server each calculate the same session key from the key exchange values exchanged in steps 1 and 2. The session key itself is not sent over the network.
  5. After that, HTTP requests and responses are encrypted with the session key and exchanged.

The session key is used for symmetric encryption, which encrypts and decrypts with the same single key. Public key cryptography takes a lot of computation, so it is used only for checking the server and exchanging keys, and the actual data is handled with symmetric encryption.

Because of SNI, the server can choose a different certificate for each domain even when several domains share one IP. Nginx compares the SNI domain with server_name and sends the certificate of that server.

Certificate types

Section titled “Certificate types”

Certificates fall into three types depending on who signed them. The difference is which trust store holds the root certificate used to check that signature.

Type Signed by Trusted by Used for
Public certificate A public certificate authority (Let’s Encrypt, DigiCert, Sectigo and others) Every OS and browser. The root certificates are included from the start Services open to the internet
Private CA certificate A certificate authority the company or team created itself Only PCs and servers where that private CA’s root certificate is installed Internal network servers, development servers
Self-signed certificate The certificate itself Only PCs where that certificate is installed directly. Without it, the warning has to be bypassed on every connection Development environments with few servers, testing

All three types use the same encryption. What differs is whether the browser can check the server, and if it can’t, a warning appears.

Issuing a public certificate

Section titled “Issuing a public certificate”

Before issuing a certificate, a public certificate authority checks that the applicant manages the domain. Let’s Encrypt, a free certificate authority, handles this check and the issuance with an automated issuance protocol called ACME.

Challenge What it does Requirement
HTTP-01 You place a value given by the certificate authority at the path http://domain/.well-known/acme-challenge/, and the certificate authority connects to that address to check it The domain must be reachable on port 80 from the internet
DNS-01 You register a value given by the certificate authority as a TXT record for the domain, and the certificate authority checks it through DNS You must be able to edit the DNS records. The server doesn’t need to be open to the internet. Wildcard certificates can be obtained only this way

Let’s Encrypt certificates are valid for 90 days, so automatic renewal is set up along with them. Tools that use ACME include Certbot and acme.sh, and web servers such as Caddy handle issuance and renewal themselves. Paid certificates with longer validity periods also exist, but the maximum validity period of public certificates is getting shorter, so either way a renewal procedure needs to be in place.

Issuing certificates with a private CA

Section titled “Issuing certificates with a private CA”

Internal network servers often can’t get a public certificate, because they can’t be reached from the internet or have no public domain. In this case, you create a private CA, issue certificates with it, and install its root certificate on the PCs that will use them. Below is the order for creating one with openssl.

File Content Where it goes
ca.key The private CA’s private key Kept separately in a secure place
ca.crt The private CA’s root certificate The trust store of the PCs and servers that connect
server.key, server.crt The server’s private key and certificate Web server configuration (Nginx’s ssl_certificate_key, ssl_certificate)
server.csr Certificate signing request. Not used after signing

A CSR (Certificate Signing Request) is a file that holds the server’s public key and name and asks a certificate authority to sign it. The same format is used when obtaining a public certificate.

How to install ca.crt in the trust store differs by OS.

Environment How to install
Windows certutil -addstore -f Root ca.crt with administrator rights, or open the certificate file and install it in “Trusted Root Certification Authorities”
macOS sudo security add-trusted-cert -d -r trustRoot -k /Library/Keychains/System.keychain ca.crt
Ubuntu, Debian Copy ca.crt to /usr/local/share/ca-certificates/, then sudo update-ca-certificates
Firefox Uses its own trust store, so import it separately in the certificate manager in settings
Java applications Add it to the JDK’s trust store with keytool -importcert

Whoever has ca.key can create a certificate for any domain, and PCs with ca.crt installed trust all of those certificates. So ca.key is managed more strictly than a server certificate’s private key. The details are in Risk on PCs with a root certificate installed.

Generating a self-signed certificate

Section titled “Generating a self-signed certificate”

A self-signed certificate is created together with its private key in a single command, without a CA. The certificate is signed with its own private key, so the receiver has no root certificate to check it against. As a result, a warning appears on PCs where that certificate hasn’t been installed directly.

basicConstraints on the last line is the field that sets whether this certificate is a CA that can sign other certificates. openssl req -x509 adds CA extensions in its default configuration, so without this field the certificate is created with CA:TRUE. The step 1 command that created the private CA’s root certificate also gets CA:TRUE for the same reason. The reason for specifying CA:FALSE is in Risk on PCs with a root certificate installed.

Self-signed certificates and private CAs compared

Section titled “Self-signed certificates and private CAs compared”

With both approaches, the server holds the same two files: a private key and a certificate. A private CA adds the CA’s private key and root certificate. The root certificate is installed on the connecting side, and the CA’s private key is not placed on the server.

File Self-signed Private CA
server.key (the server’s private key) Server Server
server.crt (the server’s certificate, including the public key) Server Server
ca.crt (root certificate) None The trust store of the connecting PCs and servers
ca.key (the CA’s private key) None Kept separately somewhere other than the servers and PCs, and used only when issuing certificates

To connect without a warning, a certificate has to be added to the trust store of each connecting PC. Which certificate is added, and when it has to be added again, differs between the two approaches.

Task Self-signed Private CA
Connecting without a warning Install the server certificate as a trusted certificate on each PC Install the root certificate once on each PC
Adding a server Install the new server’s certificate again on each PC Only sign with the same CA; nothing is installed again on the PCs
Renewing a certificate Install the changed certificate again on each PC. Browsers that were bypassing the warning have to bypass it again Nothing is installed again on the PCs
Creating a certificate One command Three steps: creating the CA, creating the CSR, signing

For example, with 3 servers and 10 connecting PCs, self-signed certificates mean installing 3 server certificates on each PC, 30 installations in total. A private CA means installing 1 root certificate on each PC, 10 installations, and nothing is installed again on the PCs when servers are added or certificates are renewed.

When nothing is installed on the PCs and the warning is bypassed, both approaches show the ERR_CERT_AUTHORITY_INVALID warning, so users see no difference. The difference grows as servers and users increase and connections need to work without a warning.

A certificate used on only one development PC can also be created with the mkcert tool. mkcert -install creates a private CA on that PC and adds it to the trust store, and mkcert localhost 192.168.0.20 creates a certificate signed by that CA. Since it is the private CA approach, no warning appears on that PC, and a warning appears on other PCs where the root certificate isn’t installed.

Risk on PCs with a root certificate installed

Section titled “Risk on PCs with a root certificate installed”

A root certificate added to the trust store has, by default, no limit on the domains it can sign for. So if the CA’s private key leaks, the problems follow in this order.

  1. Whoever has the private key can create a certificate for any domain, such as bank.example.com.
  2. PCs with the root certificate installed trust that certificate as a valid certificate.
  3. If the attacker is on the same network or can change DNS responses, they can read and change HTTPS traffic between that PC and the real server without a warning. This is called a man-in-the-middle attack.

If a server is compromised, what leaks is the server’s private key and certificate. The server certificate is not a CA and can’t sign other certificates, so the attacker can only impersonate the names in that certificate’s SAN. This limit holds as long as ca.key is not kept on the server as well.

The same problem can occur with self-signed certificates. If a self-signed certificate with CA:TRUE is installed in the trust store, that certificate is placed in the same position as a root certificate. Its private key is on the server, so if the server is compromised, steps 1 to 3 above can happen as they are. This is why the command above specifies CA:FALSE, and a certificate with CA:FALSE, even when installed, is trusted only for the names in its SAN.

Task Method
Storing ca.key Don’t upload it to servers; keep it separately in a place used only for issuing certificates
Limiting signing scope Add the Name Constraints extension to the root certificate to limit signing to internal domains such as .test. Support for this extension differs by OS and browser
Installation scope Install the root certificate only on the PCs that need it, and remove it from the trust store when it is no longer used
Self-signed certificates Create them with basicConstraints=critical,CA:FALSE

Certificates for IP addresses

Section titled “Certificates for IP addresses”

When connecting by IP, as in https://192.168.0.20, the browser checks whether that IP is in the SAN as IP:192.168.0.20. Connecting by IP with a certificate that holds only a domain gives a name mismatch and a warning.

Private IPs are used as the same addresses on many internal networks, so public certificate authorities don’t issue certificates for private IPs. If an internal network server has to be reached by IP, issue the certificate with the IP in the SAN, as in step 3 of Issuing certificates with a private CA. If a name can be given through internal DNS or the hosts file, the certificate can also be issued for a domain.

Certificate warnings

Section titled “Certificate warnings”

When certificate verification fails, the browser shows a warning screen instead of the page. The error code on the warning screen tells you which check failed. Below are Chrome’s codes.

Error code Failed check Common causes
NET::ERR_CERT_AUTHORITY_INVALID Chain A PC without the self-signed certificate or the private CA’s root certificate installed, the server not sending the intermediate certificate
NET::ERR_CERT_COMMON_NAME_INVALID Name The domain or IP connected to is not in the SAN
NET::ERR_CERT_DATE_INVALID Validity period Expired certificate, the PC’s clock is wrong

Clicking the site information icon in the address bar shows the certificate’s issuer, SAN and validity period.

Connections that bypass the warning

Section titled “Connections that bypass the warning”

Continuing from “Advanced” on the warning screen opens the page. This choice stays in that browser as an exception for a period of time, but it doesn’t mean the certificate is now trusted. So problems remain in the following cases.

Case Result
Another person or another browser connects Each person has to bypass the warning again
fetch requests and WebSocket (wss://) connections the page sends to another address (an API server and so on) The warning screen appears only for pages opened from the address bar, so connections to that address, which has no exception registered, fail without a warning
Another server or app makes the call A server’s HTTP client makes no exceptions, so it fails with a certificate error

For a server used by many people, instead of bypassing the warning, use a public certificate or install the private CA’s root certificate on the PCs that use it, so the warning doesn’t appear at all.

HSTS

Section titled “HSTS”

HSTS (HTTP Strict Transport Security) is a response header with which the server tells the browser “connect to this domain only over HTTPS from now on”.

Part Meaning
max-age How long the browser remembers this instruction, in seconds. 31536000 is one year
includeSubDomains Applies the same to subdomains

A browser that has received this header handles two things differently for the max-age period.

  • Even if http:// is typed in the address bar, it changes it to https:// before sending the request. This prevents attacks that intercept HTTP requests in transit.
  • It removes the button for continuing on that domain’s certificate warning screen.

Because of the second behavior, HSTS is not turned on for servers that use a self-signed certificate or private CA certificate not installed on the connecting PCs. Turning it on makes that domain unreachable. HSTS remembered by the browser stays until max-age passes, even if the header is removed. Nginx’s HTTPS setup and HTTP→HTTPS redirection are in the Nginx post.

Certificate check commands

Section titled “Certificate check commands”

Outside the browser, use openssl and curl to check the certificate the server sends.

-servername is the domain sent as SNI. A server with several domains on one IP sends a different certificate depending on this value.

curl -k skips certificate verification. It is used only to see whether the server responds, not as a way to fix a certificate problem.

Command summary

Section titled “Command summary”
Task Command
Check a server’s certificate openssl s_client -connect domain:443 -servername domain
View a certificate file’s contents openssl x509 -in file -noout -text
Create a private CA openssl req -x509 -new -nodes -newkey rsa:2048 -keyout ca.key -out ca.crt -days 3650
Create a self-signed certificate openssl req -x509 -nodes -newkey rsa:2048 -keyout server.key -out server.crt -addext "basicConstraints=critical,CA:FALSE"
Create a server private key and CSR openssl req -new -nodes -newkey rsa:2048 -keyout server.key -out server.csr
Sign with the private CA openssl x509 -req -in server.csr -CA ca.crt -CAkey ca.key -CAcreateserial -out server.crt -extfile san.ext
Install a root certificate (Ubuntu) Copy to /usr/local/share/ca-certificates/, then sudo update-ca-certificates
Request with verification by the private CA curl --cacert ca.crt https://domain
