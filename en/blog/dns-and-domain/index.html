DNS and domains

Oct 28, 2026 - 17 min read
nabong

SeriesNetwork basics

  1. Network layers
  2. IP addresses and ports
  3. NAT and port forwarding
  4. VPN
  5. DNS and domains
  6. HTTPS and certificates

The previous posts connected by IP, as in 192.168.0.20. In practice you often connect with a domain such as example.com, and the browser turns the domain into an IP before connecting. This post looks at that process, DNS, along with records, the hosts file, internal DNS and how to check lookup results. In terms of the network layers, DNS is an application layer protocol and uses UDP port 53 (TCP port 53 when the response is large).

Domains and DNS

Section titled “Domains and DNS”

A domain is a name given to an IP address so that people can remember it. DNS (Domain Name System) is the system that turns a domain into an IP address.

When you type https://api.example.com into the browser, the browser first asks DNS for the IP of api.example.com, then connects to the IP it gets back (203.0.113.20). If the server moves to a different IP, only the value in DNS needs to change, and users keep connecting with the same domain.

Domain structure

Section titled “Domain structure”

A domain is split by dots, and the further right a part is, the wider its scope.

Part Name Who decides it
.com Top-level domain (TLD) Set by international bodies. .com, .org, .kr and so on
example Registered domain Bought and registered through a domain registrar
api Subdomain Created by the domain owner by adding a record in DNS

Once example.com is registered, names under it such as api.example.com, www.example.com and dev.example.com can be created without registering them separately.

Subdomains and paths

Section titled “Subdomains and paths”

A subdomain is a name placed in front of the domain, and a part after the domain such as /users/12 is the path. The two are handled in different places.

Part In https://api.example.com/users/12 Handled by
Subdomain and domain api.example.com DNS turns it into an IP. Each subdomain can be sent to a different IP
Path /users/12 DNS does not look at the path. The server at that IP (Nginx, the backend) receives it and routes it

So the addresses that separate the frontend and backend can also be built in two ways.

Approach Addresses Characteristics
Split by path example.com, example.com/api The approach in the Nginx post. There is one address, so no CORS setup is needed
Split by subdomain example.com, api.example.com DNS can send each to a different server. The hosts differ, so the origins differ, and the backend needs a CORS setup

Records

Section titled “Records”

Each line written in DNS for a domain is called a record. Records are stored on the name servers covered below.

From the left: the name, the TTL (how long this result may be kept in a cache, in seconds), the record type, and the value. TTL is covered below in “Caching and TTL”.

Type Value Used for
A IPv4 address Pointing a domain at an IP
AAAA IPv6 address Pointing a domain at an IPv6 address
CNAME Another domain An alias. In the example above, www.example.com follows the IP of example.com
MX Mail server domain The server that receives mail sent to this domain
TXT Text Domain ownership verification, mail sender authentication
NS Name server domain The authoritative name server responsible for this domain

CNAME

Section titled “CNAME”

An A record returns an IP directly, and a CNAME record returns another domain name.

Record Name looked up Value returned
A example.com 203.0.113.10 (an IP)
CNAME www.example.com example.com (another domain)

So finding the IP of www.example.com takes two lookups.

  1. Looking up www.example.com returns example.com as a CNAME instead of an IP. This means www.example.com is another name for example.com.
  2. Next, example.com is looked up and the A record’s 203.0.113.10 comes back.
  3. The browser connects to 203.0.113.10, the last value it received.

DNS carries out the second lookup itself, so the browser receives only one IP.

CNAME is used so that the IP is managed in only one place. Take the case where the server IP changes from 203.0.113.10 to 203.0.113.50.

How the www record is set Records to change when the IP changes
The IP written directly with an A record Two: example.com and www.example.com
Linked to example.com with a CNAME One: example.com. www.example.com changes along with it

When a cloud deployment service tells you to “point blog.example.com at myapp.host.example with a CNAME”, it is the same principle. The service company manages the A record of myapp.host.example, so even if the service’s IP changes, the record in your DNS stays as it is.

Name servers

Section titled “Name servers”

A name server is a DNS server that holds a domain’s records and answers the question “what is the IP of this domain”.

No single server holds the information for every domain on the internet. Like the domain structure, it is split into levels: each name server knows only its own range and hands the levels below to the next name server. This is called delegation.

Name server What it knows
Root name server The addresses of the name servers responsible for each top-level domain (.com, .kr and so on)
TLD name server (.com) The addresses of the name servers responsible for each domain under .com (example.com and so on)
Authoritative name server (example.com) The actual records of example.com and its subdomains

“Authoritative” means the server holds that domain’s records itself, so it can answer without asking anywhere else.

Domain registration and name servers

Section titled “Domain registration and name servers”

When you register a domain, you specify the authoritative name servers for it. You can use the name servers the registrar provides by default, or switch to the name servers of a DNS service such as Cloudflare or AWS Route 53. The specified name servers are registered with the TLD name server as NS records.

After that, records such as A and CNAME are added and changed in the admin page of the specified name servers. Two or more name servers are specified so that if one stops, the other can still answer lookups.

Resolvers and name servers

Section titled “Resolvers and name servers”

Besides name servers, which answer, DNS servers also include resolvers, which go around asking.

Resolver Authoritative name server
What it does Asks several name servers in turn on behalf of your PC to find the final IP, and keeps the result in a cache Answers with the records of the domains it is responsible for
Examples Your internet provider’s DNS, 8.8.8.8 (Google), 1.1.1.1 (Cloudflare), a company’s internal DNS The name servers of the DNS service specified for the domain
The “DNS server” field in a PC’s network settings What goes here is a resolver Not entered here

Lookup process

Section titled “Lookup process”

The first lookup of api.example.com goes like this.

  1. Your PC checks the hosts file and its own cache. If the name is there, the lookup ends here.
  2. If not, it asks the resolver set in the network settings.
  3. The resolver asks a root name server and gets the address of the TLD name server responsible for .com.
  4. The resolver asks the TLD name server and gets the address of the authoritative name server for example.com.
  5. The resolver asks the authoritative name server and gets 203.0.113.20, the IP of api.example.com.
  6. The resolver stores the result in its cache and returns it to your PC.

Caching and TTL

Section titled “Caching and TTL”

A DNS response carries a TTL (Time To Live, how long it stays valid). Resolvers and PCs keep the result in a cache for the TTL, and when the same domain is asked again, they answer directly without steps 3 to 5.

So when you change the IP in a record, the change does not reach every user right away. Resolvers and PCs that cached the previous value keep connecting to the old IP until the TTL runs out. Shortening the TTL before moving a server makes the changed value take effect sooner.

The hosts file

Section titled “The hosts file”

During development and testing, there are times when you need to connect by domain name but can’t create a record in DNS, or shouldn’t create one yet. The hosts file is used in these cases.

The hosts file is a file on the PC where pairs of domains and IPs are written directly. As in step 1 of the lookup process above, the PC reads this file before asking the resolver. A name written here goes straight to the written IP without a DNS lookup.

OS Location
Windows C:\Windows\System32\drivers\etc\hosts (edit with administrator rights)
Linux, mac /etc/hosts

Write one IP and domain per line.

Uses of the hosts file

Section titled “Uses of the hosts file”
Situation Why connecting by IP doesn’t work What to write
Splitting several services on one server by name Nginx uses server_name to look at the domain name in the request and pick a server block. Connecting by IP gives no name to decide which service to send it to As in the first and second lines of the example above, a different name for each service on the same IP
Checking an HTTPS certificate Certificates are issued for domain names. Connecting by IP doesn’t match the name on the certificate, so the browser shows a warning The domain on the certificate and the development server’s IP
Checking a new server before moving to it Changing the DNS record sends every user to the new server, and if something goes wrong, it is hard to go back to the old value during the TTL As in the third line of the example above, the production domain and the new server’s IP. Only your PC goes to the new server
Naming servers in a team without the “Internal DNS” below IPs are hard to remember, and when a server’s IP changes, every setting that has that IP written in it has to be changed A name for each server, as in 192.168.0.30 db.example.test

The hosts file applies before DNS, so if you don’t remove the entry after checking, only your PC keeps connecting to that IP. If “it works for others but only my PC goes to the old server”, check the hosts file first.

.test is a top-level domain reserved for testing, so it doesn’t overlap with real domains on the internet.

Resolver settings

Section titled “Resolver settings”

“The resolver set in the network settings” from step 2 of the lookup process is set separately on each PC and server. If this value is empty, communication by IP works but every domain lookup fails.

Available resolvers

Section titled “Available resolvers”
Type Example Characteristics
Router 192.168.0.1 Many routers also act as a resolver and pass the questions they receive on to the provider’s DNS
Company internal DNS An internal IP set by the company Answers for internal names, covered in “Internal DNS” below, as well as internet domains
Provider DNS The address given by the internet provider Often received automatically when connecting to the internet
Public DNS 8.8.8.8 (Google), 1.1.1.1 (Cloudflare) Usable from any network. It doesn’t know internal names, and on company networks that block external DNS it doesn’t respond

Usually two or more resolvers are listed. If the first resolver doesn’t respond, the lookup continues with the second.

nameserver in configuration files

Section titled “nameserver in configuration files”

In configuration files, resolvers are often written under the name nameserver. Linux and many tools have traditionally called “the DNS server to ask” by this name. A nameserver in a configuration file is not an authoritative name server from the “Name servers” section above, but the resolver this PC or server asks.

Where it is written Example value Meaning
nameserver in the server’s /etc/resolv.conf, nameservers in netplan 8.8.8.8 The resolver this server asks
The domain’s NS record ns1.dns-provider.example. The authoritative name server that holds this domain’s records

Resolvers on Linux servers

Section titled “Resolvers on Linux servers”

On Linux servers such as Ubuntu, a program running inside the server called systemd-resolved acts as the resolver. Programs on the server ask it, and systemd-resolved in turn asks a resolver outside the server, such as the router or 8.8.8.8 from the table above. Below, this resolver is called the upstream resolver to tell it apart from systemd-resolved inside the server.

systemd-resolved doesn’t decide the upstream resolver’s address itself; it receives it through the network settings. netplan and the renderer are involved in these settings.

Name What it does
netplan On Ubuntu, the YAML files (/etc/netplan/*.yaml) where network settings such as the IP, gateway and resolvers are written, and the tool that hands those files to the renderer. It does not configure the network card itself
Renderer The program that takes netplan’s settings, actually assigns the IP and gateway to the network card, and passes the resolver list to systemd-resolved. It is set with the renderer: entry in the netplan file

There are two renderers, and they do the same job.

Renderer Default on Characteristics
networkd (systemd-networkd) Ubuntu Server Only reads and applies configuration files. Suits servers whose settings rarely change
NetworkManager Ubuntu Desktop Has features for changing connections often, such as choosing Wi-Fi, connecting to a VPN, the network menu on screen and the nmcli command

The two renderers use different configuration formats. netplan lets you write one YAML format and converts it into the format of the chosen renderer, so the user doesn’t need to know the difference. Whichever renderer is used, systemd-resolved still acts as the resolver.

The settings are passed along in this order.

Order Where What it does
1 netplan configuration file The upstream resolvers are written under nameservers
2 netplan apply Converts the file into the renderer’s configuration format and hands it over
3 Renderer (networkd or NetworkManager) Applies the settings to the network card and passes the upstream resolver list to systemd-resolved
4 systemd-resolved Forwards lookups using the upstream resolver list it received
5 /etc/resolv.conf Contains nameserver 127.0.0.53. 127.0.0.53 points to systemd-resolved inside the server itself, and programs on the server ask this address
Entry Meaning When empty
renderer The renderer that applies the settings The default, networkd, is used
addresses (top level) This server’s IP. /24 means addresses whose first three parts, 192.168.0, are the same are treated as the same range The server doesn’t connect to the network
to: default and via under routes The two lines are one rule. to: default means every other destination with no route of its own (the internet and other ranges), and via is the gateway those packets are handed to (the address of a router in the same range). The example means “hand every packet for other destinations to 192.168.0.1” Packets can’t leave the same range, so the internet can’t be reached even by IP
addresses under nameservers The resolvers to ask about domains Communication by IP works, and only domain lookups fail

The same 192.168.0.1 appears in both via and nameservers in the example because one router acts as both the gateway and the resolver.

Even if resolvers are written in the configuration file, the list in systemd-resolved is empty if the settings haven’t been applied. Check the values actually in use with resolvectl status.

If this command prints nothing, systemd-resolved has nowhere to forward questions to, and every domain lookup fails. Check nameservers in the configuration file, apply it again with sudo netplan apply, then use the same command to see whether the list is filled in. netplan apply reapplies the network, so the SSH connection may drop briefly.

If the list is still empty after reapplying, the renderer that received the settings is different from the renderer that actually manages the network card. For example, if netplan hands the settings over with renderer: networkd but NetworkManager manages the card, the resolver list networkd received isn’t applied to that card. In nmcli device status, a card shown as connected is managed by NetworkManager, and one shown as unmanaged is managed by networkd. Servers without NetworkManager installed don’t have this command, and networkd manages the card. Write the resolver settings on the side of the renderer that actually manages the card.

The settings above apply to servers where a person writes a static IP by hand, such as servers you install yourself. Servers created in the cloud receive their IP and resolvers automatically, so netplan usually isn’t edited by hand.

Item Self-installed server Cloud server (AWS, GCP, Azure and so on)
IP, gateway, resolvers Written by a person during installation Received at boot through DHCP (a way of automatically handing out an IP, gateway and resolvers to devices connected to a network)
netplan file Created by the installer or written by a person Created by cloud-init (a program that sets up the network, accounts and SSH keys when a cloud server first boots)
Where to change resolvers The netplan file The network (VPC) settings in the cloud console. Files created by cloud-init can be regenerated, so changes made by hand may be lost

Either way, checking resolvers with resolvectl status works the same, and so does the container resolver behavior covered below in “Name lookup on Docker networks”.

On a Windows PC, check the resolvers in use under the “DNS Servers” entry of ipconfig /all.

Internal DNS

Section titled “Internal DNS”

Companies sometimes run a DNS server used only inside the internal network. Internal DNS holds the names of internal servers, as in db.corp.example.test → 192.168.0.30, and these names can’t be looked up from the internet.

Situation Internal name lookup
Office internal network Works. The network settings use the internal DNS as the resolver
Connected through a VPN from home Works if the VPN sets the internal DNS as the resolver
From home without a VPN Doesn’t work. Resolvers on the internet don’t know internal names

If you’re connected to the VPN and IPs work but internal names don’t, the VPN hasn’t passed on its DNS settings. Check the DNS server entry of the VPN adapter in ipconfig /all.

Name lookup on Docker networks

Section titled “Name lookup on Docker networks”

IP addresses and ports said containers on the same Docker network can connect to each other by name, as in api:8000. This is DNS too. Docker runs a built-in DNS server (127.0.0.11) for each user-created network and answers container names with that container’s IP.

The default bridge network has no such name lookup, so containers can be reached by name only on networks created with docker network create.

Internet domains, as opposed to container names, follow the server’s resolver settings. A container can’t reach the server’s 127.0.0.53, so Docker takes the upstream resolver list that systemd-resolved uses, from “Resolvers on Linux servers” above, and uses it.

Server’s resolver settings Resolvers the container uses
systemd-resolved has upstream resolvers Those resolvers
No upstream resolvers Docker’s defaults, 8.8.8.8 and 8.8.4.4

So if the server’s resolver settings are empty, docker pull can’t look up the image registry’s domain, and build steps such as RUN apt-get ask 8.8.8.8. On company networks that block external DNS, these steps fail too. In this case, fill in the server’s resolver settings first, and if a container needs a specific resolver, use docker run --dns 192.168.0.1 or the "dns" entry in the Docker configuration file (/etc/docker/daemon.json).

Checking lookup results

Section titled “Checking lookup results”
Line Meaning
Server The resolver used for this lookup
Non-authoritative answer The answer came from a resolver, from its cache or a lookup on your behalf, rather than from the authoritative name server
Address The IP that was looked up

Looking up a domain with a CNAME using dig +short prints the CNAME value and then the final IP. This shows the two lookups from “CNAME” above in the result.

nslookup and dig ask the DNS server directly, so they don’t read the hosts file. It is expected that a value written in the hosts file doesn’t show up in nslookup. To see the result with the hosts file applied, check the IP that ping shows.

Clear your PC’s DNS cache with the commands below.

Order for checking domain connection problems

Section titled “Order for checking domain connection problems”
Symptom What to check
DNS_PROBE_FINISHED_NXDOMAIN in the browser There is no record for that name. Check for typos in the domain and whether the record is registered with nslookup
Connecting by IP works but by domain doesn’t A DNS problem. Check whether the nslookup result is that IP
Every domain lookup fails on a server (docker pull fails, Temporary failure in name resolution) If ping 8.8.8.8 works and dig domain @8.8.8.8 also works, the internet connection is fine and the server’s resolver settings are missing. Check the DNS server list in resolvectl status
The record was changed but connections still go to the old server Caching during the TTL. Check whether the new value is in effect with dig @8.8.8.8, and clear your PC’s cache
Only your PC goes to a different server Check whether that domain is written in the hosts file
Internal names don’t work after connecting to the VPN Check the DNS server settings of the VPN adapter

Command summary

Section titled “Command summary”
Task Command
Look up a domain’s IP nslookup domain, dig +short domain
Look up through a specific resolver dig domain @8.8.8.8
Look up a specific record type dig domain CNAME, nslookup -type=MX domain
