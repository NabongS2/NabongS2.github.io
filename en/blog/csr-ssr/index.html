CSR vs SSR

Oct 12, 2026 - 7 min read
nabong

What you see on screen is ultimately HTML. Whether the browser builds that HTML, or the server builds it and sends it is what separates CSR from SSR. This post covers how each one’s requests flow, how they differ, and which one the framework you use belongs to.

Rendering

Section titled “Rendering”

Rendering is turning data into the HTML that appears on screen. Even for one page such as /history/12, the record data has to be made into HTML with a heading and a table.

Name Where the HTML is built
CSR Client-Side Rendering The browser, as the JS runs
SSR Server-Side Rendering The server, for every request, before sending it

Request flow

Section titled “Request flow”

CSR

Section titled “CSR”

A React app built with Vite works this way. The dist from Nginx part 1 is what it produces.

  1. The browser requests /history/12, and Nginx sends index.html.
  2. index.html has no content, only the line that loads the JS file.
  3. The browser downloads and runs the JS, and the JS calls /api/history/12 to get the data.
  4. The JS uses that data to build the page inside <div id="root">.

The page appears only after step 4. During steps 1 to 3 the user sees a blank page or a spinner.

All the server does is send files. It can send the same index.html for any address, and the JS builds the page that matches the address. The try_files $uri $uri/ /index.html from Nginx part 1 does exactly this.

SSR

Section titled “SSR”

Frameworks such as Next.js and Nuxt work this way. The server that receives requests runs on Node.

  1. The browser requests /history/12, and the Node server receives it.
  2. The Node server calls the API itself to get the data.
  3. The Node server builds HTML filled with that data and sends it.
  4. The browser shows the HTML it received right away.
  5. The JS then downloads and runs, and wires up behavior such as clicks on the page that’s already showing.

The page appears at step 4, because the server has already done the API call and built the HTML before sending it.

Hydration

Section titled “Hydration”

Step 5 of SSR is called hydration. The HTML the server sent can only be looked at; pressing a button does nothing. Only after the JS runs and attaches events to the existing HTML does it behave like a CSR app.

So SSR still downloads JS. The difference is that the page shows first, without waiting for the JS. After hydration, moving between pages is handled in the browser, just as with CSR.

Checking with the page source

Section titled “Checking with the page source”

To check which one a page uses, open View page source (Ctrl + U) in the browser. The page source is the HTML exactly as the server sent it, before any JS runs.

Page source Approach
Empty, like <div id="root"></div>, with none of the text on screen CSR
The text on screen is in the HTML SSR, or SSG below

The Elements tab in the developer tools shows the result after JS has run, so even a CSR page shows all its content there. To tell them apart, look at the page source, not Elements.

Differences

Section titled “Differences”
CSR SSR
Where the HTML is built The browser The server (Node)
The first HTML received No content Contains the content
When the first page appears After the JS runs and the API call finishes Right after the HTML arrives
Moving between pages Changes instantly in the browser Same as CSR after hydration
Search engines, link previews May not be able to read the content Read the content in the HTML
Server Only needs to send files (Nginx) A Node server that builds HTML for every request
Server load Light Rendering cost on every request

First page

Section titled “First page”

With CSR, the larger the JS files and the slower the API, the later the first page appears. In the meantime the user sees a blank page. With SSR, the HTML response is delayed by the time the server spends calling the API, but the content shows as soon as it arrives.

Moving between pages

Section titled “Moving between pages”

With CSR, once the JS has loaded, moving to another menu doesn’t fetch new HTML. The JS changes only the page and fetches only the data it needs from the API, so navigation is fast. An app that shows many screens by swapping content within one HTML page like this is called an SPA (Single Page Application).

Search engines and link previews

Section titled “Search engines and link previews”

Search engines, and the previews that appear when you paste a link into a messenger, read the HTML the server sent. With CSR the HTML is empty, so they sometimes can’t read the content, title or image. Google sometimes runs the JS to read the page, but places such as messenger previews usually read only the HTML.

Server and deployment

Section titled “Server and deployment”
CSR SSR
Build output HTML, JS and CSS files (dist) A server app run with Node
Deployment Put the files on Nginx Run the Node server as a container
Nginx’s role Serve the files and forward /api to the backend Forward requests to the Node server

CSR doesn’t add another server. With SSR the frontend becomes a server too, so there is one more process to run and keep an eye on.

SSG

Section titled “SSG”

SSG (Static Site Generation) builds the HTML ahead of time, at build time. When a request comes in, it only sends the prebuilt file.

When the HTML is built Server
CSR After the request, in the browser Only sends files
SSR On every request, on the server A Node server
SSG Once, at build time Only sends files

This blog uses SSG. When a post is published, the build creates the HTML for each post, and GitHub Pages only sends those files. That’s why the page source contains the whole post, and why the server, as with CSR, only needs the files.

The trade-off is that anything changed after the build needs another build to show up. It suits content that doesn’t change often, such as posts, and doesn’t suit pages that show different data to each user.

By framework

Section titled “By framework”

Here is where the frameworks in common use fall.

Framework Approach
React or Vue built with Vite CSR. The build output is static files in dist
Next.js (React), Nuxt (Vue) SSR by default, switchable to SSG or CSR page by page
Astro SSG by default, with SSR for the pages that need it. This blog is built with Astro
Spring with Thymeleaf or JSP SSR. The Java server builds the HTML and sends it

The same React is CSR when built with Vite and SSR when used on top of Next.js. What decides the approach isn’t the UI library but the framework around it.

The setup from Nginx part 1, where one Java app served both pages and the API, is SSR in the Thymeleaf or JSP style. Splitting those pages out into React turned them into CSR, and that’s why a separate Nginx to serve the frontend files became necessary.

Choosing

Section titled “Choosing”
Page Fits Why
An admin screen used after logging in CSR It never needs to appear in search results, and Nginx alone is enough as the server
A blog or documentation site SSG The content rarely changes and should appear in search results
Shop product pages, news SSR The content changes often but still needs to appear in search results and link previews

An admin screen at work being CSR fits these criteria. You have to log in to use it, so it doesn’t need to show up in search engines, and although the first page is a little slower, moving around is fast once you’re in.

Frameworks such as Next.js can mix SSR, SSG and CSR page by page within one app. It isn’t a matter of picking just one, but of deciding, for each page, where its HTML gets built.
