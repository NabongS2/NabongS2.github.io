React hook basics

Oct 12, 2026 - 10 min read
nabong

The CSR post said that with CSR the browser’s JS builds the page. In a React app the pieces that do that are components, and the functions that let a component remember values or do work after the screen is drawn are hooks. This post covers the six basic hooks you use most, and props, which is how components pass values to each other.

Components and rendering

Section titled “Components and rendering”

A component is a function that returns the JSX to show on screen.

Pressing this button doesn’t change the number, for two reasons.

  • Changing count doesn’t tell React that the screen needs redrawing.
  • Even if it redrew, Counter() would run from the top and go back to let count = 0.

To change the screen in React you have to change a value React keeps for you: state. When state changes, React runs the component function again. This is called rendering.

Every hook in this post builds on this order. In particular, on every render the function runs from the top, and the variables, objects and functions inside it are created anew. That’s why useRef, useMemo and useCallback exist.

useState

Section titled “useState”

A value that survives past the end of a render, and that redraws the screen when you change it.

Part Meaning
useState(0) The initial value. Used only on the first render
count The value for this render
setCount A function that changes the value and triggers a re-render

Values don’t change immediately

Section titled “Values don’t change immediately”

Calling setCount doesn’t change count in the function that’s currently running. The new value shows up on the next render.

Updating from the previous value

Section titled “Updating from the previous value”

For the same reason, writing this to add two at once only adds one.

To update based on the previous value, pass a function. React passes in the value just before.

Objects and arrays

Section titled “Objects and arrays”

React decides whether to redraw by checking whether the new value is the same object as the old one. If it’s the same array, React treats it as unchanged even if its contents changed.

... is the spread syntax. It lays out the contents of an array or object one by one in place. So [...items] is a new array with the same contents, and { ...user } is a new object with the same fields.

Goal Changing the original (avoid) Making a new one
Add push [...items, item]
Remove splice items.filter((x) => x.id !== id)
Update items[i] = … items.map((x) => x.id === id ? { ...x, name } : x)
Sort sort [...items].sort(…), items.toSorted(…)
Change an object field user.name = … { ...user, name }

It’s easy to miss that sort reorders the original array. Calling sort directly on an array of data from the server also changes the order for other screens that use the same data.

props

Section titled “props”

Props are the values a parent component passes to a child component. A component is a function, so props are that function’s arguments.

Property Meaning
Read-only A child doesn’t change the props it receives. If it needs changing, the parent that owns the value changes it
Re-render with the parent When the parent re-renders, the child re-renders too, even if its props are the same

Function props

Section titled “Function props”

When a child needs to change a parent’s value, the parent passes a function as a prop and the child calls it.

PlusButton doesn’t know about count; it only reports that it was pressed by calling onPlus(). Parent is what changes the state, and the new count reaches the screen when Parent re-renders.

Data in React flows one way like this. Values go down as props, and events go up as function calls. To find where a value changes, you only need to look at the one component that holds it as state.

Lifting state up

Section titled “Lifting state up”

When two sibling components need the same value, move that state to their common parent and hand it to both as props. This is called lifting state up.

If SearchInput kept keyword as its own state, ResultList couldn’t know it. When their parent SearchPage holds the state, both receive it as props.

props drilling

Section titled “props drilling”

As state moves upward, you end up with intermediate components that take props they never use, just to pass them on to one component at the bottom. This is called props drilling.

A few levels are fine. As it gets deeper, the intermediate components have to know about props that have nothing to do with them, and renaming a prop or changing its type means editing every file it passes through. At that point you can use useContext below, or manage the value with a state management library.

useEffect

Section titled “useEffect”

Registers work to run after the screen is drawn. Work that has nothing to do with producing the render result goes here: API calls, timers, event subscriptions, direct DOM manipulation.

Dependency array

Section titled “Dependency array”

The array passed as the second argument decides when the effect runs again.

Dependency array When it runs
None After every render
[] Once, when the component first appears
[id] Once at first, then whenever id changes

Put every prop, state value and variable the effect uses into the array. If one is missing, the effect keeps using its old value. ESLint’s react-hooks/exhaustive-deps rule points out missing ones.

Cleanup function

Section titled “Cleanup function”

If an effect returns a function, React calls it before running the effect again and when the component leaves the screen. It’s used to cancel timers and subscriptions.

In development mode with StrictMode, effects run, clean up, and run again. This is to surface a missing cleanup right away; production builds run them once. It’s why APIs get called twice during development.

When you don’t need an effect

Section titled “When you don’t need an effect”

Values you can calculate from props or state should be calculated during rendering, without an effect and extra state.

In practice, API calls are often left to a library such as React Query rather than written with useEffect by hand. It handles loading and error states, caching and refetching for you.

useRef

Section titled “useRef”

A value that survives past the end of a render but doesn’t trigger a re-render when it changes. You read and write it through ref.current.

Use Example
Holding a DOM element Focusing an input, scrolling to a position
Keeping a value unrelated to the screen A timer id, a previous value, whether a request is in flight
Plain variable useState useRef
Survives to the next render No. Created anew each time Yes Yes
Re-renders when changed No Yes No
When the new value is visible Immediately Next render Immediately

Use useState for values that must show on screen, and useRef for values you only need to remember.

useMemo and useCallback

Section titled “useMemo and useCallback”

Objects and functions inside a component are created anew on every render. Even with the same contents, a newly created object counts as a different object from the previous one.

useMemo remembers a computed result, and useCallback remembers a function. If the values in the dependency array haven’t changed, they return what was made before.

useCallback(fn, deps) is the same as useMemo(() => fn, deps). The thing being remembered just happens to be a function.

When they’re needed

Section titled “When they’re needed”
Case Example
The calculation is heavy Sorting or filtering a list of thousands of items
The result is passed on as something another place compares A useEffect dependency array, props of a child wrapped in React.memo

The second case is the options example above. Without remembering it, the effect runs on every render, or a child wrapped in React.memo sees its props as changed and re-renders every time.

When they’re not needed

Section titled “When they’re not needed”
  • Light calculations such as filtering a short array or joining strings
  • When the result is used directly on screen and isn’t passed anywhere that compares it

In these cases the cost of remembering (comparing dependencies, keeping the old value) plus longer code outweighs the gain. Adding it doesn’t change behavior, but putting it on every value makes it hard to see where it really matters. With React Compiler, this memoization is inserted automatically at build time, so you need to add it by hand less often.

Don’t change the original inside

Section titled “Don’t change the original inside”

When sorting inside useMemo, don’t change the original array either.

In JS, putting an array in a variable or passing it around doesn’t copy it. Several names simply point at the same single array.

sort doesn’t create a new array; it reorders the array itself. So in the first snippet above, data.sort(…) isn’t a value used only inside useMemo; it changes the original array data points to.

If data is server data from a library such as React Query, that array is the very array the library keeps in its cache. Any other screen using the same data receives the reordered array as well. With two screens that sort differently, each overwrites the other’s order, and the result depends on which one renders first.

Sorting a copy made with [...data] leaves the original alone. data.toSorted(…) does the same thing: it returns a new sorted array and leaves the original unchanged.

Method Changes the original Use instead
sort Yes [...arr].sort(), arr.toSorted()
reverse Yes [...arr].reverse(), arr.toReversed()
splice Yes filter, arr.toSpliced()
push, pop, shift, unshift Yes [...arr, item], arr.slice(…)
map, filter, slice, concat No Fine as is

useContext

Section titled “useContext”

Solves the props drilling above. Put a value in once at the top, and components below take it out directly without going through the ones in between.

When the Provider’s value changes, every component that uses it re-renders. That makes it a good fit for values used in many places that don’t change often, such as the logged-in user, the theme or the language. When a value shared by many components changes often, you can manage it with a state management library such as Zustand, so that components that don’t use it aren’t re-rendered as well.

Rules of hooks

Section titled “Rules of hooks”

Hooks aren’t functions you can call from anywhere. React sets two rules for them. They apply not only to the hooks in this post but also to hooks from libraries and hooks you write yourself.

Only inside components

Section titled “Only inside components”

Call hooks only inside a component function or another hook. A regular function can’t call them.

The values a hook remembers are stored on the component that is currently rendering. A regular function has no rendering component, so there is nowhere to store them.

At the top of the component

Section titled “At the top of the component”

Call hooks at the top of the component function. If you need a condition, write it after the hooks.

If a useEffect should only run under some condition, put the condition inside the useEffect.

ESLint’s react-hooks/rules-of-hooks rule points out code that breaks either rule.

Custom hooks

Section titled “Custom hooks”

A function whose name starts with use and that calls other hooks is itself a hook. You write one, like useLoginUser in this post, to wrap a combination of hooks that several components use. The use prefix is how ESLint recognises it as a hook and checks the rules above.

Summary

Section titled “Summary”
Hook What it does Re-renders
useState Remembers a value and redraws the screen when it changes When changed
useEffect Runs work after the screen is drawn No (yes if it changes state inside)
useRef Remembers a value or a DOM element No
useMemo Remembers a computed result No
useCallback Remembers a function No
useContext Takes out a value passed from above When the value changes
