# Redis 컨테이너 세팅 — 따로 쓸 글의 재료

`redis-docker.mdx` 를 사용 쪽으로 좁히면서 뺀 본문이다. 세팅 글을 쓸 때 여기서 시작한다.
아래 「뺀 본문」은 글에 있던 그대로다. 안의 링크와 "앞에서", "아래" 같은 말은 원래 글 기준이다.

## 잡아 둔 순서

- 이미지 받기 — `docker pull redis:7`. 아직 안 씀
- 한 줄로 띄워 보기 — 옵션 없이 `docker run -d -p 6379:6379 redis:7`. 아직 안 씀
- 여기에 무엇을 더해야 하나 — 아래 「기본값으로 띄우면 어떻게 되나」의 표
- 볼륨 빼두기 — 아래 「볼륨이 뭔가」
- 껐다 켜면 무엇이 남나 — RDB, AOF
- 메모리 한도 정하기 — 아래 「메모리가 차면」
- 비밀번호 걸기 — 아직 안 씀
- 설정을 어디에 두나 — 실행 옵션 / 설정 파일 / `CONFIG SET`. 아직 안 씀
- 다 합친 명령 — `docker run` 예제가 본문에 세 벌 있었다. 이 자리 하나로 모은다

## 뺀 본문

### 기본값으로 띄우면 어떻게 되나

`docker run redis:7` 로 띄우면 아무것도 정하지 않은 상태입니다. 무엇이 기본값인지 알고 두는 것과 모르고 두는 것이 다릅니다.

| 항목 | 기본값 | 바꿔야 하는 때 |
| --- | --- | --- |
| 비밀번호 | 없음 | 포트를 호스트로 열었을 때 |
| 영속성 | RDB 만, 조건을 채울 때만 저장 | Redis 가 원본인 것을 담을 때 |
| 데이터 위치 | 익명 볼륨 | 컨테이너를 갈아 끼울 때 |
| `maxmemory` | `0` — 한도 없음 | 한 장비에 여러 개를 돌릴 때 |
| `maxmemory-policy` | `noeviction` | 캐시로 쓸 때 |

마지막 두 줄의 조합을 보면 **한도가 없고 아무것도 버리지 않습니다.** 메모리가 남는 동안은 계속 늘어나고, 장비 메모리를 다 쓰면 커널에 종료됩니다. 캐시로 쓴다면 버려도 되는데 버리지 않아 죽는 것이고, 원본을 담고 있다면 죽는 순간이 곧 손실입니다.

어느 쪽이든 기본값 그대로 두면 **언젠가 메모리로 죽습니다.** 언제 죽을지가 데이터가 쌓이는 속도에 달려 있을 뿐입니다.

### 컨테이너로 띄우기

옵션 없이 띄우면 거의 다 기본값입니다. 기본값이 무엇인지 모르고 두면 나중에 문제가 되는 것이 네 개 있습니다.

```sh
docker run -d --name myapp-redis \
  -v /opt/myapp-redis/data:/data \
  -p 6379:6379 \
  -m 2g \
  redis:7 redis-server \
    --appendonly yes \
    --maxmemory 1500mb \
    --maxmemory-policy noeviction
```

| 옵션 | 왜 있나 |
| --- | --- |
| `-v .../data:/data` | 영속화 파일이 컨테이너 밖에 남게 합니다 |
| `-p 6379:6379` | 호스트에서 붙을 수 있게 합니다 |
| `-m 2g` | 컨테이너 메모리 한도 |
| `--appendonly yes` | AOF 영속화를 켭니다 |
| `--maxmemory` | Redis 가 쓸 메모리 한도. 컨테이너 한도보다 낮게 |
| `--maxmemory-policy` | 한도에 닿았을 때의 동작 |

각각을 아래에서 하나씩 봅니다.

### 볼륨이 뭔가

컨테이너 안에는 자기만의 파일 시스템이 있습니다. `/data` 도 `/etc` 도 다 있는데, 호스트의 그것과는 다른 것들입니다. `docker rm` 으로 컨테이너를 지우면 그 안에 있던 파일도 같이 없어집니다.

볼륨은 **호스트의 폴더 하나를 컨테이너 안의 경로에 겹쳐 놓는 것**입니다.

```sh
-v /opt/myapp-redis/data:/data
```

왼쪽이 호스트 경로, 오른쪽이 컨테이너 안 경로입니다. 컨테이너가 `/data` 에 쓴 파일은 실제로는 호스트의 `/opt/myapp-redis/data` 에 적힙니다. 같은 파일을 양쪽에서 봅니다.

```sh
docker exec myapp-redis ls /data   # 컨테이너 안에서
ls /opt/myapp-redis/data           # 호스트에서. 같은 파일이 보입니다
```

여기서 호스트는 **컨테이너를 돌리는 서버**입니다. 개발 서버에 붙어서 `docker run` 을 했다면 그 서버의 디스크지, 내 노트북이 아닙니다.

#### 컨테이너를 갈아 끼울 수 있게 됩니다

볼륨을 빼두는 이유입니다. 도커에서 하는 일이 대부분 "컨테이너를 지우고 다시 `run`" 입니다. 버전 올리기도, 설정 바꾸기도, 고장 났을 때 되살리기도 그렇습니다. 볼륨이 없으면 그때마다 데이터가 날아가니, 컨테이너를 건드리지 못하는 상태가 됩니다.

#### 바인드 마운트와 이름 있는 볼륨

`-v` 왼쪽에 무엇을 적느냐로 갈립니다.

| | 쓰는 법 | 파일이 어디 있나 |
| --- | --- | --- |
| 바인드 마운트 | `-v /opt/myapp-redis/data:/data` | 내가 정한 호스트 경로. `ls` 로 바로 봅니다 |
| 이름 있는 볼륨 | `-v redisdata:/data` | 도커가 관리하는 자리. 경로를 내가 정하지 않습니다 |

백업 스크립트를 돌리거나 파일을 직접 열어 볼 일이 있으면 바인드 마운트가 편합니다. 경로가 정해져 있으니까요.

`-v` 를 아예 안 줘도 공식 redis 이미지는 이름 없는 볼륨을 하나 만들어 붙입니다. 그것으로 될 것 같지만 아래 [영속화 파일이 어디 쌓이나](#컨테이너로-띄웠다면-볼륨을-같이-봐야-합니다)에서 보듯 컨테이너를 갈아 끼울 때 이어지지 않습니다.

### 껐다 켜면 무엇이 남나

메모리에 있는 것을 디스크에 남기는 방식이 두 가지입니다. 하나만 켜도 되고 둘 다 켜도 됩니다.

| | RDB | AOF |
| --- | --- | --- |
| 무엇을 쓰나 | 특정 시점의 메모리 전체를 파일로 | 받은 쓰기 명령을 순서대로 기록 |
| 파일 | `dump.rdb` | `appendonly.aof` |
| 복구할 때 | 그 시점으로 돌아갑니다 | 명령을 다시 실행해 재현합니다 |
| 잃는 범위 | 마지막 저장 이후 전부 | 설정에 따라 최대 1초 |
| 비용 | 저장하는 순간 부하가 몰립니다 | 계속 쓰지만 부하가 고릅니다 |

> `RDB` 는 **R**edis **D**ata**b**ase 의 약자입니다. 관계형 DB와 무관합니다.

#### 기본값은 RDB 뿐이고 조건이 붙습니다

```
save 3600 1
save 300 100
save 60 10000
```

각 줄은 "몇 초 안에 몇 건 이상 바뀌면 저장한다" 는 뜻입니다. 1시간에 1건, 5분에 100건, 1분에 1만 건입니다.

**이 조건을 못 채우면 저장이 안 됩니다.** 한가한 시간에 재시작하면 한참 전 상태로 돌아가는 것이 이 때문입니다. 쓰기가 드문 Redis 일수록 잃는 범위가 넓어집니다.

```sh
docker exec myapp-redis redis-cli CONFIG GET save
docker exec myapp-redis redis-cli LASTSAVE      # 마지막 저장 시각
```

`LASTSAVE` 는 유닉스 시각으로 나옵니다. `date -d @1758500000` 으로 읽습니다.

#### Redis 가 원본인 것이 있으면 AOF

세션이나 진행 중인 상태처럼 [Redis 가 원본인 것](/blog/redis-basics/#원본이-어디-있느냐로-갈립니다)을 담고 있다면 AOF 를 켜는 편이 낫습니다.

```
appendonly yes
appendfsync everysec
```

`appendfsync` 가 얼마나 자주 디스크로 밀어낼지 정합니다.

| 값 | 동작 |
| --- | --- |
| `always` | 매 쓰기마다. 가장 안전하고 가장 느립니다 |
| `everysec` | 1초에 한 번. 최악의 경우 1초분을 잃습니다 |
| `no` | OS 가 알아서. 가장 빠르지만 잃는 양을 예측할 수 없습니다 |

`everysec` 가 기본이고 대개 이걸 씁니다. `always` 는 쓰기가 많으면 눈에 띄게 느려집니다.

#### 컨테이너로 띄웠다면 볼륨을 같이 봐야 합니다

두 파일 모두 컨테이너 안의 `/data` 에 쓰입니다. 공식 이미지는 이 경로를 **익명 볼륨**으로 선언해 두었습니다. 컨테이너 레이어에 쌓이지는 않지만, 이름이 없어서 **컨테이너를 새로 만들면 새 익명 볼륨이 붙습니다.** 이전 데이터는 남아 있어도 새 컨테이너에서는 보이지 않습니다.

그래서 버전을 올리며 컨테이너를 갈아 끼우는 방식이면 그때마다 빈 상태로 시작합니다. 영속성을 켜 둔 의미가 없어집니다. 바인드 마운트나 이름 있는 볼륨을 직접 지정해야 합니다.

```sh
docker exec myapp-redis redis-cli CONFIG GET dir          # 어디에 쓰고 있나
docker inspect myapp-redis --format '{{json .Mounts}}'    # 그 경로가 마운트돼 있나
```

`Mounts` 의 `Type` 이 `volume` 이고 `Name` 이 무작위 문자열이면 익명 볼륨입니다. `bind` 이거나 이름을 직접 준 `volume` 이어야 컨테이너를 갈아 끼워도 이어집니다.

```sh
docker run -d --name myapp-redis \n  -v /opt/myapp-redis/data:/data \n  -p 6379:6379 \n  redis:7 redis-server --appendonly yes
```

### 메모리가 차면

`maxmemory` 에 도달했을 때의 동작을 `maxmemory-policy` 가 정합니다.

| 정책 | 동작 |
| --- | --- |
| `noeviction` | 아무것도 버리지 않고 **쓰기를 거절**합니다. 읽기는 됩니다 |
| `allkeys-lru` | 오래 안 쓴 키부터 버립니다. 만료를 걸었는지와 무관하게 |
| `volatile-lru` | 만료가 걸린 키 중에서만 버립니다 |

담는 것이 무엇이냐에 따라 골라야 할 값이 **정반대로** 갈립니다.

| 담는 것 | 정책 | 이유 |
| --- | --- | --- |
| 캐시 | `allkeys-lru` | 버려도 관계형 DB에서 다시 채웁니다 |
| 세션, 진행 중인 상태 | `noeviction` | 버리면 안 됩니다. 에러를 받아 알아채는 편이 낫습니다 |

**세션 저장소에 `allkeys-lru` 가 걸려 있으면 메모리가 찰 때 사용자가 조용히 로그아웃됩니다.** 에러 로그도 남지 않습니다. Redis 는 지시받은 대로 오래된 키를 버린 것이고, 앱은 "키가 없다" 만 보기 때문입니다.

#### maxmemory 가 0 이면

한도가 없다는 뜻입니다. 장비 메모리를 다 쓸 때까지 늘어나다 커널에 종료됩니다. 원본이 메모리에 있으니 종료되는 순간이 곧 손실입니다.

컨테이너로 띄웠다면 **컨테이너 한도보다 낮게** 잡습니다. Redis 는 데이터 외에 클라이언트 버퍼와 복제 버퍼에도 메모리를 씁니다. 같게 잡으면 Redis 가 자기 한도에 닿기 전에 컨테이너가 먼저 죽습니다.

```sh
docker run -d --name myapp-redis \n  -m 2g \n  redis:7 redis-server --maxmemory 1500mb --maxmemory-policy noeviction
```

#### 지금 상태 보기

```sh
docker exec myapp-redis redis-cli INFO memory | grep -E "used_memory_human|maxmemory_human|maxmemory_policy"
docker exec myapp-redis redis-cli INFO stats | grep evicted_keys
```

`evicted_keys` 가 0 이 아니면 **이미 키가 버려지고 있다는 뜻**입니다. 세션을 담고 있다면 그만큼 로그아웃이 일어났다는 것입니다.

`CONFIG SET` 으로 지금 바꿀 수 있지만 재시작하면 사라집니다. 영구 적용은 설정 파일이나 실행 옵션에 넣어야 합니다.

```sh
docker exec myapp-redis redis-cli CONFIG SET maxmemory 1500mb
```

## 사용 글에서 뺀 확인 절

「볼륨 빼두기」 끝에 붙이면 된다. 볼륨을 설명한 뒤 "제대로 붙었는지 확인하는 법" 으로 이어진다.
사용 글 「영속성」 끝에는 "여기서 말하는 재시작은 같은 컨테이너를 껐다 켜는 것이다. 새로 만들 때는
사본 파일이 어디 있느냐가 걸린다" 는 문단이 있었다. 세팅 글에서 둘을 잇는 문장으로 쓸 수 있다.

#### 저장 경로와 마운트

```sh
docker exec myapp-redis redis-cli CONFIG GET dir          # Redis 가 파일을 쓰는 컨테이너 안 경로
docker inspect myapp-redis --format '{{json .Mounts}}'    # 그 경로가 이어진 컨테이너 밖 위치
```

컨테이너를 지우고 새로 만들어도 데이터가 남는지를 이 두 결과로 판단합니다.

`Mounts` 는 이런 식으로 나옵니다.

```json
[{"Type":"bind","Source":"/opt/myapp-redis/data","Destination":"/data", ...}]
```

`Destination` 이 컨테이너 안 경로, `Source` 가 실제로 파일이 놓이는 호스트 경로입니다. 먼저 **`CONFIG GET dir` 로 나온 경로가 `Destination` 중에 있는지** 봅니다. 있으면 그 항목을 아래 표에서 찾습니다.

| 나온 것 | 컨테이너를 지우고 새로 만들면 |
| --- | --- |
| `Type` 이 `bind`, `Source` 가 `/opt/...` 같은 호스트 경로 | 남습니다. 새 컨테이너에 같은 `-v` 를 주면 그 폴더를 다시 씁니다 |
| `Type` 이 `volume`, `Name` 이 `redisdata` 처럼 직접 붙인 이름 | 남습니다. 같은 이름을 `-v` 로 주면 이어집니다 |
| `Type` 이 `volume`, `Name` 이 `3f9a1c…` 같은 긴 무작위 문자열 | 이어지지 않습니다. 도커가 자동으로 만든 볼륨이라, 새 컨테이너에는 또 새 볼륨이 붙습니다. 옛 파일은 남아 있어도 새 컨테이너에서 보이지 않습니다 |
| `dir` 과 같은 `Destination` 이 없음 | 사라집니다. 파일이 컨테이너 안에만 있습니다 |

마지막 줄은 설정 파일에서 `dir` 을 `/data` 가 아닌 곳으로 바꿨을 때 생깁니다. 공식 이미지가 자동으로 잡아 주는 자리는 `/data` 뿐이라서, 다른 경로로 바꾸면 그 경로도 `-v` 로 따로 빼야 합니다.

위와 같은 이유로 「영속성」 확인 절도 뺐다. 「껐다 켜면 무엇이 남나」 끝에 "지금 켜져 있는지 확인하기" 로 붙인다.

#### 영속성

Redis 는 데이터를 메모리에 두기 때문에, 재시작하면 메모리에 있던 것은 사라집니다. 디스크에 사본을 써 두는 설정이 켜져 있어야 다시 켤 때 그 사본을 읽어 되살립니다. 그 설정이 켜져 있는지 봅니다.

```sh
docker exec myapp-redis redis-cli CONFIG GET appendonly
docker exec myapp-redis redis-cli CONFIG GET save
docker exec myapp-redis redis-cli LASTSAVE      # 마지막 저장 시각
```

| 나온 값 | 재시작하면 |
| --- | --- |
| `appendonly` 가 `yes` | 거의 다 남습니다. 기본 설정이면 잃는 것은 마지막 1초분입니다 |
| `appendonly` 가 `no`, `save` 에 값이 있음 | 마지막으로 저장한 시점까지 남습니다 |
| `appendonly` 가 `no`, `save` 가 빈 값 | 아무것도 남지 않습니다 |

`LASTSAVE` 는 유닉스 시각으로 나옵니다. `date -d @1758500000` 으로 읽습니다.
