# 메모  JVM 과 컨테이너 메모리

블로그 글에서 뺀 내용이다. 지금 쓰는 서버에서는 필요가 없어서 빼 뒀고, 나중에 다룰 일이 생기면 여기서 가져간다.

2026-09-22 확인한 것:

- 개발 서버 62GB, 컨테이너 40개, 전부 `limit=0` (한도 없음)
- `cas_2.1.1` 의 힙 최대치 15.7GB = 62.79GB 의 1/4. 이론대로 잡혀 있었다
- 40개 합계 사용량은 약 7GB. 천장 근처에 가는 것이 하나도 없다
- `Exited (137)` 이 10개 있었으나 전부 `OOMKilled=false`. 메모리로 죽은 적은 2년간 한 번도 없다
- 137 은 `docker stop` 이 10초를 기다렸다가 강제 종료한 흔적이었다. 원인은 메모리가 아니라 시그널 전달이다

---

### 메모리는 얼마나 쓰게 되나

도커는 컨테이너 메모리에 **기본적으로 한도를 걸지 않습니다.** 자바는 그 상태에서 "보이는 메모리의 1/4" 을 힙 최대치로 잡습니다. 한도가 없으면 보이는 것이 서버 전체라, 62GB 서버에서는 천장이 15.7GB가 됩니다.

대개는 그대로 둬도 됩니다. 앱이 실제로 그만큼 쓰지 않으니까요. 한도가 필요해지는 것은 한 서버에 여러 개를 올렸고 그중 하나가 메모리를 계속 늘릴 수 있을 때입니다. 한도가 있으면 그 컨테이너만 죽고, 없으면 서버 전체가 흔들립니다.

```sh
docker run -m 3g ...          # 한도는 도커에 준다
-XX:MaxRAMPercentage=75       # 그 안에서 힙이 차지할 비율만 자바에 준다
```

`-Xmx2g` 처럼 고정 숫자를 지정하는 것은 피합니다. 도커 한도를 바꿔도 따라가지 않아 두 값이 어긋납니다.

지금 어떻게 잡혀 있는지는 이렇게 봅니다.

```sh
docker stats --no-stream      # LIMIT 이 서버 전체 메모리면 한도가 없는 것
docker exec myapp java -XX:+PrintFlagsFinal -version | grep -i maxheapsize
```

한도를 넘겨 커널에 종료당하면 `docker ps -a` 에 `Exited (137)` 이 남습니다. 다만 137은 "강제 종료됐다" 는 뜻일 뿐이라 `docker stop` 이 10초를 기다렸다가 죽인 경우도 같은 값입니다. 메모리 때문인지는 따로 확인해야 합니다.

```sh
docker inspect myapp --format '{{.State.OOMKilled}}'
```

## 쿠버네티스로 가면 달라진다

파드 매니페스트의 `resources.limits.memory` 가 사실상 필수다. 스케줄러가 그 값을 보고 노드를 고르기 때문에 안 적으면 배치가 어긋난다. 그때 이 내용을 다시 본다.
